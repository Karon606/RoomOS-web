# 도메인: 재고 관리

핵심 파일: `app/(app)/inventory/{overview.ts(잔량 계산), actions.ts, InventoryClient.tsx}`.

## 품목 식별 = (propertyId, category, label) 유니크
`TrackedItem`은 `@@unique([propertyId, category, label])`. **qtyUnit 은 식별자가 아니다**(표시용 메타데이터, null 가능). 구매(Expense)의 품목 귀속은 (category, itemLabel)로 판단.
- 잔량/소모/입수/단가 계산의 구매 매칭은 **느슨 매칭**(`qtyUnit이 null이거나 같으면 일치`)으로 통일됨. 엄격(완전일치)이면 단위 미입력 구매가 누락됨(과거 라면·물티슈 버그).

## 수령확정 = 반드시 위치에 배치
`confirmReceipt`는 위치 미지정으로 받아도 **품목 허브(hubLocationId → 영업장 기본 창고 → 첫 위치)에 자동 배치**하고 자동 점검(`sourceExpenseId`)을 생성한다. 안 그러면 위치별 점검이 미배치 입고분을 못 세어 잔량에서 증발(과거 라면 120개 버그).
- 인라인 일괄수령은 **순차** 처리(동시 호출 시 자동점검 경합).
- **멱등**(2026-07-10, 쌀 신고): receivedAt이 이미 있으면 재호출은 그대로 성공 반환 — 응답 유실 후 재클릭이 자동 점검을 또 만들어 입고량이 이중 가산되는 것 방지. receivedAt 갱신 + 자동 점검 생성은 한 트랜잭션(중간 실패 시 '수령됐는데 잔량 미반영' 장부 과소 방지).

## 허브 차감 클램프는 조용히 삼킨다 (2026-07-10 쌀 사건)
위치별 점검의 보충이 허브 장부 잔량보다 크면 `Math.max(0, 허브 − 보충)`으로 0 클램프되고 **부족분은 어디에도 기록되지 않는다**. 장부 허브가 실물보다 적으면(실측이 오래됨) 보충 한 번에 총량이 급락해 소진임박 오탐 — 쌀: 창고 장부 20에서 5층 보충 +20 → 창고 0, 총량 28.5(실물 ~68). 허브(창고)도 주기적으로 실측해야 하는 이유.

**봉합(2026-07-23, 신고 f37a93cc)**: 조용한 클램프 대신 서버가 감지해 막는다. `detectHubShort`(lib/stockCheckMerge)가 `restockedQty > 허브 base`면 `HUB_SHORT` 반환 → 클라 `HubShortDialog`가 (1)다른 위치→허브 이동 (2)허브 실측 유도 (3)그냥 진행(`allowHubClamp:true`)을 묻는다. 오탐(장부<실물) 대비로 실측을 권함. 요점:
- **서버 단일 게이트**가 정본 — 두 보충 경로를 모두 커버해야 한다. 경로 A(`locationPatch`, 위치 패널)는 서버 base에서, 경로 B(`locationQtys` 마커, CheckForm)는 마커 합 vs 서버 재구성 허브(직전점검 허브+`additionsSinceCheckByLocation`)로 감지. `updateStockCheck`(CheckEditForm 수정)에도 경로 B 게이트 필수 — 빠지면 수정 경로로 쌀 재발(클래스 반만 닫힘).
- **경로 B 재시도는 이동 출처 위치를 `locationQtys`에서 제외**해야 유령 재고(총량 과다)가 안 생긴다. 절대값을 그대로 재전송하면 이동으로 깎인 출처가 carryOver 제외로 stale 복원돼 이중 계상. 이동/강행 저장 **두 재시도 경로 모두** `excludeLocationIds`를 넘겨야 함(한쪽만 넘기면 강행 저장으로 재발).
- **판정 허브 = 클라 차감 허브**여야 한다. 클라가 `restockHubLocationId`(isHub 위치)를 넘겨 서버 검출(`resolveItemHubLocationId` 폴백)과 일치시킴 — 어긋나면 거짓 음/양성.
- 이동은 `transferLocationStock`(shortfall만), undo는 이동+보충 두 checkId LIFO `deleteStockCheck`.

## 위치별 점검 더블클릭 방지
저장 중복 제출 차단: 클라 동기 가드(`savingRef`/`submittingRef`) + 서버 멱등(같은 patch면 재적용 안 함). `locationPatch`는 상대 차감(허브 −보충)이라 재적용 시 허브 2배 차감되던 버그.

## 잔량 계산 모델 (overview.ts)
`currentStock = 마지막 점검 remainingQty + (점검 이후 수령 구매·무상입수)`. 같은 날 중복 점검은 최신만 채택(dedupSameDay). 입고 귀속은 `receivedAt`(수령일) 기준.

## 위치 숨김 = (품목,위치) 쌍의 closedAt (2026-07-18, 1b93ce7·c04ad4b·f2cb21c·17aebf8)
품목별로 보관위치를 화면에서 가리는 기능(운영자 명명 '숨김', c8912381 종결). `TrackedItemLocation.closedAt`(null=표시).
- **표시 술어는 서버 한 곳**(overview): `closedAt != null` 이고 현재 잔량 `< 0.001` 이면 `InventoryRow.hiddenLocationIds` 에 담는다. 표시 소비자는 멤버십으로만 거른다. **`locations` 는 절대 필터하지 않는다** — 필터하면 '위치 안 쓰는 품목' 분기(`locations.length===0`)가 오발동해 보정 저장이 breakdown 없는 점검을 만든다.
- **자동 치유**: 숨긴 위치에 어떤 경로로든 재고가 들어오면 잔량>0 이 되어 다시 보인다(실증됨). 재고가 조용히 사라지는 경로가 구조적으로 없다. 그래서 8개 백도어 경로에 가드를 흩뿌리지 않아도 된다.
- **음수는 0 취급(숨김)**. `Math.abs` 금지 — 표시가 이미 음수를 0 클램프하므로 절댓값 판정이면 잔량 -5 위치가 "0kg 인데 영원히 안 사라지는 칩"이 된다. ε=0.001(기존 관용 오차와 동일).
- **잔량 소스 = (B) 계열**(마지막 점검 breakdown + 이후 입수·폐기 위치별). lastCheck 단독 금지 — 위치 미지정 입수가 breakdown 에 안 잡혀 "총량엔 있는데 어느 칩에도 없는 재고"가 된다. overview 는 배치 3쿼리로 N+1 없이 계산.
- **`setItemLocations` = 3-way diff** (deleteMany 전체교체 금지 — closedAt 소실 + 재고 든 위치 무단 제거). 빠진 id: 재고 있으면 거부 / 비고 이력 없으면 삭제 / 비고 이력 있으면 숨김. 실효 허브가 빠지면 거부. 사후조건 P: 링크>0 이면 열린 링크 최소 1개. `batchSetItemLocations` 는 **가산 전용(union)** — 배치 모달이 빈 Set 에서 시작해 '교체' 개념이 성립 안 함.
- **reopen(다시 표시) vs undoClose(적용취소)는 다르다**: reopen 은 이관 점검 유지, undoClose 는 이관 점검 삭제+허브 원복. UI 의 '다시 표시'는 reopen. **reopen 후 클라 selected 에도 즉시 반영해야 한다** — state 는 refresh 로 재초기화되지 않아, 안 넣으면 다음 저장 때 조용히 재숨김(17aebf8).
- **허브 불변식은 양방향이다**: 허브는 숨길 수 없고(setItemLocations 거부), **숨긴 위치는 허브가 될 수 없다**(setItemHub 가 closedAt:null 만 허용 + 드롭다운 제외, b92c3cb — 한쪽만 막으면 역순 우회 뒷문이 생긴다). 잔량 있는 위치 숨김+이관+허브 승격은 `closeItemLocation` 서버액션에 구현돼 있으나 **현재 UI 미연결(데드코드)** — 필요해지면 UI 만 얹으면 된다. 빈 위치 숨김(실사용 케이스)은 선택 해제+저장으로 동작.
- 병합은 source 링크의 closedAt 을 전파(target 우선), unmerge 는 3세대 payload 하위호환(gen0 없음/gen1 ids/gen2 {id,closedAt}).
- 점검·보정 폼은 숨긴 위치를 여전히 0 입력행으로 보여준다(후속 개선 후보) — 데이터는 무해(0 저장=유지, 양수 저장=자동 재표시).
- 후속 2건(b92c3cb 등록): exportAllData 백업에 trackedItemLocation(closedAt 포함) 누락 / reopen 이 0행 갱신에도 성공 토스트(동시성 한정, 무해). undo 페이로드는 클라이언트발 값 — **각 필드를 품목 스코프로 검증**할 것(B1 선례).

## 불변식: 재고가 들어간 위치엔 반드시 링크가 있다 (2026-07-17, 67ccfa3·06585a5)
**모든 (품목 T, 위치 L)에 대해, T 의 재고가 지금 L 에 들어가 있다면 `TrackedItemLocation(T,L)` 이 존재한다.** 현재시제 판정 기준 = T 의 마지막 점검 `StockCheckLocation` 중 `remainingQty > 0` 인 행.
- **왜 치명적인가**: 위치별 재고확인 탭(`InventoryClient.tsx` `row.locations.some(...)`)과 보정 폼이 **링크로 필터**한다. 링크 없는 위치의 재고는 화면에서 통째로 사라진다(오류신고 601303c5 — 김치 20kg 중 15kg). 총량에는 잡히는데 위치 어디에도 안 보인다.
- **더 나쁜 것**: 타임라인 보정 폼이 예상 20 / 실측 5 라는 **가짜 차이 −15 를 보여주고**, 운영자가 그걸 옳게 정정하면 총량이 5 로 박혀 15kg 이 조용히 사라진다. `isReconcile` 이 분실·오차로 흡수해 경고도 없다. 화면이 거짓을 보여주고 그 거짓을 고치면 데이터가 깨지는 구조라 더 악질이다.
  - 주의: 재고 카드에서 여는 보정(`expectedFor`)은 차액을 허브에 얹어 diff 0 이라 안전. **두 보정 화면의 동작이 다르다.**
- **쓰기 계약**: 어떤 코드도 링크 없이 `StockCheckLocation` 행을 쓰지 않는다. 쓰려면 같은 트랜잭션에서 링크를 먼저 만든다.
- **막은 생성기 4개**: (1) `transferLocationStock` — 점검만 만들고 링크 미생성. 이동 대상은 영업장 전체 위치(`getItemLocationStock`)라 미링크 선택이 정상 경로이고, 김치 orphan 의 유일한 출처였다. **양쪽(from·to) 링크한다** — 맞바꿈은 재고를 양쪽에 넣으므로 도착지만 링크하면 출발지에 새 orphan 이 생긴다(06585a5, 적대검증 지적). (2)(3) `confirmReceipt` 폴백·지정위치 — 영업장 기본 허브(`isHub`)를 무검사로 썼다. **`isHub` 는 영업장 기본값이지 품목별 선언이 아니다.** (4) `additionsSinceCheckByLocation` — 같은 깨진 체인. (5) `mergeTrackedItems` — 링크를 안 옮기고 source delete 로 cascade 소멸시켜 이전된 breakdown 을 전부 orphan 으로 만들었다. 합집합 병합 + undo payload 에 `sourceLocationIds`·`targetLocationIdsBefore`.
- **정본 리졸버 `resolveItemHubLocationId`** — 위치 미지정 배치는 반드시 **링크된 위치 중에서** 고른다(hubLocationId 우선 → 영업장 isHub 가 링크됐을 때만 → **화면에 먼저 보이는 열린 링크(DFS 랭크 첫 번째)** → null). 폴백 허브에 링크를 만들어주는 안은 기각 — 운영자가 선언한 적 없는 위치를 사실로 만든다.
  - **3순위가 sortOrder 였다가 DFS 로 바뀌었다(2026-09-14 트리).** 트리에서 sortOrder 는 **형제 사이** 순서라 다른 부모의 값끼리 비교하면 뜻이 없다 — 루트 `4층 주방`(1)과 그 자식 `선반`(0)에만 링크된 품목은 미지정 입수가 `선반` 으로 가는데 카드는 `4층 주방` 을 먼저 보였다. 화면에 먼저 보이는 칸이 곧 귀속처다.
  - **쌍둥이가 둘이다** — 화면 `overview.resolveHubSync`(순수, 쿼리 0)와 서버 `ledgerShift.resolveItemHubLocationId`. 갈리면 카드가 보여 주는 칸과 수량이 들어가는 칸이 달라진다. 전부 루트인 데이터에선 DFS 순 == sortOrder 순이라 **데이터 대조로는 안 잡힌다** — `check-stock-ledger-parity` 의 소스 가드가 두 정의를 함께 본다.
- **아직 안 막은 생성기 2개(2단계)**: `setItemLocations`·`batchSetItemLocations` 가 재고 유무를 안 보고 링크를 `deleteMany` 한다. **품목 설정에서 재고 든 위치 체크를 풀고 저장하면 그 수량이 즉시 증발한다.** 옮기기가 잔량 0 출발지 링크까지 보존하는 것과 정면 비대칭. 고치려면 "재고 있는 위치를 떼면 어떻게 되나"를 정해야 하므로 위치 닫기(2단계) 계약에 묶는다. 영업장 소속 검증 공백도 같이.
- **백필**: `scripts/backfill-orphan-item-locations.mjs` (드라이런 기본, `--apply`, 멱등). 대상 = 마지막 점검 breakdown 중 잔량>0 + 링크 없음. 전 이력이 아니라 **현재시제**로 좁힌다 — 과거 0 행까지 링크하면 의도적으로 해제했던 위치가 부활한다. 2026-07-17 실행 = 김치 2행.
- **검증**: orphan 4소스(StockCheckLocation·StockAddition·StockDisposal·Expense.receivedLocationId) 전부 0행 + 전 품목 `total == byLoc 합`. 커밋 메시지 참조.

## 평균 소모율 = 최근 30일 '합산' (2026-07-17, eaa6726)
`avgDaily = 최근 30일 구간 consumed 합 / 그 구간들의 days 합`. `daysUntilEmpty = floor(currentStock / avgDaily)`이고 이게 알림(`dashboard/alerts.ts` lowstock)의 유일한 입력.
- **단일 구간 추정은 폐기됐다**(종전: 마지막 두 점검 차이). 점검 간격이 1~3일이라 표본이 1개뿐 → 그 구간이 크면 과대(라면 8/일, 실제 4.1 → 임박 오탐), 작으면 과소(쌀 0.5/일, 실제 3.45 → 소진 175일로 표시), **0이면 추정이 사라져 무알림**(김치·수세미·물티슈·핸드워시). 자주 점검할수록 알림이 나빠지는 구조였다.
- **합산이어야 하는 이유 = telescoping.** 구간별 값을 개별 표본으로 다루면(중앙값·EWMA) 입고 타이밍 오차(한 구간 +X, 다음 구간 −X)가 상쇄되지 않고 표본에 영구히 남는다. 월별 사용량 산식이 쓰던 원리와 동일하며 **구간 시리즈를 공유한다**(신규 쿼리 0).
- **분모는 달력 span 이 아니라 '포함된 구간 일수의 합'.** 보정(isReconcile) 구간을 소모에서 빼면 그 일수도 함께 빠져야 한다. 안 그러면 소모율이 과소평가되어 알림이 사라진다. consumed 와 항상 같은 구간 집합 위에서 계산할 것.
- **창 컷오프는 KST 달력일 기준**(`StockCheck.date`가 `@db.Date`=그 날 UTC 자정이라 표현을 맞춤). 서버 로컬 `new Date()`로 잡으면 배포 TZ(Vercel=UTC)에서 창이 하루 흔들린다.
- **avgDaily 의 3-상태**: 양수=추정 성립, **0=관측했으나 안 씀**, **null=추정 불가**(관측 7일 미만 / 창 총합 음수=장부 모순). 0과 null 을 뭉개지 말 것 — 그게 원래 버그의 근원이었다. 창 총합이 음수여도 0으로 클램프하지 않는다(허브 클램프 사건처럼 장부 모순은 상시 조건이라, 0으로 누르면 '안 씀'으로 위장되어 영구 무알림).
- 창 경계를 걸친 구간은 통째로 포함(소모를 일별로 쪼개면 없는 정보를 지어내는 것) → 실제 관측일수가 30을 넘을 수 있어 `avgDailyBasisDays`로 노출하고 화면에 "최근 N일 기준"으로 부기한다. 카드 아래 "최근 N일 동안 X 소모"는 **마지막 점검 구간**이라 범위가 다르다(둘은 서로 다른 값이 정상).
- 최소 관측 7일 — 구매 직후 점검 1회로 D-3 오탐 나던 리클린 사례 방어. 점검 1회뿐이라 구간이 없는 품목만 최초구매 기준 폴백을 탄다. 점검 2회 이상이나 전부 7개월 이전이면 avgDaily 소실(의도 — 낡은 데이터로 알림 금지).
- **보류된 제안**: "재고 0 + 소모율 미상이면 재고 없음 알림". 그 술어가 `InventoryClient.tsx` suggestHide(단종 후보 → '숨기기' 버튼)와 동일해, 아카이브 안 한 방치 품목 전량이 영구 알림이 된다. 채택하려면 '조회 구간 내 소모 이력 있음' 같은 추가 게이트 필요.

## 월별 사용량의 3-상태 (2026-07-17, 8837d32)
`monthlyConsumption.qty`는 `number | null`. **0 = 점검했으나 안 씀, null = 그 달엔 점검 자체가 없음(미관측)**. avgDaily의 0/null 관례와 동일하게 맞춘 것으로, 둘을 뭉개면 추적 시작 전 달이 '사용량 0'으로 그려진다(운영자 "편차가 너무 큰 것 같다" 의문의 근원). `observed: boolean` 플래그 대신 null을 쓴 이유는 strictNullChecks가 모든 소비처에 "이 달을 어떻게 볼 거냐"를 강제로 묻기 때문 — 플래그는 기존 소비처가 0을 조용히 읽고 지나간다.
- **산식 자체는 정확하다.** 일당 환산하면 쌀 2.5/3.6/2.8, 라면 3.8/6.5/4.4로 안정적. 문제는 전부 표시였다.
- 막대 표시: 미관측=막대 없음(회색 막대는 '소량 사용'으로 오독됨) / 실사용 0=시리즈색 2px 실선(0도 데이터라 색 유지) / **진행 중인 이번 달=`--inspect-bg` 트랙 + `--inspect-fg` 라벨**(가이드 §04 기존 토큰). 진행 중인 달을 만월과 나란히 두면 급감으로 오독된다.
- **이번 달 판정은 시계가 아니라 배열 마지막 슬롯**(구조적). 클라 `new Date()`로 월 키를 비교하면 브라우저 TZ에 따라 월 경계에서 어긋난다.
- 넣지 않기로 한 것: 범례(10.5px 하한에서 범례가 24px 차트보다 커짐), 막대별 일당 환산(같은 카드 '평균 소모/일 · 최근 N일 기준'과 중복), 빗금·패턴(이 크기에서 안 보임), 예측 막대(소모를 일별로 쪼개는 건 없는 정보를 지어내는 것).

## 비품·자재 배정 차감 = 선입선출 (2026-07-09 운영자 확인)
집계 카드(여러 구매분 합)에서 배정/이동 시 `buildSplitOps`가 **구매일 오래된 행부터** 차감한다(같은 날짜는 큰 행부터, 분할 최소화). 이전의 '수량 큰 행부터'는 어느 구매분에서 빠질지 예측 불가 + 단가가 섞여 방별 비용 왜곡("랜덤으로 빠진다" 신고). 옮기기 모달에서 특정 구매분만 지정해 차감할 수도 있다(구매 2건 이상일 때 select).

## 규격 곱셈 정본 specMultiplier (2026-07-21, 신고 0d6242f0)
구매 수량의 규격 환산은 서버·클라이언트 전 지점(9곳)이 `lib/units.ts specMultiplier`를 쓴다 — convertUnit 직접 곱셈 금지.
- 규칙: 품목 단위로 환산 가능하면 환산 곱셈 / specUnit 미상('개' 등 비물리·null)이면 원값 곱셈(구식 데이터 폴백) / **specUnit이 알려진 물리 단위인데 품목 단위와 차원이 다르면(120g vs '개') 곱하지 않고 qtyValue만** — 그 규격은 개당 중량·용량 속성이지 포장 입수량이 아니다.

## 소진임박 알림 실효 임계값 (2026-07-21, 신고 edffb4a7)
알림 판정은 `daysUntilEmpty <= effectiveAlertDays`. **실효 임계값 = max(품목 설정 D-N, 재주문 리드타임 중앙값 + 여유 2일)** — overview.ts 한 곳에서 계산해 카드 배지·대시보드 알림·종·푸시가 단일 소스로 정합. 리드타임 = 최근 수령 구매 최대 6건의 (receivedAt − date) 일수 중앙값(0~30 클램프). 설정 폼은 원값(alertThresholdDays) 표시.

## 세트 상품 등록 규칙 (2026-07-22, 신고 91b812ce)
"주문 1 = 실물 N"(세트)의 저장 방식은 **품목 성격으로 갈린다**: 소모품(추적 카테고리)은 규격 흡수(qty 1세트 + specValue N — 재고 수학이 규격 곱 의존), **비품(내구재)은 개수 환산(qtyValue=N, 총액 불변·개당 단가)** — 비품은 qtyValue가 곧 개수·방 배정 단위라 규격 흡수가 부적합. 정본 patch는 FinanceClient durableSetCountPatch.
- 등록·수정 저장 시 미확답 세트 의심(setHint)이 남은 비품 항목은 choiceDialog 확답 강제(취소=저장 중단). 세트 감지 정규식은 한글 접미사 \b 버그 수정됨("3개입" 감지).

## 품목 정체성 = 품명 문자열 하나다 (2026-08-06, 전문가 3라운드 설계 C안)
**재고 카드를 나누고 싶은 구분은 품명에 쓴다. 메모로 남길 구분은 규격 직접 입력(specText)에 쓴다. 시스템은 구분의 종류(용량·색·향)를 해석하지 않는다.** 스키마 변경 없음 — `TrackedItem` 이 이미 `@@unique([propertyId, category, label])` 이므로 정체성은 label 하나뿐이고, 규격·색·향을 담을 자리는 원래부터 없었다. 새 필드를 만드는 대신 **품명이 정체성이라는 사실을 화면이 말하게** 한 것이 이 설계다.
- **비대칭은 버그가 아니라 도메인 의미다.** 소모품에서 specText 는 비정체성 메모(잔량 수학에 안 들어감), 비품·자재에서는 카드 구분 서술(같은 이름 다른 규격을 `AssetsClient` 가 제목 옆에 병기해 나눔). 소모품은 '같은 물건을 계속 사서 쓰는' 잔량 추적이고 비품은 '개별 물건을 배정하는' 대장이라, 같은 칸이 두 뜻을 갖는 게 맞다. 통일하려 들면 한쪽이 망가진다.
- **규격 게이트 = 규격 칸 통로의 품명 승격 문지기**(`FinanceClient.handleAddExp`, 카테고리 이력 게이트 직후). 운영자가 10L 마대와 20L 마대를 규격 칸으로 구분하려 하면 카드는 조용히 하나로 합쳐진다. 그래서 저장 직전에 한 번만 묻는다: 나누면 이번 구매를 `'{품명} {값}{단위}'` 로 승격하고, 이력이 단일 규격이면 구 카드도 `'{품명} {기존값}{단위}'` 로 개명한다(`renameTrackedItemLabel` → 재고 정본 `updateTrackedItem`, 지출 라벨 전파 내장). '같은 품목으로' 를 고르면 그 규격이 이력에 남아 다음부터 침묵한다 — **이력이 곧 기억이다**(설정도, 예외 목록도 없다).
- 발동 조건은 전부 AND 이고 하나라도 어긋나면 침묵(보수 편향): 품명에 숫자 없음(이미 규격이 이름에 있으면 침묵) · specValue>0 과 specUnit 존재 · 활성 카드가 있고 `trackUnit='qty'` · `specMultiplier` 가 null(규격이 수량 계산에 참여하면 그건 크기가 아니라 양이다) · 이력 규격 집합이 비지 않았고 이번 규격이 그 어느 것과도 **물리 동치가 아님**(2.1L 과 2100ml 는 같은 규격 — `convertUnit` 비교). 실지출 340건 전수 재생에서 **충돌형 발동 0건**(설계 검증치 재현).
- **읽기 쪽 짝은 specHint**(`overview.resolveSpecHint`, `unitHint` 와 같은 전원일치 규칙). 수량 카드의 규격은 잔량 수학에 안 들어가 화면 어디에도 안 보이는데, 그 크기가 곧 정체성인 경우가 있다(특수마대 10L). 구매 규격이 전원일치일 때만 카드 제목 옆에 캡션으로 병기하고 혼재면 null — 실측: 특수마대 10L·테프론 테이프 10m·점보롤 500m 점등, 주방용 물티슈·키친타월(롤타입) 비점등. 표시 전용이고 편집 값 자리(SettingsForm)에는 쓰지 않는다.
- **표시 계층은 꼬리 크기 토큰을 캡션으로 분리한다**(`lib/units.ts` `splitSizeLabel`, 재고 카드 제목·상세 모달 제목). "종량제쓰레기봉투 (20L)" 은 이름 "종량제쓰레기봉투" + 캡션 "20L" 로 보이지만, **정체성·병합 키·검색 매칭은 라벨 원문 그대로** 쓴다 — 떼어낸 값은 화면 밖으로 나가지 않는다. 토큰이 없거나 둘 이상이거나(장판몰딩 12m x 7.4cm) 이름 중간이면 원문 폴백. specHint 와는 **구조적 배타**(specHint 는 품명에 숫자가 있으면 서버가 null) 라 캡션 자리가 겹치지 않는다. 단위 집합은 병합 가드 `actions.ts` `sizeSignature` 와 동일하게 유지(양쪽 주석 상호 참조) — 갈리면 화면이 크기로 떼는 값과 병합이 크기로 보는 값이 달라진다. 실측: 활성 28건 중 봉투 7건 분리, 특수마대·A4용지·7종 세트 등 21건 폴백.
- 유사명 다이얼로그도 같은 원칙으로 말한다 — "같은 품목이면 합쳐서 기록되고, 색상·규격이 다른 물건이면 새 품목으로 나뉘어 재고도 따로 관리됩니다". 버튼이 카드 하나냐 둘이냐를 정한다는 사실을 문장으로 드러낸 것.

## 점검은 절대값, 입수는 델타 — 그 사이를 잇는 것이 원장 조정이다 (2026-08-19, 쌀 40kg)

**`StockCheck.remainingQty` 와 `StockCheckLocation.remainingQty` 는 그 시점 잔량의 절대값이고, `StockAddition`·`StockDisposal`·`Expense.receivedAt` 은 델타다.** 읽기 정본(`overview.currentStock`)이 "마지막 점검 절대값 + 그 이후 델타"라서 **모든 점검은 그 앞의 델타를 전부 삼킨다.** 여기서 사고가 난다.

- **증상**: 8/18 로 잘못 넣은 무상 입고 40kg 을 8/10 으로 정정하면, 그 사이 점검(8/12·8/14)의 저장 절대값은 그대로인데 입고만 그 앞으로 가서 잔량에서 40kg 이 통째로 증발한다. **틀린 날짜일 때는 우연히 맞고, 날짜를 옳게 고치는 순간 깨진다** — 정직한 정정이 처벌받는 구조였다. 운영자는 결국 전 기록을 지우고 다시 입력했다.
- **채택 의미론 = 기록된 소모는 보존하고 입고 귀속만 옮긴다.** 조정량은 `shift(C) = (바뀐 뒤 기록이 C 에 반영되면 +수량) − (바뀌기 전 기록이 C 에 반영되면 +수량)` 라는 상수 이동이다. 두 세계 모두에서 반영되는 점검(입고보다 뒤에 센 실측)은 0 이라 자동으로 대상에서 빠진다. 정본은 `lib/stockLedger.ts planStockShift`(순수, 쿼리 0).
- **자동 적용하지 않는다.** 서버는 계획만 만들고(`previewStockAdditionShift`) 확인 다이얼로그가 영향받는 점검을 **실제 숫자로** 나열한 뒤 '함께 조정' 과 '이 기록만' 을 가른다. 실측값을 시스템이 조용히 덮으면 실사라는 행위 자체가 무의미해진다(패널 3인 공통 반대). 어긋나는 점검이 0 건이면 아무것도 묻지 않는다.
- **조정은 그 입수가 도착한 위치에만 얹힌다.** 위치별 점검에서 **허브 칸은 파생값**(`hubAutoAfter = 허브이전 − 보충합`)이고 주방 칸이 유일한 실측이다. 창고 도착분의 조정이 허브에만 얹히므로 실측한 주방 값은 구조적으로 불변이다.
- **전체 보정(isReconcile)에서 전파가 멈춘다.** 보정은 실측 리셋 선언이라 앞선 기록 변경에 흔들리면 안 되고, 그 뒤는 새 기준선이 이미 사실을 흡수했다.
- **건드리지 않는 것**: 보충 마커(`restockedQty` — 이동량이지 잔량이 아니고, `undoConfirmReceipt` 의 '실측 머지' 판정이 이것 하나에 걸려 있다), `StockCheck.createdAt`(밀면 `effTime` 구간 귀속 순서가 조용히 바뀐다).
- **음수는 0 클램프가 아니라 거부다.** 조용한 클램프가 쌀 사건의 원형이다(위 §허브 차감 클램프). 어느 점검이 음수가 되는지 이름으로 알린다.
- **링크 없이 breakdown 행을 만들지 않는다** — 같은 트랜잭션에서 `TrackedItemLocation` 을 먼저 만들고 되돌리기 페이로드에 기록한다(위 §불변식).
- **등록·수정·삭제 세 경로 모두**에 건다. 수정만 막으면 소급 등록으로 같은 증발이 나고, 삭제를 빼면 조정된 만큼이 유령 재고로 남는다. 등록의 역조정은 삭제가, 삭제의 역조정은 복원이 맡는다(대칭이 유닛 테스트로 박혀 있다).
- 회귀: `scripts/test-stock-ledger.ts`(verify:fast, 51건 — 운영자 쌀 시나리오 값 그대로), `scripts/check-stock-ledger-parity.ts`(verify:db — 소스 가드 + 점검 헤더 대 위치합 + 화면 총량 대 위치합).

**같은 날 경계는 입력 시각으로 가른다.** 델타가 점검보다 뒤인가의 정본 술어는 `date > 점검일 || (date == 점검일 && createdAt > 점검 createdAt)` 이다(`overview.sumAdditions`, `lib/stockLedger.deltaAfterCheck`). `getStockAsOf` 만 `date > baseDate` 라 **같은 날 점검보다 늦게 입력된 입수가 프리필에서 통째로 빠졌고**, 그 프리필을 저장하면 그 수량이 새 기준선에서 영구히 사라졌다(2026-08-19 수정, 정본 함수 호출로 대체). 폐기 등록의 잔량 초과 게이트도 같은 함수를 쓴다.

**아직 안 닫은 같은 클래스(접점)**: `updateStockCheck` 의 점검 날짜 이동, `updateExpenseFromInventory` 의 수령일(`receivedAt`) 이동(값 있는 이동 — 비움은 아래 취소 정본으로 봉합됨), 폐기(`StockDisposal`) 수정 경로 부재, `assets/actions.setAssetReceived` 의 `receivedAt` 직접 쓰기(자동 점검 동기화 없음).

## 지출(구매 수령) 델타의 전파 짝 (2026-08-19, 점보롤 백로그 4건)

**구매 델타의 반영 경계는 무상 입수와 다르다** — `receivedAt(실시각) > 점검.createdAt` 이면 미반영(`sumPurchases` 의 gt, 정본 `lib/stockLedger.purchaseAfterCheck`). 무상 입수는 (date, createdAt) 축. 조정 계획(`planStockShift`)은 두 델타를 모두 받고 순회·보정 정지 축은 (date, createdAt) 하나다(백필 점검의 축 차이는 테스트 박제).
- **적용층 공용 모듈** `app/(app)/inventory/ledgerShift.ts`(비액션·서버 전용) — `applyShiftRows`·`revertShiftRows`·`resolveItemHubLocationId`·`matchedTrackedItemForExpense`(qtyUnit 느슨 매칭)·`convertedPurchaseQty`(useSpec 게이트, 읽기 정본과 동일 — confirmReceipt 의 수령량 산출과는 specUnit 미설정 품목에서 다를 수 있고 조정의 기준은 읽기 쪽). 'use server' 파일은 async 액션만 내보낼 수 있어 분리했다.
- **지출 수정(updateExpense)**: 수량·규격 정정은 미리보기(`previewExpenseStockShift`) 후 3지선다(함께 조정/이 기록만/취소, `lib/stockShiftAsk` 공용 정본) — adjustStock 게이트로만 적용, 자동 점검 메모(`[수령 자동] +N`)도 재생성, 조정만 되돌리는 `undoExpenseStockShift`. **정체성 이탈은 차단**: 다른 기존 카드로 이동(라벨 dup·카테고리 이동 대상에 카드 존재)·qtyUnit 변경으로 느슨 매칭 절단·수령완료 추적 구매의 다품목 재분할 — 수령 취소 후 변경이 정본 경로. 진짜 이름변경(카드째 개명)과 카드 없는 카테고리 이동(저장 후 동기화 흐름)은 현행 유지.
- **수령 취소 정본 `cancelReceiptCore`** — `undoConfirmReceipt` 와 `updateExpenseFromInventory` 의 수령일 비움이 같은 가드를 탄다(종전 비움 경로는 실측 머지·이후 점검 가드를 통째로 우회하는 뒷문). adjustFollowing 으로 이후 점검에서 수령분을 함께 빼며 취소(자동 점검은 계획에서 제외하고 삭제), `undoCancelReceipt` 가 자동 점검을 **입력 시각(createdAt)까지** 복원 — 안 살리면 구매 반영 경계가 조용히 달라진다. 실측 머지 가드(restockedQty)는 계속 하드 차단. **자동 점검 없는 구식 수령(실측 288/322건)의 무가드 취소도 봉합** — 반영 점검이 있으면 조정 없인 거부(재수령 이중 가산 방지).
- **삭제(deleteExpense)**: 자동 점검 있으면 종전 차단 유지(수령 취소가 정본). 없는 구식 수령은 3지선다 후 adjustStock 로 함께 조정 삭제, undo 에 조정 스냅샷 동봉. **재고 제외/재포함도 같은 물음**(제외=델타 제거, 포함=대칭 복원 — 계획 대칭성이 undo 를 대신한다).
- **시작 재고 정식 자리**: 품목 추가 모달의 시작 수량(선택) — 오늘(KST) 날짜 `[시작 재고]` 점검을 같은 트랜잭션 생성, **isReconcile 앵커**(뒤늦은 과거 입수 등록의 전파가 여기서 멈추고 이전 구간이 소모로 안 잡힘). 0 도 유효(재고 없이 시작 명시). 부활(숨김 해제)도 같은 앵커.
- **같은 날 중복 앵커는 안내만**(createStockCheck sameDayNotice, 자동 삭제 절대 금지) — 수령 자동 점검·보정·보충 마커 실린 앵커는 사건 기록이라 중복으로 안 친다(점보롤 앵커 오판 삭제 교훈). locationPatch(병합 저장)는 설계된 흐름이라 제외.
- **실측 > 장부 신호**: `overbookExcess`(lib/stockLedger, 오차 0.001) — CheckForm 이 입력 중 경고 박스로 '입수 기록 누락 의심' 안내(수령 대기 건수 부기). 첫 점검(시작 선언)·미입력 상태 제외. 자동 수정 없음.
- 감지망: check-stock-ledger-parity 에 지출 게이트 축 5종(preview 존재·updateExpense/deleteExpense adjustStock·cancelReceiptCore 게이트+머지 가드·수령일 비움의 정본 경유·클라 물음 연결).

## 지출의 브랜드·상세제품명 (2026-08-27 신설, 1단계)

운영자 요구 — "같은 라면이라도 진라면일지 삼양라면일지도 아는게 좋고, 모니터도 삼성껀지 LG인지".

`Expense.brand`·`Expense.productName` 두 칸(널 허용). **표시·검색 전용이고 단가 계산과 재고
수학에 일절 관여하지 않는다.** `specText` 가 2026-07-03 에 들어온 것과 같은 층위다.

**제품 카탈로그 테이블을 안 만든다.** 이 앱의 품목 정체성이 이미 품명 문자열 한 축으로 통일돼
있어서다(`TrackedItem` 유니크, `inventory/ledgerShift` 매칭 정본, OCR 어휘 사전). 카탈로그를
세우면 "이 지출이 무슨 물건인가"의 진실 원천이 둘로 갈라진다. 훗날 필요해지면 쌓인
(itemLabel, brand, productName) 조합에서 파생 생성할 수 있다.

**채움의 주 경로는 영수증 인식이다.** 영수증 원문에는 이미 '오뚜기 진라면 매운맛'이 찍혀 있는데
어휘 사전이 통일 품명으로 접으면서 버리고 있었다(원문 `rawLabel` 은 별칭 학습에만 쓰고 저장 안 함).
이 두 칸이 그 버려지던 자리다. 프롬프트에 경계를 못 박았다 — 보이는 표기만·추측 금지·label 복사
금지·색상과 사이즈는 specText 로.

**직전값은 채우되 '지난번 값'이라고 말한다**(운영자 확정). 규격·수량은 틀리면 눈에 띄지만
브랜드는 조용히 틀린 채로 저장되고, 그 값이 2단계에서 재고를 가르는 기준이 되면 진라면 산 것이
삼양 재고에 쌓인다. 손대는 순간 표시가 사라진다.

**저장 경로가 셋이다** — 단일 품목·다품목·방별 분배. 한 갈래만 고치면 브랜드가 첫 줄에만 남는다.
감지망 `check-expense-brand-wiring` 이 세 갈래와 수정 프리필·hidden input·프롬프트 문구를 본다.

**기존 데이터는 빈 칸이다.** 추정으로 안 채운다. 운영자가 근거(기간별 구매 내역)를 주면 그때
백필한다 — "언제부터 언제까지 산 건 진라면 매운맛" 식으로. 예행 후 적용, 근거는 스크립트 주석에.

**같은 파일에 이름이 겹치는 칸이 있다.** 금융 자산 등록 폼의 `name="brand"`(은행·카드사)다.
별개 `<form>` 이라 FormData 가 안 섞이지만 감지망은 hidden 만 세도록 좁혀 뒀다.

## 병합은 지출의 단위를 덮어쓰지 않는다 — 카드를 단위 무시로 (2026-09-07)

재고 부착 판정(`seedTrackedItemsFromExpenses`)은 (카테고리·품명·규격값·규격단위·**수량단위**)

수량단위가 다른 구매는 라벨을 고쳐도 튜플이 계속 어긋나 **영원히 미부착**이었다. "병합 처리

  재발 감지다. 그물은 `scripts/check-merge-unit-wiring.mjs`(배선 단언 25건).


## 길이 규격이 붙은 카드에서 trackUnit 은 '잘라 쓰는가'를 뜻한다 (2026-09-07 운영자 확정)

운영자 원문. "어떤 빨래줄은 잘라서 사용할 수 있지만 이 빨래줄은 그러한 빨래줄은 아니다."

- 잔량 표시 판정은 `overview.ts` 의 `useSpec = trackUnit !== 'qty' && !!specUnit` 하나다.
  길이 규격이 붙은 카드에서 이 값이 곧 **재단 가능 여부**다. 잘라 쓰면 길이가 잔량이고
  (spec — 장판·호스·전선), 통으로 쓰면 개수가 잔량이다(qty — 빨래줄 10m 한 세트).
- **새 칸을 만들지 않는다.** 축은 이미 trackUnit 이 쥐고 있고, 옳게 선언된 선례가 점보롤이다
  (qty + specUnit m). 없던 것은 칸이 아니라 **묻는 자리**였다 — 영수증에서 카드가 자동
  생성될 때 기본값이 굳고 아무도 확인하지 않았다.
- **묻는 조건은 좁다.** 추적 카테고리 · 카드 없음 · specUnit 이 길이 · **qtyUnit 이 길이가
  아님**, 넷을 다 만족할 때만이다. 마지막이 핵심 — 장판처럼 수량 자체를 미터로 적는 품목은
  재단이 자명해 묻지 않는다. 길이 규격에 개수 단위가 붙은 경우만 애매하다. 폭·두께는
  specText 에 남는다.
- 빨래줄이 어긋난 근원은 영수증 인식이 "길이 10m x 두께 5mm" 를 specText 에 넣으면서
  10m 를 specValue 에도 같이 넣은 것이다.
- 규격 값이 **하나도 없는** 카드(수세미·박스테이프)는 지금 우연히 수량으로 세어 맞게 보이지만
  규격이 붙은 구매가 한 번 들어오면 그날 숫자가 뒤집힌다(규격 자동 반영). qty 로 못박으면
  그 자동 반영이 건너뛴다. 표시는 무변동이라 선언해 두는 쪽이 항상 낫다.
- 정합 검사(check-item-category-split)는 종전에 길이 규격을 **무조건 오류**로 봤다. 그 단정은
  장판까지 잡는 반쪽이었다. 묻는 자리가 생긴 뒤로는 선언된 값이라 오류가 아니라 눈으로 보는
  명부로 낮춘다.

## 이월 행은 파생 박제, 실측 행만 절대값 (2026-09-11, 김치 · 운영자 승인 설계)

운영자 신고 — "9/10 점검을 나중에 고쳐(4층 상단 4·하단 6) 9/11에도 자동 반영돼야 하는데 안 딸려간다."

`StockCheckLocation` 한 행은 두 종류다. **이월 행**은 "직전 같은 위치 값 + 사이 입수 − 이번 점검의
허브 차감"을 저장해 둔 **파생 박제**고, **실측 행**은 그날 실제로 센 **절대값**이다. 종전에는 둘이
구분 없이 같은 칸에 들어가 있었고, `updateStockCheck` 은 뒤 점검을 아예 보지 않았으며 이월 경로
(`createStockCheck` 의 base·carryOver)는 qty 만 복사해 "이 값이 어디서 왔는가"를 버렸다.

- **표식 `StockCheckLocation.carried`**(Boolean?). true=이월, false=실측, null=표식 이전 구식 행.
  찍는 자리는 저장 경로다 — `applyLocationCheck` 이 점검한 위치만 false·나머지 전부 true(허브 자동
  차감 행도 파생이라 true), `carryOver` 행 true, 폼이 보낸 `locationQtys` 는 전부 false.
  **클라가 보낸 carried 는 쓰지 않는다** — 실측 선언은 저장 경로가 아는 사실이다.
- **구식 행(null)은 휴리스틱** — 저장값이 파생식과 같으면 이월로 본다(행이 없으면 값 0). 애매하면
  실측으로 보는 쪽이 안전하다(덜 옮긴다).
- **전파 정본 `lib/stockLedger.planCheckPropagation`**(순수, 쿼리 0). 위치별로 걷다가 실측을 만나면
  **그 위치만** 멈추고 다른 위치는 계속 간다. 보정(isReconcile)·위치 내역 없는 점검에서는 전체 정지
  (planStockShift 의 정지 규칙과 같은 축). 총량 `remainingQty` 도 **위치 합으로 다시 센다** —
  overview 가 총량과 위치 행을 둘 다 읽어서 한쪽만 옮기면 화면 두 경로가 갈라진다.
  뒤 점검에 없는 위치는 새 값 > 0 일 때만 행을 만든다(링크 불변식은 applyShiftRows 가 지킨다).
  음수는 0 클램프가 아니라 거부이고 **어느 점검의 어느 위치인지** 이름으로 알린다.
- **자동 적용하지 않는다.** `previewStockCheckPropagation` 이 계획만 만들고 §14 확인창이 행 단위
  숫자를 나열한 뒤 '함께 조정'/'이 기록만'/'취소' 를 가른다. 게이트는 `updateStockCheck(propagate)`.
  수정과 전파는 **한 트랜잭션**이고 되돌리기는 **한 스냅샷**(`StockCheckEditUndo` — 점검 자체 +
  `LedgerShiftUndo`)이다. 따로 되돌리면 '수정만 원복, 전파는 남음' 이라는 중간 상태가 장부에 남는다.
- **표식은 계획이 판정한 행 전부에 박는다**(운영자 후속 오더). 덮어쓴 행은 true, 실측으로 보고 그
  위치에서 멈춘 행은 false, 새로 만든 행은 true. **값이 같아도 표식이 다르면 계획에 행으로 나온다** —
  조용히 넘기면 그 행은 영원히 구식(null)으로 남아 다음 수정 때 또 휴리스틱으로 추측된다.
  그래서 값이 안 바뀐 위치도 판정 대상(live)이다. 되돌리기 스냅샷은 표식의 **이전 값**도 담는다
  (null 도 유효한 이전 값이라 '없음'의 기준은 undefined 뿐이다).
- 확인창은 **값이 바뀌는 행만** 나열한다. 표식만 찍는 행을 '17kg 에서 17kg 으로' 라고 적으면
  확인창이 제 말을 못 한다. 표식은 '함께 조정' 을 고른 뒤 서버가 계획을 다시 세워 같이 찍는다.
- 확인창 문법은 공용 정본(lib/stockShiftAsk)과 같은 4단이다 — 유지 한 줄 · 영향 한 줄 · 행 · 안내.
  값 전환은 §29 화살표 표기(`17kg → 7kg`)다. 조사를 붙이면 단위 없는 품목에서 '4개으로' 가 된다
  (같은 결함이 있던 lib/stockShiftAsk 두 자리도 같이 고쳤다).
- 회귀: `scripts/test-check-propagation.ts`(62건 — 김치 3점검 실제 값 박제),
  `check-stock-ledger-parity` 에 소스 가드 + 이월 행 대조(carried=true 행이 파생식과 다르면 붉게).

보충 마커(`restockedQty`)는 '창고에서 이 위치로 옮긴 양'이라 창고 자신에게는 뜻이 없다. 그런데

  `finalN = afterN ?? beforeN` 이라 그대로), 서버 `applyLocationCheck` 은 `isHubChecked` 면 마커 0.
  한쪽만 막으면 다른 경로로 다시 들어온다.
- 정리 `scripts/fix-hub-restock-marker.ts`(예행 기본, `--apply`) — 마커만 null 로, 잔량은 안 건드린다.

## 재고 대조 셋은 '필터 통째 결손'을 못 잡는다 (2026-09-11 탐침)

`app/(app)/inventory/overview.ts` 의 `excludeFromInventory: false` 를 지우고 재고 대조 셋
(verify-overview-parity · check-stock-ledger-parity · check-stock-asof-parity)을 돌리면 **전부
초록으로 지나간다.** 같은 코드 경로를 서로 견주거나 내부 정합을 보기 때문에 필터가 통째로 빠지면
양쪽이 똑같이 틀려 차이가 안 난다. 오늘 만든 대시보드 대조(`verify-dashboard-parity`)는 잡지만
기준 JSON 이 있어야 돌아 상시 그물이 못 된다.

그래서 소스 가드 `scripts/check-inventory-exclude-filter.mjs`(verify:fast)를 뒀다. 규칙은
**잔량 정본에서 prisma.expense 를 만지는 함수는 그 몸통에 `excludeFromInventory` 를 갖는다**
(지금 sumPurchases·resolveUnitHint·resolveSpecHint·dedupSameDay 넷). 주석은 걷고 본다.

**한계를 알고 쓴다.** 이 가드는 필터의 존재만 보지 의미는 못 본다. 값을 뒤집거나 조건을 다른 곳으로
옮기는 변경은 못 잡는다. 그 몫을 질 데이터 대조가 아직 없다는 것이 남은 빈자리다.
덧붙여 `getMonthlyInflow`(actions.ts) 같은 **이력 표시** 질의의 필터를 지우는 것은 잔량을 안 바꾸므로
대조가 초록인 것이 옳다 — 두 축을 섞어 보면 안 된다.

## 위치점검 머지는 carried 도 승계한다 (2026-09-14, 4층/5층 주방)
같은 날 연속 위치 점검이 앞 위치의 **실측 표식(carried=false)** 을 이월(true)로 뒤집었다. `applyLocationCheck` 의
비점검 가지가 `carried: true` 를 무조건 찍고 base 형 `LocBreakdown` 에 `carried` 가 없어서다. 신고 8319ba10 이
`restockedQty` 를 `keepMarker` 로 보존한 것과 **같은 클래스에서 한 필드 옆**이 빠져 있었다.
- **규칙은 승계다.** base 가 표식을 갖고 오면 그대로, 없으면(직전 점검 base) true. **null 은 null 로** — true 로
  접으면 "모르는 것"을 "파생이다"로 단정해 `planCheckPropagation` 이 null 에 걸어 둔 휴리스틱을 무력화한다
  (맞바꿈·전체보정·수령자동 행이 null 이다).
- **`createStockCheck` 의 base(직전 점검)에는 싣지 않는다.** 실으면 어제의 실측 표식이 오늘 새 점검의 이월 행에
  박혀 그 위치의 전파가 영구히 멈추고, 값은 안 바뀌어 그물도 침묵한다. `restockedQty` 와 정확히 같은 비대칭이고
  `check-stock-ledger-parity` 가 양쪽 base 조립문을 소스 가드로 지킨다.
- `applyLocationCheck` 는 순수함수인데 진리표가 없었다. `test-stock-check-merge`(verify:fast) 신설.
- **백필**(`scripts/backfill-check-carried-flip.ts`, 날짜 인자·예행·--apply·--revert). 표식은 memo 의
  `위치별 점검 (X)` 에서 X = 먼저 잰 위치 = 실측이라는 구조적 사실로 되돌린다(memo 는 첫 저장에서만 박힌다).
  `restockedQty > 0` 휴리스틱은 보충 없이 잰 위치를 못 가려 쓰지 않는다.
- **같은 위치 재점검(전=후)은 보충 마커를 지운다** — "마지막 값으로 덮어씀" 한계가 임시저장 혼동을 타고 실제로
  터졌다(9/14 15:04 재저장). 허브 차감은 이미 일어났으므로 마커 = 직전 허브 − 지금 허브 − 다른 마커 합 으로
  역산했다(운영자 승인). 마커 없는 나중 실측 행이 **정확히 하나**일 때만 쓴다.
- 그물이 못 보는 자리: 실측값이 우연히 파생값과 같은 뒤집힘(핸드워시·물티슈 4층이 그랬다). 대조 그물은 증상
  그물이지 클래스 그물이 아니다 — 클래스는 진리표가 막는다.

## 보관 위치 트리 (2026-09-14, 운영자 승인 설계)

운영자 요청이 출발이다. "4층 주방에 김치냉장고가 있고 상단·하단이 있는데 각각 개별로 놔버리니
한번에 체크를 못 해. 레이어가 하나 밖에 없어서." 9/11 김치 점검에서 냉장고 상단·하단 분류를
깜빡해 9/10 내역을 나중에 고쳐야 했던 사고가 근거다.

### 구조 — 자기참조 parentId, 트리는 표시층일 뿐이다
`StorageLocation.parentId` 자기참조. **허브·잔량·숨김·박제·전파 다섯 기제는 전부
`storageLocationId` 집합 위에서 돌고 그 집합은 트리와 무관하게 평면**이다. 트리는 표시·그룹핑
층이다. 판정 정본은 `lib/locationTree.ts`(순수, 쿼리 0), 진리표는 `scripts/test-location-tree.ts`.

불변식 넷이 전부다. **"재고는 잎에만"이 아니다 — 모든 노드가 자기 재고를 가진다**(잎만 허용하면
김치냉장고를 4층 주방 아래로 넣는 순간 4층 주방의 9품목을 새 잎으로 옮기는 이관 점검이 필요해진다).
1. **순환 없음** — 자기 자신·자손 아래로 못 옮긴다(`wouldCycle`).
2. **깊이 상한 4**(`MAX_DEPTH`) — 루트가 1단계. 옮길 때는 **서브트리 최대 깊이까지** 세야 자손을
   단 노드가 상한을 넘겨 앉지 않는다.
3. **형제 이름 유일** — 루트(parentId NULL)끼리도 본다. Postgres 유니크는 NULL 을 서로 다르게
   보므로 루트는 부분 유니크 인덱스가 맡는데 **그 인덱스는 Prisma 스키마 밖에 산다**(db push 한 번에
   사라진다). 서버 검사가 1차 관문이다.
4. **영업장 안 전체 이름(pathName) 유일** — 형제 유일(3)은 같은 부모 안만 본다. 루트
   `4층 김치냉장고 상단`(오늘의 평면 데이터)과 트리 `4층 김치냉장고` 아래 `상단` 은 부모가 달라
   둘 다 통과하면서 전체 이름이 글자까지 같아진다 — **이관 과도기에 실제로 생기는 모양**이다.
   그러면 화면에 같은 칩이 둘 뜨고 비품 배정 이력 역조회(`byPathName`)가 중복이라 아무것도 못 찍어
   되돌리기가 멈춘다. 판정은 `conflictingPathName`(lib/locationPaths, 순수)이고 쓰기 셋(생성·이름
   바꾸기·이동)이 부른다. 이동·이름 바꾸기는 **서브트리 자손의 새 경로까지** 본다.

### pathName — 표기는 공백 결합
`4층 김치냉장고` 아래 `상단` 의 표기 경로는 `4층 김치냉장고 상단`. **오늘의 평면 이름과 글자가
같다** — 트리를 안 만든 영업장은 픽셀 하나 안 바뀌고, 만든 영업장도 보던 문자열 그대로다.
정본은 `flattenDfs`, 영업장 단위 색인은 `app/(app)/inventory/locationPaths.ts`.

- **화면에 찍는 위치 이름은 전부 `pathName`** 이다. 그물 `check-location-name-axis.mjs`.
- **예외는 트리 행뿐**이다 — 위치 관리 모달의 행, 점검 패널의 그룹 헤더, 위치 드롭다운 행은 그
  노드 한 칸의 `name` 을 찍는다. 조상 경로를 **들여쓰기가 말하기** 때문이고, 거기서 고치는 대상이
  그 한 칸 자체이기 때문이다. 같은 그물이 그 전제(들여쓰기가 실제로 그려지는가)를 함께 본다.
- **`name` 은 없어진 칸이 아니라 더해진 칸이다.** `pathName` 을 새로 얹었고 `name` 은 트리 편집용
  원본으로 남겼다. 덮었다면 트리 편집기가 읽을 원본 이름이 사라진다.
- **저장 문자열도 pathName 이다.** 위치별 점검의 memo `위치별 점검 (X)` 는 백필 매칭 키다
  (`backfill-check-carried-flip` 이 X 로 실측 위치를 되찾는다). 평면 이름이면 같은 이름의 칸이 둘
  생기는 순간 기록만으로는 영원히 복원할 수 없다. 체인 저장에서 X = **고른 서브트리 루트**의 pathName.

### 체인 저장 — 서브트리를 한 번에, 허브는 마지막
위치별 점검 패널에서 부모를 고르면 **자손 전부**가 점검 대상에 든다(펼쳐 보이고 행마다 개별 입력).
저장 단위는 (품목, 위치) 쌍이고, **서버는 무변경**이다 — 같은 날 연속 점검 병합 정본
(`applyLocationCheck`)을 그대로 타므로 마커 보존·`carried` 승계·허브 게이트가 한 줄도 안 바뀐다.

1. **순차**다. 병렬로 쏘면 같은 품목의 칸마다 새 점검이 서고, 그 각각이 직전 점검을 base 로 잡아
   앞 칸의 실측이 조용히 사라진다. 값은 저장되고 장부만 틀어지는 종류의 결함이다.
2. **이어 붙인다.** 같은 품목의 두 번째 칸부터는 **이 저장에서 만든/쓴 점검 id**(chainIds)에
   `updateStockCheck` 로 얹는다. props 의 stale 한 `lastCheckId` 를 다시 집으면 칸마다 새 점검이 선다.
3. **허브 행이 맨 마지막**이다. 허브 실측을 먼저 쓰면 그 위에서 다시 차감돼 이중으로 빠진다.
4. **같은 저장에 그 품목의 허브 실측이 있으면 비허브 행의 부족 게이트를 건너뛴다**(`allowHubClamp`).
   지금 세는 허브 값이 곧 정답이라 부족 판정이 뜻이 없고, 허브 행이 마지막에 그 값을 덮는다
   (`HubShortDialog` 의 '허브 실측' 선택지를 앞당겨 적용한 것). **허브 실측이 없으면 게이트는
   오늘과 똑같이 선다** — 쌀 사건의 조용한 0 클램프는 그대로 막혀 있다.
5. **비원자**다. 상단을 저장한 뒤 하단이 실패하면 거기서 멈추고 **어디까지 저장됐는지**를 버튼 줄
   위 고정 영역(스크롤 밖)에 남긴다. 저장된 행의 임시저장만 비워지고 남은 행은 그대로다.
   원자 저장으로 올리려면 `detectHubShort` 를 합산형으로 넓혀야 해서 쌀 사건 봉합 자리를 건드린다.
6. 허브 부족(HUB_SHORT)도 **멈춤**이다. 팝업이 그 한 건을 처리하면 나머지를 이어 달린다. 나머지를
   버리면 팝업을 처리한 뒤 아래 칸의 실측이 조용히 사라진다.
7. **인라인 저장은 닫지 않는다**(입력 비움 + 성공 토스트). 위치별이 재고 화면의 기본 보기가 된
   2026-09-15 부터 인라인 패널에는 닫을 뒤가 없다. 실패 0 이면 `N건 저장됨` 토스트를 띄우고
   입력(`beforeQtys`·`afterQtys`·`mergeChoice`)을 비워 그 자리에 머문다. 비우지 않으면 dirty 가
   남아 `N건 저장` 이 다시 켜지고, 값을 조금만 고쳐도 두 번째 저장이 선다(`createStockCheck` 의
   멱등창은 20초, `updateStockCheck` 는 같은 patch 만 무시한다). 모달 모드(`showBatchLoc`)는
   종전대로 닫힌다 — `onClose` 는 그쪽 전용 prop 이고 인라인에는 아예 넘기지 않는다.

8. **'전체' 는 숲이다**(2026-09-15). 위치 선택기 맨 위의 `전체`(센티널 `ALL_LOCATIONS = '__all__'`)를
   고르면 범위가 `locSubtree(고른 칸)` 대신 **위치 목록 전부**가 된다. 목록이 DFS 순이라 숲 전체가 곧
   트리 순서고, 그룹·행·`buildUnits`·체인은 (품목, 위치) 쌍 위에서 돌므로 **범위만 넓히면 성립한다** —
   허브 마지막·`allowHubClamp`·멈춘 자리·HUB_SHORT 이어 달리기는 한 줄도 안 바뀐다. 두 자리만 다르다.
   · **memo 는 접두 패턴 밖의 다른 문자열** `전체 위치 점검` 이다. `위치별 점검 (전체)` 로 적으면
     '전체' 라는 이름의 위치가 생기는 순간 백필(`^위치별 점검 \((.+)\)$`)이 그 칸의 점검으로 되찾아
     간다 — 저장 문자열은 지울 수 없으니 오염도 되돌릴 수 없다.
   · **들여쓰기 기준 깊이는 1**(루트)이다. 기준식이 고른 노드에서 나오는데 '전체'에는 고른 노드가
     없어, `?? node.depth` 로 떨어지게 두면 모든 행이 0단이 되어 트리가 평면으로 무너진다. 그러면
     트리 행이 `name` 을 찍어도 되는 근거(구조는 들여쓰기가 말한다)가 함께 사라진다.
   · 드래프트 복원은 **한 호출**이다(`getLocationDraftsFor(ids)`, 쿼리 2개). 위치마다 부르던 종전
     방식은 '전체'에서 위치 수 × 2 회 왕복이 된다.
   · 저장은 여전히 쌍 단위 순차라 45쌍이면 서버 왕복 90회다. 그동안 버튼 줄 위 고정 영역과 주 버튼이
     **진행 숫자**(`저장 중 · N/M`)를 센다 — 멈춘 자리가 빈 문자열인 동안은 '달리는 중' 이라는 뜻이고,
     실패하면 같은 자리를 멈춤 문구가 덮는다.

`carried` 규칙은 불변이다 — 점검한 행 false, 비점검 가지 승계(`test-stock-check-merge` 34단언).

### 패널 안 옮기기 — 세다가 옮기게 됐을 때 (2026-09-15, 운영자 승인 (c)안)

세는 도중에 "이건 저쪽으로 옮겨야겠다"가 생긴다. 종전에는 패널 헤더의 `위치 이동` 하나뿐이라
품목을 다시 고르고 출발지를 다시 찍어야 했다. 비허브 품목 행 하단 줄 좌측에 **`다른 곳으로`** 를
두어 그 칸에서 바로 연다(우측 `옮김 없음` 과 같은 한 벌, `justify-between` 한 줄). 모달은 같은
`TransferStockModal` 이고 품목 고정(`lockItem`)·출발지 프리셀렉트(`initialFromId`)만 다르다.

- **허브(창고) 행에는 두지 않는다.** 창고에서 나가는 이동은 도착지 행의 '채운 후' 가 정본이다
  (§27.1 — 같은 일에 입구를 둘 만들지 않는다).
- **기본 순서는 옮기기 → 세기 → 저장이다.** 세고 나서 옮기게 됐으면 **저장을 먼저** 하고 옮긴다.
- **깨지는 경우는 딱 하나다 — '옮기기 전에 센 값을 옮긴 뒤에 저장'.** 점검 시점 정렬은 옮김이
  점검 전이든 후든 정합이라, 남은 구멍은 이 하나뿐이고 화면이 그것을 막는다. 규칙: **옮긴 순간
  그 두 쌍(품목×출발지, 품목×도착지)의 미저장 입력은 무효다.** 메모리 입력값(`beforeQtys`·
  `afterQtys`)과 그 쌍의 서버 임시저장(`deleteStockCheckDraft`, 반환값을 읽는다)을 함께 비운다.
  도착지가 지금 범위 밖이어도 키는 (품목, 위치) 쌍이라 그대로 지워진다 — **그래서 되돌릴 값은
  메모리가 아니라 서버에서 읽는다**(`getLocationDraftsFor([from, to])`). 범위 밖 도착지는 메모리
  `rowDrafts` 에 없어서, 메모리로 잡으면 지워지기만 하고 복원할 값이 없다. 아이템별(`null`)
  드래프트의 그 위치 값도 `deleteStockCheckDraft` 가 함께 벗기므로 둘을 합쳐 주는 그 액션으로 읽는다.
- **패널의 옮기기 진입은 둘이고 규칙은 하나다.** 행 `다른 곳으로` 와 헤더 `위치 이동` 둘 다 같은
  완료 핸들러(`handleTransferDone`)를 탄다. 한쪽만 배선하면 같은 구멍이 옆 버튼에 남는다.
  **장부 잔량이 0(또는 기록 없음)인 행에는 `다른 곳으로` 를 그리지 않는다** — 열어도 출발지 칩이
  없는 막다른 모달이다(그때 `옮김 없음` 이 `ml-auto` 로 제 자리를 지킨다).
- **비우기 전 스냅샷 + §16 적용취소.** 토스트 하나(success, 액션형 6초)가 "옮김 완료 · 두 칸 입력
  비움"까지 말하고(비운 것이 실제로 있을 때만 그 접미가 붙는다), 적용취소는 `deleteStockCheck(이동
  점검, 기대값)` → **빈 칸만** 입력 문자열 복원 → 있었던 임시저장만 재저장(`saveStockCheckDraft`)
  순이다. 6초 사이에 새로 적은 값은 그것이 최신 실측이라 덮지 않는다. 늦게 눌려 위치를 옮긴 뒤면
  패널 상태는 안 건드린다(`locIdRef` 갈림, `handleClearLocDrafts` 와 같은 문법). 두 쌍을 비우고
  남은 드래프트가 없으면 발끝 §12 칩도 내린다(`settleChain` 과 같은 전수 대조).
  **완료 통지의 주인은 하나다** — 패널 진입(`silent`)에서는 모달이 제 토스트를 안 띄운다
  (§27.2 이중 통지 금지).
- **적용취소는 '내가 만든 그 점검' 일 때만 지운다.** 이동 점검은 같은 날·6시간 안이면 뒤따르는
  위치 점검의 **머지 대상**이 된다(`lastCheckId` 가 이 점검이라 `updateStockCheck` 로 얹힌다).
  그대로 `deleteStockCheck` 를 부르면 방금 저장한 실측까지 사라진다. 그래서 `transferLocationStock`
  이 `createdAtMs`·`rowCount`·`markerSum` 을 함께 돌려주고, 적용취소가 그 셋을 `expect` 로 되넘긴다.
  하나라도 달라졌으면 지우지 않고 `'이 이동 위에 점검이 얹혀 되돌릴 수 없습니다.'` 로 끝낸다.
  다른 호출부(헤더 이동 토스트 밖 경로·위치 숨김 적용취소)는 `expect` 없이 종전 그대로다.

**출발지 남은 양(선택) = 실측이다.** 4단계 아래 `옮긴 뒤 {출발지} 남은 양 (선택)` 입력. 적으면
서버가 출발지 행을 `장부 − N` 이 아니라 **그 값**으로 쓰고(`transferLocationStock` 의
`sourceRemainingQty`), 그 행만 `carried: false`(실측)로 박는다. 총량은 행 합이라 실측 차이만큼
변하고 그 구간의 소모가 된다. 안 적으면 종전과 완전히 같다(빈칸이 기본, placeholder 도 빈칸 —
0 을 미리 보이면 '남은 게 없다'는 실측으로 읽힌다). 미리보기 박스가 `장부보다 1kg 적음 · 소모로
기록` / `장부보다 1kg 많음 · 입수 기록 누락일 수 있습니다` 를 한 줄 더 적는다. 맞바꿈이면 뜻이
없어 숨긴다.

- **도착지 행의 `carried` 는 null 이 맞다.** 이동 행은 이월도 실측도 아닌 '이월 + 델타' 다. `true` 로
  선언하면 `planCheckPropagation` 이 파생식으로 덮어써 옮긴 델타를 지우고, `false` 면 세지도 않은
  값이 실측이 되어 그 위치의 전파가 영구히 멈춘다. 그래서 표식을 찍는 행은 **실측 하나뿐**이다.
  다만 null 은 '문을 열어 두는' 것이 아니다 — `lib/stockLedger` 의 휴리스틱은 저장값이 파생식
  (직전 + 입수 − 차감)과 같을 때만 이월로 보는데 이동 행은 옮긴 N 만큼 달라 **항상 실측 판정**이
  나고, 그 행은 **첫 전파에서 `carried: false` 로 확정**된다. 지금 규칙이 맞다는 근거는 '나중에
  정한다' 가 아니라 '확정되는 값이 실측으로도 맞다' 다. 델타 행을 planner 가 '옮김' 으로 알아보는
  표현은 아직 없다(후속 — `knowledge/open-issues.md`).
- **멱등 가드에 `carried` 가 들어간다.** `updateStockCheck` 의 `locationPatch` 멱등 판정이 잔량·마커만
  비교하면, 이동 점검 위에 얹히는 실측이 마침 `장부 − N` 그대로일 때(흔하다) no-op 으로 빠져 그
  행에 실측 표식이 영영 안 박힌다. 세 축(`remainingQty`·`restockedQty`·`carried === false`)이 모두
  같을 때만 건너뛴다.
- **조립 정본은 `lib/transferCheck.ts` 다.** `transferCheckCreateData` 는 순수 조립이라 `actions.ts`
  밖으로 뺐고(`actions` 는 import 만), 세 경우의 표식 진리표를 `scripts/test-transfer-check.ts`
  (verify:fast)가 박제한다 — 실측 있음(출발지 행만 `false`, 도착지 없음) / 실측 없음(둘 다 없음) /
  맞바꿈(둘 다 없음). 진리표는 조립부만 보므로 `measuredFromId = data.toLocationId` 같은 한 줄
  우회는 못 잡는다 — 그 축은 parity 소스 가드가 '대입 우변이 `data.fromLocationId` 뿐' 으로 막는다.
- **거부 규칙은 그대로다**(운영자 결정, 완화 없음). 옮긴 양이 장부 출발지보다 크면 실측을 적어
  와도 거부한다. "장부가 실물보다 적어서 못 옮긴다"는 케이스는 출발지 실측을 먼저 저장해서 푼다.
- `closeItemLocation` 은 같은 `transferCheckCreateData` 를 쓰지만 실측 인자를 안 넘긴다(무변경).
- 감지망: `check-draft-lifecycle` ⑧(완료 핸들러가 두 쌍을 비우는가 · 스냅샷을 서버에서 잡는가 ·
  적용취소가 기대값과 함께 점검을 지우고 **빈 칸만** 되쓰는가 · 두 진입이 같은 핸들러를 타는가 ·
  잔량 0·허브 행에는 버튼이 없는가), `check-stock-ledger-parity` 소스 가드(실측이 있을 때만 출발지
  행 `carried: false`, 도착지 행은 표식 없음, `measuredFromId` 대입 우변 고정, 거부 규칙 생존),
  `test-transfer-check`(조립 진리표 세 줄).

### 부모를 넘나드는 드래그 (2026-09-16, 운영자 승인 — 상호작용 모델 (ii) Finder 식)

종전 손잡이는 **형제 안 순서 전용**이었고 부모를 바꾸려면 `관리 > 옮기기` 모달을 거쳐야 했다.
손잡이를 다른 부모 행 위로 끌어 본 뒤에야 무반응임을 알게 되는 것 자체가 오조작이다. 이제
손잡이가 순서와 상위 위치를 함께 바꾼다. **드래그는 보조 입구고 `옮기기`·`위로`·`아래로` 는
그대로 남는다** — 포인터가 없는 조건에서도 트리를 고칠 수 있어야 한다.

**세 구간.** 한 슬롯 60px(행 54 + 간격 6)을 세로로 가른다.
- 위 경계 12px = 그 행 **앞** 형제 / 몸통 36px = 그 행의 **자식 맨 뒤** / 아래 경계 12px = 그 행 **뒤** 형제.
- **아래 경계는 언제나 '그 행의 뒤 형제'** 다. 한 단 올라가려면 다음 얕은 행의 위 경계로 간다 —
  같은 12px 에 '뒤 형제' 와 '한 단 올리기' 두 뜻을 얹으면 어느 쪽이 나올지 손이 못 센다.
  그 표시선은 **서브트리 뒤**에 선다(자식 단 행의 바로 아래에 그으면 '첫 자식 앞' 으로 읽히는데
  실제로 놓이는 자리는 그 자식들 전부의 뒤다).
- 목록 끝 아래는 최상위 맨 뒤. 몸통 구간은 그 행이 **유효한 부모일 때만** 산다(깊이 상한에 걸린
  행은 슬롯 전체가 형제 구간이다 — 눌러 봐야 아무 일도 안 나는 36px 을 두지 않는다. 그 대신
  이유 줄이 `4단계를 넘어 아래로 넣을 수 없습니다` 를 말한다. 캡션은 '행 가운데에 놓으면 그 위치
  아래로' 라고 말하고 있어, 안 되는 행에서 침묵하면 캡션이 그 행에서 거짓이 된다).
- 들리는 것은 행 하나가 아니라 `locSubtree` 한 덩어리다.

**네 규칙은 서버와 같은 정본 호출이다**(사본 금지). `wouldCycle`(자기 서브트리는 드래그 시작에
`subtreeIds` 로 한 번 센 blocked 집합) · `depthOf(parentId) + 1 + locSubtreeSpan > MAX_DEPTH` ·
`siblingNameTaken(rows, parentId, nextName, id)` · `conflictingPathName(rows, id, parentId, nextName)`.
`nextName` 은 **이름 제안을 적용한 뒤** 이름이다 — 서버가 그 이름으로 보기 때문이다.
이유 문구 다섯은 드래그와 옮기기 모달이 **한 벌로 공유**한다(모듈 레벨 `reasonOf`). 넷째·다섯째
(형제 이름·전체 이름)는 종전에 서버 거부로만 걸리던 것을 화면이 먼저 말하도록 더한 것이다.

**pathName 보존 한 규칙.** 이름 제안은 `preserveName(옛 pathName, 새 부모 pathName)` — 옛 표기
경로에서 새 부모의 접두를 뗀 나머지다. 깊어지면 줄고(떼기) 얕아지면 늘어난다(붙이기). 기본값은
**방향별**이다. 부모가 남으면 켬(`상단` 을 `4층 주방` 아래로 → `김치냉장고 상단`), 최상위로 빼면
끔(`415호 창고` 는 그대로). **드래그 중에는 체크박스를 누를 손이 없다** — 고스트 아래 한 줄은 그
기본값과 §29 미리보기를 보여 주는 **읽는 자리**고, 그때그때 바꾸려면 `관리 > 옮기기` 를 쓴다.
- **옮기기 모달도 같은 산식이다**(2026-09-16 검수 반영). `moveStorageLocation` 도 이제
  `preserveName(옛 pathName, 새 부모 pathName)` 을 쓴다 — 종전엔 이쪽만 현재 `name` 에서 앞부분을
  떼어, 같은 자리에 두 입구가 다른 이름을 놓았다(드래그는 늘리고 모달은 안 늘렸다). 루트 노드는
  `name == pathName` 이라 떼는 방향의 값은 한 글자도 안 바뀐다. 최상위 목적지에 체크를 켜면 옛
  pathName 전체가 이름이 된다 — 규칙 그대로의 붙이기이고, 기본값은 꺼짐이라 손으로 켜야 한다.
- 모달이 **회색으로 잠그는 것은 자리 자체가 안 되는 경우뿐**이다(순환·깊이·지금 있는 자리).
  이름 충돌은 체크박스를 끄면 열리는 자리라 잠그지 않는다 — 고른 뒤에도 겹치면 이유 캡션이 서고
  `옮기기` 버튼이 막힌다(종전엔 기본값 이름이 겹친다는 이유만으로 행이 죽어, 끌 수 있는 체크박스를
  두고도 그 자리를 못 골랐다).

**place 원자성.** 드롭 한 번은 '부모가 바뀌고 그 형제 안 자리도 정해진다' 는 한 동작이다.
`moveStorageLocation` + `reorderStorageLocations` 2연타로 치면 앞이 성공하고 뒤가 실패할 때
**부모만 바뀌고 자리는 맨 뒤인 반쪽**이 남는데, 화면은 이미 놓은 자리를 보여 주고 있으니 운영자는
그 어긋남을 영영 모른다. 그래서 `placeStorageLocation(id, parentId, index, preserve)` 한 트랜잭션이
자기 parentId·name 갱신과 **새 형제 집합 전체 sortOrder 재기록**을 함께 쓴다(형제 전체성은 reorder
와 같은 count 대조). **같은 부모 안 순서만 바뀐 드롭은 여기로 안 온다** — `reorderStorageLocations`
가 맡는다. 부모를 안 건드리는 드롭은 이름 제안도 없고 §16 되돌리기가 이전 순서 배열 한 번이라,
규칙이 더 얇은 그 액션에 두는 것이 맞다.

**낙관 반영이 없다.** 포인터 이동에서 목록 state 를 건드리면 한 프레임에 여러 번 오는 이동마다
트리를 다시 엮게 되고 402px 에서 행이 눈에 띄게 튄다. 목록은 드롭 전까지 한 칸도 안 움직이고
(자리표가 블록 높이를 그대로 채운다), 움직이는 것은 ref 로 DOM 에 transform 한 줄을 직접 쓰는
고스트뿐이다. state 로 올라가는 것은 표시선 자리가 **바뀔 때만**이다. 행 rect 는 pointerdown 에서
한 번만 재고, 스크롤은 목록 rect 하나만 다시 읽어 보정한다. 종전 `locReflow`(실시간 재배열)와
`locOwnerAt`(형제 블록 주인 찾기)은 이 모델에서 쓰이지 않아 지웠다.

**막힌 드롭.** 표시선이 점선이 되고 이유가 모달 하단 고정 한 줄에 선다(행은 흐리지 않는다 —
흐리면 정작 읽어야 할 그 한 줄이 가장 안 읽힌다). 놓으면 스냅백이고, **이름이 걸린 경우에만**
`info` 토스트 + `이름 바꾸기` 액션(그 행의 인라인 편집이 열린다)이 붙는다. 순환·깊이는 토스트가
없다 — 표시선과 이유 줄이 이미 말했고 거기에 토스트까지 얹으면 같은 사실을 두 번 말하는 것이다.

**재고 기제에는 영향이 없지만 역조회는 끊길 수 있다.** 드래그가 바꾸는 것은 `parentId`·`name`·
`sortOrder` 셋뿐이고 그 셋은 `moveStorageLocation` 이 이미 바꾸던 축이다. 허브·잔량·숨김·박제·
전파 다섯 기제는 여전히 `storageLocationId` 집합 위에서 돌고 그 집합은 평면이다 — 여기는 안전하다.
**끊기는 것은 문자열로 거슬러 찾는 쪽이다.** 비품 배정 이력 역조회는 `byPathName` 이 먼저고
실패하면 `byName` 인데, 그 폴백은 **이름이 영업장 안에서 유일할 때만** 값을 준다(중복이면
`undefined` — `lib/locationPaths`). 그래서 pathName 이 바뀌면 옛 문자열로 남은 기록이 그 위치를
못 찾을 수 있고, `상단`·`하단` 처럼 층마다 겹치는 이름은 폴백도 안 선다. pathName 이 바뀌는 드롭은
셋이다.
- **보존을 끄는 드롭**(최상위로 빼기) — 기본값이 꺼짐이라 `4층 주방 김치냉장고 상단` 이 루트에서
  `상단` 이 된다. 옛 경로를 잃는 쪽을 운영자가 고른 것이다.
- **옆 가지로 옮기기** — `4층 주방 김치냉장고 상단` 을 `5층 주방 김치냉장고` 아래로 놓으면 제안이
  `null`(접두 불일치)이라 이름은 `상단` 그대로인데 전체 이름은 `5층 주방 김치냉장고 상단` 이 된다.
  **이름이 한 글자도 안 바뀌는데 경로가 바뀌는 자리**라, 고스트 미리보기가 이름이 아니라
  **pathName 을 기준으로** 뜨는 이유다.
- **접두 불일치 일반** — 제안이 없으면 현재 이름을 그대로 쓰므로 새 부모 경로가 앞에 붙는다.
기본값이 pathName 보존인 것은 이 셋을 최소로 줄이려는 것이지 없애는 것이 아니다.

**감지망.** `check-location-actions-wiring` ⓖ — place 블록의 다섯 규칙 호출·형제 sortOrder 재기록이
**`$transaction` 배열 안**인가(배열 밖 for 루프로 빼는 우회를 잡는다)·`at = Math.min(index, …)`
자리 산수·형제 전체성·`undo: LocationMoveUndo`·권한·영업장, 화면 드롭 핸들러가 2연타 대신 place 를
부르는가, 포인터 이동에 `setLocs` 가 없는가, 캡션이 새 문구인가, 드래그(locHitOf)와 모달이 **같은
reasonOf** 를 부르는가. ⓗ — 적용취소가 `restoreStorageLocation` **하나**를 부르고 rename+move+
reorder 3연타가 없는가, 그 액션이 최종 상태 규칙 넷을 한 트랜잭션 안에서 보는가. `check-location-name-axis` — 표시선 좌측 여백 산식이 `LOC_INDENT_PX` 를 쓰는가
(표시선이 다른 자에 맞춰지면 한 단 들어가는 드롭과 형제로 서는 드롭이 화면에서 구분되지 않는다).

### 적용취소 — 전용 액션이 없다
쓰기 셋이 이전 값을 `undo` 로 돌려준다. **같은 액션을 이전 값으로 다시 부르는 것이 적용취소다.**
- 이름 바꾸기 — `updateStorageLocation(id, 이전 name)`.
- 순서 — `reorderStorageLocations(이전 parentId, 이전 ids)`.
- 옮기기·드래그 배치 — **`restoreStorageLocation(undo)` 한 번**이다(2026-09-16 검수). 여기만
  되돌리기 전용 액션이 있고, 그럴 수밖에 없다. 종전의 `rename → move → reorder` 3연타는 이름
  제안이 pathName 보존이 된 뒤로 **넓히는 방향에서 1단계부터 막힌다** — `4층 주방 김치냉장고`
  아래 `상단` 을 `4층 주방` 아래로 올리면 이름이 `김치냉장고 상단` 으로 늘어나는데(그 층에 이미
  `상단` 이 있어서 늘린 것이다), 되돌리기가 그 층에 선 채로 짧은 옛 이름 `상단` 을 먼저 세우려
  하니 형제 중복에 걸린다. 순서를 뒤집으면(move 먼저) 깊어지는 방향이 같은 이유로 깨진다.
  **어느 순서로도 중간 상태가 규칙을 위반한다.** 그래서 `parentId`·`name`·옛 형제 순서를 한
  트랜잭션으로 되돌리고 규칙(순환·깊이·형제 중복·전체 이름 유일·소속)은 **최종 상태에 대해서만**
  본다. 반쪽 원복도 '어디까지 되돌렸는지' 문구도 함께 사라졌다 — 한 걸음이라 반쪽이 없다.
  `siblingIds`(자기 포함, 옛 부모 아래 순서)는 그 배열 인덱스가 곧 sortOrder 이고, 그새 형제가
  늘거나 줄었으면 전체성 검사에 걸려 거부한다.
- 토스트 제목만 입구마다 다르다. 드래그는 손이 지나간 자리를 눈이 못 따라가는 경우가 있어
  `'4층 주방 김치냉장고 상단' 위치를 '4층 주방' 아래 맨 뒤로 옮겼습니다` 꼴로 **무엇을 어디로**
  놓았는지 다시 읽어 준다(이름은 목록 밖이라 `name` 이 아니라 옛 `pathName` 이다).

### 삭제는 force 로도 하위를 거부한다
`parentId` 가 `onDelete: SetNull` 이라 부모를 지우면 자식이 조용히 루트로 튀어 오르고, 그 순간
자식의 pathName 이 통째로 바뀌어 화면에서 딴 위치가 된다. 기존 2단계 영향 고지(기록 있음 → 강제
삭제)는 하위가 없을 때만 그대로 선다. 화면은 **서버 error 문구를 그대로 인라인**으로 보인다(§27.2).

## 아이템별 점검 폼은 위치 패널과 같은 한 벌이다 (2026-09-15, 운영자 승인 (c)안)

한 품목의 위치별 잔량을 적는 자리가 둘이다 — **아이템별 점검 폼**(상세 모달 → 재고 점검)과
**위치별 점검 패널**(재고 화면 기본 보기). 같은 일인데 축·행 문법·저장 경로가 셋 다 갈려 있었다.

### 갈렸던 세 축
- **허브 칸이 `afterQtys`('채운 후')에 묶여 있었다.** 위치 패널은 2026-09-11 김치 사고 때 이미
  `beforeQtys`('잔량')로 옮겼는데 아이템별 폼만 남았다. 후 − 전(빈칸=0)이 옮김량으로 셈해져
  허브 자기 행에 `restockedQty` 마커가 박히는 입구다(창고에서 창고로 옮기는 일은 없다).
- **허브 칸이 파생값으로 프리필돼 있었다** (`자동 차감 후` = 직전 허브 − 옮김 합). 아무도 세지
  않은 숫자가 칸에 들어 있고, 그 값이 절대값 경로로 나가면 서버가 **실측 선언**(`carried: false`)
  으로 읽는다. 실측 행은 전파가 멈추는 자리라, 파생값이 실측으로 박히면 그 위치의 전파가
  거기서 영구히 멈춘다. 값은 안 바뀌므로 데이터 대조도 침묵한다.
- **저장이 경로 B(절대값 `locationQtys`)였다.** 클라가 허브를 미리 깎아 보내고 서버는 그 값을 믿는다.
  같은 사건을 두 화면이 다른 규칙으로 장부에 적고 있었다는 뜻이다.

### 지금 규칙
- **입력칸은 전부 빈칸으로 시작한다.** 채워 둔 값은 '세었다'는 뜻이 되어 버린다. 허브 실측 여부는
  `beforeQtys[허브] !== ''` 하나로 말한다(플래그 `hubTouched` 폐기 — 같은 사실을 두 곳에서 말하면
  드래프트 복원에서 갈린다. 구 문서 호환은 읽기 한 줄로만 남는다).
- **허브를 안 적으면 서버가 파생값을 남기고, 그 행은 이월(carried:true)이다.** 화면은 그 값을
  참고줄 우측에 `차감 후 N` 으로 미리 말한다(적는 순간 사라진다 — 적은 값이 그 자리의 진실이다).
- **저장은 경로 A** — `createStockCheck({ locationPatches })`. 서버가 `applyLocationChecks` 로
  **순서대로 접는다**. 순서는 비허브 먼저, 허브는 맨 뒤(허브 실측을 먼저 쓰면 그 위에서 또 차감된다
  — 패널 `buildUnits` 와 같은 규칙). 안 적은 행은 패치에 안 실려 직전 점검에서 이월된다.
- **원자다.** 한 패치라도 허브 부족(HUB_SHORT)에 걸리면 **몇 번째 패치**인지를 실어 돌려주고 한 건도
  저장하지 않는다(`HubShortResponse.patchIndex`). 부분 반영으로 끝나면 화면은 '저장됨' 인데 장부는
  절반이 되고, 그 절반이 다음 점검의 base 가 된다. 패널의 체인 저장(비원자)과 갈리는 유일한 축이다 —
  거기는 (품목, 위치) 쌍이 여럿이라 멈춘 자리를 남기는 쪽을 택했고, 여기는 한 품목이라 원자가 된다.
- **멱등창 20초는 모든 패치가 직전 점검 행과 일치할 때만** 삼킨다. 하나라도 다르면 새로 적은 값이
  섞인 제출이고, 그걸 삼키면 그 값이 저장되지 않은 채 '저장됨' 이 된다.
- 경로 B 는 **첫 점검 단순 모드**(직전 점검이 없어 옮김이라는 개념이 없다)와 **타임라인 편집
  폼**(`CheckEditForm` — 저장된 점검 한 건을 고치는 다른 일)에만 남는다.

### 화면도 한 벌
행 문법은 위치 패널이 정본이다 — 참고줄(`저장된 잔량` · `저장된 옮김` · `{창고} 남음`, 우측
`이번 입력 +N` / 허브는 `차감 후 N`), 허브 행은 `잔량` 라벨 + 입력 + 단위 + `저장된 값` 버튼,
비허브는 2열 + `옮김 없음`, 행 캡션은 `Badge tone="inspect"` 3상태. 입력칸 클래스는 파일 맨 위의
공용 상수 `qtyInputCls` 한 벌이다. 아이템별 고유는 점검일(맨 위, 44px)·메모·전체 보정뿐이다.

### 성공 통지의 주인은 폼 하나다
종전에는 상세 모달이 `점검을 저장했습니다 [다음 품목]` 을 또 띄워 같은 저장이 두 번 통지됐다(§27.2).
지금은 `CheckForm` 이 세 갈래 모두 `재고 점검 저장됨 [적용취소]` 하나만 낸다(같은 날 중복 앵커는
detail 부연). **허브 부족을 거쳐 마감한 갈래만 `HubShortDialog` 가 제 토스트를 낸다** — 그쪽은
'옮기고 채움' 이라는 다른 사건이고 이미 §16 적용취소를 달고 있다. 여기서 또 띄우면 이중 통지다.
`다음 품목` 은 토스트 액션이 아니라 **보기 화면 맨 위의 영속 한 줄**이다(`다음 품목: {이름} ›`,
13px `--tc-text`, 히트 44px). §15 액션은 6초면 사라지는데 연속 점검은 그보다 오래 걸린다.

### 상세 모달 골격
이 모달은 풀블리드(`bodyClassName=''`)라 하위 폼마다 제 여백을 세우는데, 골격만 맨몸
`SkeletonRows rows={5}` 였다. 첫 페인트가 모달 벽에 붙어 뜨고 로디드 순간 좌우 20/24px·상하 16px 이

space-y-3 delayed-fallback` 을 직접 낸다.
