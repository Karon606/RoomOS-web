# 도메인: 재고 관리

핵심 파일: `app/(app)/inventory/{overview.ts(잔량 계산), actions.ts, InventoryClient.tsx}`.

## 품목 식별 = (propertyId, category, label) 유니크
`TrackedItem`은 `@@unique([propertyId, category, label])`. **qtyUnit 은 식별자가 아니다**(표시용 메타데이터, null 가능). 구매(Expense)의 품목 귀속은 (category, itemLabel)로 판단.
- 잔량/소모/입수/단가 계산의 구매 매칭은 **느슨 매칭**(`qtyUnit이 null이거나 같으면 일치`)으로 통일됨. 엄격(완전일치)이면 단위 미입력 구매가 누락됨(과거 라면·물티슈 버그).

## 수령확정 = 반드시 위치에 배치
`confirmReceipt`는 위치 미지정으로 받아도 **품목 허브(hubLocationId → 영업장 기본 창고 → 첫 위치)에 자동 배치**하고 자동 점검(`sourceExpenseId`)을 생성한다. 안 그러면 위치별 점검이 미배치 입고분을 못 세어 잔량에서 증발(과거 라면 120개 버그).
- 인라인 일괄수령은 **순차** 처리(동시 호출 시 자동점검 경합).
- **멱등**(2026-07-10, 쌀 신고): receivedAt이 이미 있으면 재호출은 그대로 성공 반환 — 응답 유실 후 재클릭이 자동 점검을 또 만들어 입고량이 이중 가산되는 것 방지. receivedAt 갱신 + 자동 점검 생성은 한 트랜잭션(중간 실패 시 '수령됐는데 잔량 미반영' 장부 과소 방지).

## 허브 차감 클램프는 조용히 삼킨다 (2026-07-10 쌀 사건)
위치별 점검의 보충이 허브 장부 잔량보다 크면 `Math.max(0, 허브 − 보충)`으로 0 클램프되고 **부족분은 어디에도 기록되지 않는다**. 장부 허브가 실물보다 적으면(실측이 오래됨) 보충 한 번에 총량이 급락해 소진임박 오탐 — 쌀: 창고 장부 20에서 5층 보충 +20 → 창고 0, 총량 28.5(실물 ~68). 허브(창고)도 주기적으로 실측해야 하는 이유.

## 위치별 점검 더블클릭 방지
저장 중복 제출 차단: 클라 동기 가드(`savingRef`/`submittingRef`) + 서버 멱등(같은 patch면 재적용 안 함). `locationPatch`는 상대 차감(허브 −보충)이라 재적용 시 허브 2배 차감되던 버그.

## 잔량 계산 모델 (overview.ts)
`currentStock = 마지막 점검 remainingQty + (점검 이후 수령 구매·무상입수)`. 같은 날 중복 점검은 최신만 채택(dedupSameDay). 입고 귀속은 `receivedAt`(수령일) 기준.

## 평균 소모율 = 최근 30일 '합산' (2026-07-17, eaa6726)
`avgDaily = 최근 30일 구간 consumed 합 / 그 구간들의 days 합`. `daysUntilEmpty = floor(currentStock / avgDaily)`이고 이게 알림(`dashboard/alerts.ts` lowstock)의 유일한 입력.
- **단일 구간 추정은 폐기됐다**(종전: 마지막 두 점검 차이). 점검 간격이 1~3일이라 표본이 1개뿐 → 그 구간이 크면 과대(라면 8/일, 실제 4.1 → 임박 오탐), 작으면 과소(쌀 0.5/일, 실제 3.45 → 소진 175일로 표시), **0이면 추정이 사라져 무알림**(김치·수세미·물티슈·핸드워시). 자주 점검할수록 알림이 나빠지는 구조였다.
- **합산이어야 하는 이유 = telescoping.** 구간별 값을 개별 표본으로 다루면(중앙값·EWMA) 입고 타이밍 오차(한 구간 +X, 다음 구간 −X)가 상쇄되지 않고 표본에 영구히 남는다. 월별 사용량 산식이 쓰던 원리와 동일하며 **구간 시리즈를 공유한다**(신규 쿼리 0).
- **분모는 달력 span 이 아니라 '포함된 구간 일수의 합'.** 보정(isReconcile) 구간을 소모에서 빼면 그 일수도 함께 빠져야 한다. 안 그러면 소모율이 과소평가되어 알림이 사라진다. consumed 와 항상 같은 구간 집합 위에서 계산할 것.
- **창 컷오프는 KST 달력일 기준**(`StockCheck.date`가 `@db.Date`=그 날 UTC 자정이라 표현을 맞춤). 서버 로컬 `new Date()`로 잡으면 배포 TZ(Vercel=UTC)에서 창이 하루 흔들린다.
- **avgDaily 의 3-상태**: 양수=추정 성립, **0=관측했으나 안 씀**, **null=추정 불가**(관측 7일 미만 / 창 총합 음수=장부 모순). 0과 null 을 뭉개지 말 것 — 그게 원래 버그의 근원이었다. 창 총합이 음수여도 0으로 클램프하지 않는다(허브 클램프 사건처럼 장부 모순은 상시 조건이라, 0으로 누르면 '안 씀'으로 위장되어 영구 무알림).
- 창 경계를 걸친 구간은 통째로 포함(소모를 일별로 쪼개면 없는 정보를 지어내는 것) → 실제 관측일수가 30을 넘을 수 있어 `avgDailyBasisDays`로 노출하고 화면에 "최근 N일 기준"으로 부기한다. 카드 아래 "최근 N일 동안 X 소모"는 **마지막 점검 구간**이라 범위가 다르다(둘은 서로 다른 값이 정상).
- 최소 관측 7일 — 구매 직후 점검 1회로 D-3 오탐 나던 리클린 사례 방어. 점검 1회뿐이라 구간이 없는 품목만 최초구매 기준 폴백을 탄다. 점검 2회 이상이나 전부 7개월 이전이면 avgDaily 소실(의도 — 낡은 데이터로 알림 금지).
- **보류된 제안**: "재고 0 + 소모율 미상이면 재고 없음 알림". 그 술어가 `InventoryClient.tsx` suggestHide(단종 후보 → '숨기기' 버튼)와 동일해, 아카이브 안 한 방치 품목 전량이 영구 알림이 된다. 채택하려면 '조회 구간 내 소모 이력 있음' 같은 추가 게이트 필요.

## 월별 사용량은 '데이터 없음'도 0으로 그린다 (표시 주의)
추적 시작 전 달과 진행 중인 달이 실제 사용량 0과 같은 0 막대로 보여 편차가 커 보인다(2026-07-17 운영자 의문). **산식 자체는 정확**하다 — 일당 환산하면 쌀 2.5/3.6/2.8, 라면 3.8/6.5/4.4로 안정적. 미개선(별건).

## 비품·자재 배정 차감 = 선입선출 (2026-07-09 운영자 확인)
집계 카드(여러 구매분 합)에서 배정/이동 시 `buildSplitOps`가 **구매일 오래된 행부터** 차감한다(같은 날짜는 큰 행부터, 분할 최소화). 이전의 '수량 큰 행부터'는 어느 구매분에서 빠질지 예측 불가 + 단가가 섞여 방별 비용 왜곡("랜덤으로 빠진다" 신고). 옮기기 모달에서 특정 구매분만 지정해 차감할 수도 있다(구매 2건 이상일 때 select).
- 배정 이력 되돌리기 = 라벨로 위치 복원해 **역이동 + 그 이력 행 삭제, 새 이력 없음**(revertAssignmentLog). 수량이 이미 다른 곳으로 가면 에러로 안내하고 이력 삭제만 가능.
- 분할 생성 행은 specText 를 반드시 복사(2026-07-08 유실 버그 — 카드가 둘로 갈라져 보임).
