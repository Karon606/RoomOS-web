**보증금은 세 경로가 같은 자리로 모인다.** 그건 정상이다.

**문제는 이용료 환불이다.** 셋 중 한 곳에만 있다. 홈이나 프리즘에서 퇴실 처리하면 보증금만
정산되고 일할·단기 요금 환불은 확정되지 않는다. 422호처럼 퇴실 정산에서 단기 요금 294,000원을
적용해 둔 계약도, 홈 알림에서 퇴실 처리를 누르면 이용료 환불 126,000원이 안 잡힌다.

**해소됐다(2026-08-31).** 어느 경로로 나가도 결과가 같다. 아래는 그때의 기록이다.

## 이미 맞춘 것 (2026-08-30, 커밋 4798a7b3)

어휘와 사유 축은 셋을 맞췄다. 보증금은 '반환', 사유 라벨은 '반환하지 않는 사유', 청소비 몫까지는
사유를 안 묻는다(화면 조건과 저장 게이트 둘 다). **어휘는 표면이었고 이용료 환불 누락이 실질이다.**

## 착수 절차

1. **패널을 먼저 소집한다.** 퇴실은 돈이 움직이는 축이라 loop.md §4 대상이고, 오류신고 5단계
   문법(분류 → 전문가 섭외 → 계획 보고 → 승인 → 시공)을 따른다. 이 단계에서 코드를 고치지 마라.
2. **세 경로가 각자 무엇을 하는지 전수로 밝힌다.** 위 표는 저장 액션만 본 것이다. 청소 예정
   생성·상태 이력·거주 구간(RoomStay)·현금영수증·회계 귀속월까지 갈리는지 확인해야 한다.
3. **한 자리로 모으는 설계를 낸다.** 세 화면이 같은 컴포넌트를 쓰게 할지, 서버 액션 하나로
   모을지, 아니면 빠진 경로에 이용료 환불만 이어 붙일지. 각각의 접점과 회귀 위험을 대라.
4. **감지망을 세운다.** 퇴실 경로가 넷째로 늘거나 한 경로만 무엇을 빠뜨리는 것을 잡는다.
   결함을 일부러 심어 실제로 잡는지 확인한다.

## 설계 패널 보고 (2026-08-30)

### 패널 구성

UX/UI 전문가, 웹디자이너(가이드 검토), 도메인 전문가, 회계 전문가, 회귀 위험 분석가 5명을 소집했다.

### 추가 확인한 사실

기존 표의 이용료 환불 외에 **청소 예정 생성도 갈린다.**

| 축 | 홈 알림 | 프리즘 위젯 | 입주자 수정 |
|---|---|---|---|
| 보증금 반환 | `recordDepositReturn` | `recordDepositReturn` | `recordDepositReturn` |
| 이용료 환불 | 없음 | 없음 | `finalizeRentRefund` |
| 청소 예정 | `ensureCheckoutCleaning` | `ensureCheckoutCleaning` | **없음** |
| 예약 선납 재앵커 | 있음 | 있음 | **없음** |

즉 **어느 경로도 완전하지 않다.** 입주자 수정은 이용료 환불은 하지만 청소 예정을 안 만들고, 홈/프리즘은 청소 예정은 만들지만 이용료 환불을 못 한다.

### 기존 audit에서 이미 P0으로 식별됨

`docs/audit-2026-08/B-findings.md:92-98`에서 같은 문제가 이미 보고되어 있다. 실측 미환불 잔액: 504호 이예준 50,667원, 409호 변세진 13,000원(둘 다 CHECKED_OUT이라 미납 집계에서 빠져 영구 방치). 설계 방향도 `docs/audit-2026-08/checkout-settlement-design.md:69`에 제시되어 있다: "퇴실 미니폼과 편집폼 환불 모달을 같은 컴포넌트로 통일해야 한다."

### 통합 방안 비교

| 방안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 컴포넌트 공유 | 세 화면이 같은 퇴실 미니폼 컴포넌트 사용 | UI 일관성 | 화면 맥락이 달라 어색할 수 있음 |
| B. 서버 액션 통합 | 퇴실 처리를 단일 서버 액션으로 | 결과 일관성 확보, UI 변경 없음 | 기존 3개 액션 호출부 수정 필요 |
| C. 누락분만 추가 | 각 경로에 빠진 것만 추가 | 변경 범위 작음 | 중복 코드, 동기화 부담, 또 갈릴 위험 |

**UX 전문가 권장: B(서버 액션 통합).** 세 화면이 같은 액션을 호출하면 결과가 동일해지고, UI 변경 없이 기능 일관성을 확보한다. 경고 메시지(현재 프리즘 방식)는 보조 수단이지 대체 수단이 아니다.

### 회계 관점

- `finalizeRentRefund`는 원 record를 소프트삭제하고 회사 귀속액을 재기록한다.
- 두 경로에서 빠지면 record 이중 계상 또는 매출 증발이 발생한다.
- 이용료 환불은 퇴실과 분리해서 나중에 처리 가능하지만, 일할 정산(`checkoutProratedAmount`)이 먼저 적용되어야 올바른 환불액이 나온다.

### 회귀 위험

- **관련 감지망**: `test-settlement-period`(57축), `verify-money-consistency`의 roomStillOccupied/청소비 분류 규칙.
- **주의**: `check-deposit-settlement`(퇴실 보증금 정산 누락 감지)는 현재 안 돌고 있다.
- **통합 시 깨질 수 있는 것**: 예약 선납 재앵커가 입주자 수정 경로에 없어, 그 경로로 RESERVED를 ACTIVE로 바꾸면 선납이 옛 달에 남아 입주월이 미납으로 뜬다(B-findings.md:21-24).

### 디자인 가이드 위반 (웹디자이너 점검)

1. `CheckoutRefundModal` (DashboardClient.tsx:308-327): raw `<button>` 사용. Btn 컴포넌트로 교체 필요.
2. `TenantStatusTransitions.tsx:502`: 확인 버튼 라벨이 "확인". brand-guide-v2.0 §10 위반. 동사("퇴실 처리" 등)로 변경 필요.
3. `CheckoutRefundModal:325`: 확인 버튼 배경이 `--viz-4`. §10 primary는 --tc 계열이어야 함.

### 계획안

1. **단일 서버 액션 신설**: `processCheckout(leaseTermId, tenantId, moveOutDate, options)` 형태로, 보증금 반환 + 이용료 환불 + 청소 예정 + 상태 전이를 한 트랜잭션에서 처리.
2. **세 화면의 퇴실 처리 호출부를 새 액션으로 교체**: 기존 `checkoutTenant`, `applyStatusTransition`의 퇴실 분기, `updateTenant`의 퇴실 분기를 모두 새 액션으로 라우팅.
3. **감지망 추가**: 퇴실 경로가 새로 생기거나 한 경로만 처리가 빠지는 것을 잡는 소스 정적 분석 규칙.
4. **디자인 가이드 정비**: 위 3건 수정.

### 운영자가 확인해야 할 것

1. **통합 방안 선택**: B(서버 액션 통합)를 권장하지만, 변경 범위가 크다. C(누락분만 추가)로 먼저 급한 불을 끄고 나중에 B로 갈 수도 있다.
2. **기존 퇴실자 미정산 처리**: 이예준 50,667원, 변세진 13,000원. 소급 정산할 것인가, 대손 처리할 것인가.
3. **청소 예정 누락 건**: 입주자 수정으로 퇴실 처리한 건 중 청소 예정이 빠진 것이 있는지 확인 필요(실기 확인 대상).
4. **예약 선납 재앵커 누락**: 입주자 수정으로 RESERVED를 ACTIVE로 바꾼 건이 있으면 그 달 청구가 어긋났을 수 있다(DB 조회 필요).

### 이 환경의 한계

- DB에 접근할 수 없어 기존 퇴실 건의 청소 예정/선납 재앵커 누락 여부를 실측하지 못했다.
- 실기 확인을 못 해 UI 변경 후 모바일 동작을 검증하지 못한다.

## 해소 (2026-08-31)

세 번에 걸쳐 닫았다.

1. **부수 처리 정본화** (161001a2) — 공실·예약가·청소 예정·거주 구간 마감을
   `applyCheckoutSideEffects` 한 자리로 모았다. 상태를 쓰는 세 서버 문이 전부 그것을 부른다.
2. **이용료 환불 배선** (b51b193b) — 세 경로가 `finalizeRentRefund` 를 확정한다.
3. **정산 물음과 안내 통일** (e7d48411 · 189dcb9a) — 배선만으로는 부족했다. 홈과 프리즘은
   *미리 확정해 둔 값이 있을 때만* 환불했고, 정산을 안 해 둔 중도퇴실은 아무것도 안 묻고
   만월 청구를 그대로 두었다. 계산·표시·확정 문법을 `components/checkout/RentSettlementSection`
   한 벌로 뽑아 세 화면이 쓴다. 홈택스 조치 안내도 `lib/refundTaxNotice` 한 벌로 모았다 —
   종전에는 수정 폼만 말해서, 현금영수증을 발행한 계약을 홈에서 퇴실 처리하면 앱 매출만
   조용히 줄고 취소하라는 말을 아무도 못 들었다.

**감지망.** `scripts/check-checkout-side-effects.mjs` 가 여섯 축으로 지킨다 — 정본 4축,
경로가 정본 호출, 정본 밖 직접 생성 금지, 세 경로 이용료 환불, 정산 정본 공유(계산 직접 호출
금지 포함), 홈택스 안내. 넷째 경로가 생기거나 한 화면만 무엇을 빠뜨리면 여기서 걸린다.

**남긴 것.** 환불 지급 수단·지급일 기록은 운영자 결정으로 CODEF 계좌연동(Phase 2) 때 함께
설계한다. 단기 계약 조기 퇴실 환불은 지금처럼 정책 밖이다(수납 기록에서 직접 조정).
