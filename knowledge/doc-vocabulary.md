# 서류 용어·액션 정본 (2026-08-01 확정)

발단은 운영자 지적이다. "비슷한 기능과 용어가 여러 군데 있어서 나도 헷갈려."
**매일 쓰는 사람이 못 외우는 화면은 그 자체로 결함이다.** 이 노트가 서류 도메인 어휘의 정본이다.

## 동사 5개

| 동사 | 정의 | 사용자가 겪는 결과 |
|---|---|---|
| **발급** | 공식본 PDF 를 만들어 보관하고 이력에 남긴다 | 발급 이력이 늘어난다 |
| **보내기** | 만들어진 서류를 **입주자에게** 전달한다 | 상대에게 간다 |
| **저장** | **내 기기**에 파일로 남긴다(사진첩·다운로드) | 내 손에 파일이 생긴다 |
| **보기** | 열어서 확인한다. 아무것도 만들지 않는다 | 아무 흔적이 없다 |
| **작성** | 내용을 채우는 화면으로 들어간다 | 화면이 바뀐다 |

선정 기준은 하나다. **처음 보고도 결과를 예측할 수 있는가.** 다섯 결과가 서로 겹치지 않는다.

예외 1건. 스캔본 업로드는 앱 **안으로** 들어오는 유일한 방향이라 다섯으로 안 덮인다.
'스캔본 올리기' 한 라벨로 고정하고 사전 밖 예외로 둔다.

개발·외부 서비스 용어(공유, 시트, 세션, Drive, 링크)는 라벨에 쓰지 않는다(가이드 §29).

## 쓰면 안 되는 표현

| 금지 | 이유 | 대신 |
|---|---|---|
| 공유 | '보내기'와 같은 동작인데 이름만 달랐다. 이 사고가 이번 정리의 발단 | 보내기 |
| 계약서 저장 (Drive 보관) | 확인서·영수증의 '발급'과 같은 동작인데 서류마다 말이 달랐다 | 계약서 발급 |
| 재발급 | 아무것도 발급하지 않고 작성 화면만 연다 | 다시 작성 |
| 출력 | 어느 쪽도 인쇄가 아니었다(작성 화면 열기 / 원본 열기) | 작성·서명, 보기 |
| Drive 보기 | 외부 서비스명 노출 + 실제로 앱을 벗어났다 | 보기 |
| 인쇄 | 6번째 동사를 만들면 "보내기와 뭐가 다른가"가 다시 생긴다 | 보기(뷰어 안에서 인쇄) |

## 라벨은 컴포넌트에서만 정한다

`ShareDocButton`·`SendDocButton`·`SaveDocImageButton`·`ViewDocButton` 은 기본 라벨을 갖고,
**호출부는 `label` prop 을 넘기지 않는다.** 이름 정의처가 둘이면 반드시 갈린다 — 실제로 같은
`ShareDocButton` 이 모달에서는 '공유', 계약서 목록에서는 '보내기' 로 불렸다.
`ViewDocButton` 은 아예 `label` prop 을 두지 않았다.

## 보내기 vs 사진 저장 — 합치지 말 것

디자이너가 "형식이 겹치니 사진 저장을 보내기에 접자"고 제안했으나 **운영자가 기각했다**(2026-08-01).
> "보내기는 말그대로 전송의 역할인데 사진으로 할지 pdf로 할지이고 사진 저장은 저장해서 바로
> 사진함에 넣는거니까 목적이 달라. 5개 버튼이라도 괜찮은 것 같아"

**보내기는 목적지가 상대방, 사진 저장은 목적지가 내 사진함.** 형식(사진/PDF)이 겹칠 뿐 목적어가 다르다.
버튼 수를 줄이려고 합치면 사진함에 넣는 경로가 공유 시트 뒤로 숨는다. 영수증·확인서 행이 5개인 것은
붐비는 게 아니라 목적이 5개인 것이다.

## 행 액션 구성 (서류 목록 4화면 공통)

```
보기(primary solid) · 보내기 · [사진 저장] · [다시 작성] · 삭제(ghost danger)
```

- §22 "액션 행에 solid 는 하나". solid 는 **보기** — 가장 잦은 동작이자 인쇄·저장·확대의 관문이다.
- 삭제는 항상 마지막.
- 계약서 행은 사진 저장·다시 작성이 없어 3개.
- `Btn size="sm"`(44px 터치 타겟). `Btn` 을 못 쓰는 자리(className 만 받는 컴포넌트, 파일 input 을
  감싸는 `<label>`)는 `btnClass()` 로 토큰을 공유한다 — 손복사하면 그 자리만 뒤처진다.
- **기기별로 버튼을 감추지 않는다.** 계약서 목록만 `canShare` 로 보내기를 숨겨 같은 서류 행이
  맥과 폰에서 다르게 생겼다. 데스크톱도 다운로드 폴백과 안내 토스트가 있어 실패하지 않는다.
  (다중 선택 바의 `canShare` 게이트는 별개 문제라 그대로 둔다.)

## 인쇄 경로

- **모바일**: '보내기'의 시스템 공유 시트 안에 프린트가 들어 있다. 별도 버튼이 없는 게 정상이다.
- **데스크톱**: '보기'로 앱 안 PDF 뷰어를 열고 거기서 인쇄한다.

이 기기별 분기는 `app/contract/[tenantId]/ContractView.tsx` 가 먼저 확립한 정본 결정이다.
운영자가 "여기서 인쇄가 안 된다"고 한 것은 **데스크톱에 문서를 여는 컨트롤이 없었기** 때문이지
인쇄 버튼이 없어서가 아니었다. 원인을 라벨 부재로 오독하면 6번째 동사를 만들게 된다.

`/api/doc-file` 은 `Content-Disposition` 을 붙이지 않아 브라우저가 인라인으로 렌더한다.
**`attachment` 를 추가하지 말 것** — '보기'가 조용히 '저장'이 되어 같은 불만이 재발한다.
권한은 이 라우트가 영업장 소유를 검증하며 역할을 가리지 않는다('보내기'와 같은 통로).

## 인쇄 경로의 전제가 홈화면 앱에서 깨진다 (신고 f12c265b·083239c3, 2026-08-04)

위 '인쇄 경로' 절은 "데스크톱은 '보기'로 앱 안 PDF 뷰어를 열고 거기서 인쇄한다"를 전제했다. 그 전제가 **홈화면 앱(manifest display: standalone)에서는 거짓**이다. 주소창도 뒤로가기도 없어서, `target="_blank"` 로 연 PDF 는 인쇄 UI 도 없고 돌아올 길도 없다. 운영자가 "껐다 켜야 됨"이라 신고했다.

그래서 '보기'의 목적지를 앱 안 뷰어 라우트(`/doc/[fileId]`)로 되돌렸다. 동사 5개는 그대로다 — **'인쇄'는 여전히 6번째 동사가 아니다.** 다만 그 정상 상태를 사용자에게 말해 주는 자리를 만들지 않은 것이 결함이었으므로, 뷰어에 안내 한 줄을 둔다.

모바일 '보내기'가 공유 시트 안에 프린트를 담는다는 것도 UI 어디에도 안 적혀 있었다. 라벨이 '보내기'라 프린터를 찾는 눈에 안 걸린다. 납부확인서·실거주확인서의 미리보기도 터치 기기에서는 새 탭이 아니라 공유 시트로 가도록 계약서 분기를 이식했다(`lib/docPreview.ts`).

**아직 수렴하지 않은 것** — `ContractView` 가 터치 판정·공유·파일명 안전화를 자체 구현으로 들고 있다. `lib/docPreview` 를 만들면서 원본을 걷지 않았다.
