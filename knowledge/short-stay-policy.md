# 단기 입실 정책 (2026-07-06, 운영자 기준 §4)

## 규칙 (더스테이원룸텔 제기역점 기준 — 시드 저장됨)
1. 최소 거주 1주.
2. 계약은 주 단위 — 단기 구간에서는 일할 아님(거주일을 주 단위로 올림).
3. 1달 이내 거주 = 계약일수 × 1.5 를 청구 일수로(소수 그대로, **버림 안 함** — 2026-07-26 변경), 1개월(30일) 요금 상한 + 청소비 2만원.
   기본요금은 **1,000원 단위 반올림**(roundTo, 영업장별 절삭 단위 — 운영자 추가 지시 2026-07-06).
   - 1주 → 10.5일치 + 2만 · 2주 → 21일치 + 2만 · 3주 → 31.5일이라 1개월 상한(사실상 월 계약과 동일).
   - **버림 제거 이유(2026-07-26):** 계약일수에 floor 를 한 번만 적용하면 1주(10.5→10)만 깎여 둘째 주 추가금이 첫 주보다 비싸지는 역전이 생겼다(157k → +172k). 소수 청구일을 그대로 두면 주당 균등(10.5·21·31.5)해 역전이 사라진다. 배율 1.5(단기 할증)는 유지. 470k 방: 1주 165,000 · 2주 329,000 · 3주 470,000(상한).
4. 이 수치는 제기역점 전용 — 다른 영업장은 설정 > 단기 입실 정책(오너 전용)에서 수치만 바꾸면 됨.

## 구현
- Property.shortStayPolicy Json?(migrate_short_stay_policy.sql 적용) — null = 미사용. 파싱은 parseShortStayPolicy 방어(범위 밖 → 기본값).
- lib/shortStay.ts: calcShortStay(policy, 월세, 거주일수) 순수함수 — scripts/test-money.ts 고정(1주=10.5일, 2주=21일, 3주=상한, 10일→2주 올림, 최소 1주, 31일=정책 밖 null).
- 시뮬: 고객 관리 > 요금 계산 — 적용 범위 안이면 정책 카드(계약 N주·기본요금·청소비·총액·올림/상한 안내), 밖이면 기존 월+일할 견적.
- 설정: SettingsForm ShortStayPolicyCard(오너 전용) — 사용 토글 + 단위일/최소단위/상한일/배율/청소비 + 월세 60만 예시 미리보기. 저장은 requireOwner.

## 연장 규칙 (2026-07-20 운영자 승인 — 패널 7인 논의)
1. 연장 = 퇴실일 변경. 요금은 항상 "최초 입주일 ~ 새 퇴실일" 전체 기간을 calcShortStay로 **누적 재계산**한다. 연장 구간을 따로 계산하지 않는다(증분 금지 — 경로 의존이라 총액이 어긋남).
2. 추가 납부액 = 새 총 사용료(baseAmount) − 기존 rentAmount. 청소비·보증금은 차액 계산에서 제외.
3. 청소비는 입실 에피소드당 1회. 연장 시 재청구하지 않는다. 퇴실 후 재입실은 새 에피소드.
4. 재계산 기산일은 항상 최초 입주일. 누적 방식은 텔레스코핑이라 **경로 독립** — 1주씩 여러 번이든 한 번에든 같은 퇴실일이면 총액 동일(test-money 고정).
   - **I8' (회계 확정 2026-07-26, 종전 I8 대체):** 경로 독립은 **정책가 경로**에서만 성립한다. 마지막 저장이 manual(운영자 협의가)이면 그 금액이 새 기준선이 되고, 이후 원인 사실이 바뀔 때까지 재계산하지 않는다. 원인 사실 = 퇴실일·이용료·호실·입주일 넷(`shortStayBasisChanged`).
5. 새 총 거주일수가 thresholdDays(기본 30일)를 넘으면 단기 정책 밖 → 월 계약 전환 안내(연장 확정 차단). 전환 자동화·정산은 후속 결정.
6. 단축(조기 퇴실) 환불은 범위 밖 — 주 단위 계약이라 일할 환불 자동 적용 불가, 별도 정책 필요.
7. 라벨 정본: 단기 rentAmount 라벨은 '이용료'(2026-07-20 운영자 결정, 장기는 '월이용료'/'월 이용료' 유지).

## 단기 보증금 (운영자 확정 2026-08-02)

**경우에 따라 받는다.** "안 받는다"가 아니다. 실측으로도 단기 9건 중 4건에 5만원이 들어 있었다.

따라서 계약마다 수기 입력이 정본이고, 자동 기본값을 채우지 않는다(운영자 지시 "계약마다 직접하는걸로", 2026-08-02).
`TenantClient` 의 프리필 제외(`isNoAutoFill` 에 shortTerm 포함)는 **정상 동작이다.** 자동으로 5만원을 넣으면
안 받기로 한 계약에 값이 생긴다.

다만 빈칸으로 저장하면 `LeaseTerm.depositAmount` 가 `Int @default(0)` non-null 이라 0 으로 굳고,
'미입력'과 '무보증 0원'을 저장 계층이 구분하지 못한다. 그래서 **계약 보증금이 0인 상태에서는 보증금 수납을 막는다**
(`rooms/actions.ts` `saveDepositPayment`). 막지 않으면 받은 돈이 이용료로 넘어가 예수금이 매출로 인식된다.

관련 — [[money-display-feedback]] 의 보증금 계약 단위 표시, [[cash-receipt-refund]] 의 "보증금은 애초에 매출이 아니다".
- 예약 선납(prepaid)의 청소비 분리 수납 — 현행 FIFO가 청소비를 다음달 이용료 record로 밀어냄(파트쿨리나 실증).
- 미납 문구: 단기 dueDay null이라 경과일 오탐 — 연장 차액의 기일 표기 별도 검토.

## 단기 예약금 처리 (운영자 확정 2026-08-19 — 신고 8c0f9688, 2·3단계)

**설정 축.** `shortStayPolicy.reservationMode` — `refundableDeposit`(퇴실 시 환불 보증금, 종전)
| `applyToRent`(청소비 차감 후 이용료 충당). null = 미설정이면 영업장 공통 기본값
(`Property.reservationDepositMode`)을 그대로 따라 해석이 종전과 문자 그대로 같다.
해석 우선순위는 **계약 개별 선택 > 단기 정책 > 영업장 기본 > 단기/장기 폴백**(`resolveReservationDepositMode`).

**확정 산식 5건.**
1. 입실 전 취소는 청소 용역 전이라 **청소비 몫도 반환·몰취 기준에 포함**한다.
   취소 기준액 = 선납 record 합 + 예약 청소비 부가수익 합.
2. 청소비 수익 인식일은 **받은 날**이다(기존 '받은 달 수익' 정본과 같은 축). 입주월 재앵커가
   선납 record 만 옮기고 청소비 부가수익을 건드리지 않는 이유가 이것이다.
3. 402호 황인정 정정은 이미 처리됐다 — 백필 대상 없음.
4. 진행 중 단기 2건(503 송호준·404 조성훈, 보증금 5만)은 **소급하지 않는다.** 퇴실 때 반환 3만을
   입력하면 기존 `splitWithheldDeposit` 정본이 청소비 2만·몰취 0 으로 같은 결과를 낸다.
5. 잔여 몫이 그 달 이용료를 넘으면 초과분은 선납으로 남고 퇴실 정산의 **기존 완납 초과 환불 흐름**이
   처리한다. 새 산식을 만들지 않는다.
6. 수납 폼 예약금 기본값은 `shortStayPolicy.deposit` 시드(제기역점 50,000). 수기 변경 가능.

**발동 조건(삼중 가드, `reservationFeeSplitApplies` 정본).** 해석 모드가 `prepaid` + 단기 계약 +
정책이 `applyToRent` + 계약 청소비 > 0. 하나라도 어긋나면 종전 선납 경로가 그대로 돈다.
서버(저장)와 화면(미리보기)이 **같은 함수**를 쓴다.

**저장 모양.** 청소비 몫 = `ExtraIncome '청소비'`(받은 날 귀속, 실결제수단, detail 은 `… 예약 · 청소비`),
잔여 몫 = `savePayment` 입주월 이용료 선납. **보증금 record 는 만들지 않는다.**
이 부가수익이 서면 `cleaningFeeDeductible` 이 퇴실 공제를 자동으로 0 으로 판정한다(계약서 §2-4 either/or).
청소비 생성부는 입실 별도 수령과 공용(`createCleaningFeeIncome`).

**정책값의 뜻이 모드에 따라 다르다.** `shortStayPolicy.deposit` 는 `refundableDeposit` 에서는
퇴실 시 환불하는 예치금이고, `applyToRent` 에서는 **예약금 시드**다. 그래서 단기 요금 카드의
[이 금액 채우기]는 applyToRent 일 때 계약 보증금 칸을 채우지 않는다 — 채우면 받지도 않은 예치금
책임이 계약에 박히고 퇴실 정산이 그걸 환불하려 든다.

**감지망.** `scripts/check-short-stay-reservation.mjs`(verify:db) — 축A 단기 퇴실의 '보증금 몰취'(기준선 0),
축B 분해 규칙 영업장의 단기 계약에 보증금 수납 신규 생성(발효일 컷오프), 축C 분해 정합(청소비 행 중복·
계약 청소비 상한 이탈·보증금 공존). 소스 가드 5종 + 자가 역주입 5 + 오탐 8.
