잔여 소지품 임의처분 동의서 하단 "○○ 대표 귀하"(contractPrintHtml:153·ContractView:724)는 **의도된 표준 서식**. 이 동의서는 입주자가 작성·서명해 대표(운영자)에게 제출하는 서류라, '귀하'는 시스템이 운영자를 높이는 게 아니라 제출자(입주자)가 수신인을 높이는 것 — 유지 결정(오류신고 88c2f268). 존칭 규칙: 개인=귀하, 기관=귀중.

## 인쇄 = 한 장 맞춤 (2026-06-29 해결)
화면 미리보기(ContractView)는 `transform: scale()` + `min-height:297mm`로 한 장처럼 보이지만,
PDF(`lib/contractPrintHtml.ts`)는 별도 CSS·원본 크기라 가용높이 초과 시 다음 장으로 넘쳤음.
**해결: `app/api/contract/generate/route.ts` 에서 shrink-to-fit** — 의도 페이지 수(html의 `.paper` 개수:
계약서 1 + 동의서 옵션 1)보다 많으면 한 장에 맞을 때까지 `page.pdf({ scale })` 단계적 축소(**하한 0.88 = 가독성 바닥**, 최대 12% 축소).
**축소(≥88%)로도 못 맞추면 = 내용이 매우 많음 → 원본(100%)으로 되돌려 '읽기 좋은 크기 + 다중 페이지'로 출력**(미세글자화 방지, 2026-06-29). 즉 글씨는 절대 88% 미만으로 작아지지 않음.
동의서는 `page-break-before` 로 항상 별도 장이라 '서류별 한 장'이 목표(전체 1장 강제 아님).
**여백 상하좌우 14mm 대칭**(헤더/푸터 간격·좌우 동일). 좌우 14mm 는 표 우측 테두리 잘림 방지.
주의: 화면(ContractView)·브라우저인쇄(@media print)·PDF(contractPrintHtml) 가 **CSS 3벌**이라 픽셀 동일은 아님 — 출력 기준은 PDF(발급).

### 조항 2단 = 화면=PDF 동일 (2026-08-26 개정 — 아래 옛 사실 폐기)
**화면·PDF 둘 다 선형 DOM + `column-count: 2`**. 절을 문서 순서 그대로 한 흐름으로 뱉고 브라우저가 나눈다.
- ⚠️ **조항 순서 절대 불변**은 그대로 살아 있다. 다만 이제 **DOM 이 선형이라 구조적으로 자동 충족된다** — 분배 함수가 없으므로 순서를 뒤섞을 자리 자체가 없다.
- `column-fill` 은 **기본값 balance 를 쓴다. auto 금지** — 마지막이 아닌 프래그먼트에서 단을 페이지 바닥까지 채워, 한 장짜리 계약의 왼단만 바닥까지 차거나 서약·서명이 밀린다.
- `.clause-group` 에 `break-inside: avoid` 를 두면 안 된다 — 절이 단 경계에서 통째로 점프해 바닥 공백이 커진다. 절이 단을 넘어 이어지는 것이 옛 분배(title:null 이어짐)와 같은 규칙이다. `.clause-h` 의 `break-after: avoid`(고아 헤더 방지)와 `li` 의 `break-inside: avoid` 는 유지한다.
- **계약서 레이아웃 바꿀 때 두 파일(ContractView·contractPrintHtml) CSS·구조를 항상 같이 수정**(드리프트 주의).

#### 항목 번호는 자리에서 매긴다 (2026-08-27 운영자 확정)
`.clause-list { counter-reset: clause }` + `li::before { content: counter(clause) "." }`. **점(·)은 안 쓴다** —
번호가 곧 표시다. 본문 글자에 박힌 손 번호는 `lib/contract` 의 `stripClauseBullet` 이 걷는다.
- 왜. 손 번호는 **박아 넣은 항목에만** 있었다. 추가 호실 특약 8개 전부, '[청소비]', '[강제 퇴실 시 정산 규정]'
  이 번호가 없어 "몇 조 몇 항"으로 가리킬 수 없었다. 운영자가 템플릿에 항목을 끼워 넣을 때마다 뒤 번호를
  손으로 고쳐야 하는 문제도 함께 사라진다.
- **화면과 인쇄본이 `stripClauseBullet` 하나를 쓴다.** 종전에는 규칙이 두 벌이라 인쇄본만 번호를 벗겼고
  화면은 '· 1. 1인 1실을'로 이중 표기가 났다. 화면 쪽 주석에는 "동일 규칙"이라 적혀 있었지만 사실이
  아니었다 — 손사본은 언젠가 갈린다.
- 번호 자리 확보로 `li` 의 들여쓰기를 3mm 에서 **4.5mm** 로 넓혔다(padding-left·text-indent 짝).
- 감지망 `test-contract-clause-order` 가 점 복귀·본문 손 번호 잔존·counter 소실을 잡는다.

#### 왜 바꿨나 — 옛 사실이 더 이상 참이 아니다
2026-06-29 노트는 "**CSS 멀티컬럼은 Chrome 인쇄에서 1단으로 흐른다**"를 사실로 적고, 그 제약 때문에 명시적 2단(flex) + `splitClauseColumns`(글자 수로 높이를 추정해 좌우를 반반으로 가르는 함수)를 세웠다.

**2026-08-26 Chrome 151 재실측에서 그 1단 붕괴가 재현되지 않는다.** 현 세대 Chromium 은 multicol 을 페이지별로 왼쪽 채우고 오른쪽 채운 뒤 다음 장으로 넘긴다. 당시 붕괴는 그때의 Chromium 세대나 당시 `.paper` 가 flex 였던 구조의 문제였을 가능성이 크다.

그 사이 옛 구조가 결함을 냈다. flex 2단은 **페이지 경계에서 각 단이 독립적으로 이어 그려진다.** 조항이 한 장을 넘치면 이렇게 된다.
```
p1: 왼쪽 1조 2조 | 오른쪽 4조
p2: 왼쪽 3조     | 오른쪽 5조 6조
```
읽는 순서가 1, 2, **3(2페이지)**, **4(1페이지 복귀)** 가 된다. 김상혁 님 계약서에서 운영자가 발견했다(2026-08-26). 방아쇠는 `appendSubLeaseAddendum` 이 붙이는 추가 호실 특약(창고)·거주 호실 일정 절이다 — 절이 하나 늘어 축소맞춤 하한(88%)을 넘기면 다중 페이지 폴백에서 드러난다.

**곁들여 사라지는 것**: 옛 분배는 한 줄 28자 가정으로 높이를 **추정**했다. multicol 은 렌더러 자신의 실측으로 나누므로 추정이라는 층 자체가 없어진다.

**실측 근거**(2026-08-26, 로컬 Chrome 151, A4 여백 14mm, 실제 `buildContractPrintHtml` 출력).
- 과중 계약(기본 템플릿 + 창고 특약 + 호실 일정 절): flex 는 위 순서 파괴를 재현, multicol 은 `p1 왼 1·2·3 / 오른 4·5, p2 6` 으로 정상.
- 보통 계약(기본 템플릿만): 페이지 수도 단 나뉨 지점도 flex 와 **동일**. 즉 한 장짜리 계약의 인쇄 결과는 사실상 안 움직인다.

**미지수 하나**: 프로덕션은 `@sparticuz/chromium` 148 이고 위 실측은 로컬 151 이다. 프리뷰 배포에서 PDF 를 실제로 떠 확인한 뒤 본배포한다.

**본문 문자열은 한 글자도 안 바뀐다.** `contractPrintedFacts` 19축은 전부 데이터 축이라 드리프트 0건이고, `signedContractSnapshot` 격리는 본문을 지키는 장치지 레이아웃 장치가 아니다. 이미 발급된 PDF 는 Drive 에 바이트로 박제라 불변이다. 서명 계약을 **재발급**하면 본문은 격리본 그대로, 배치만 새 코드로 나온다(신원번호 동의문 추가와 같은 클래스의 전례).

### 인쇄/PDF 버튼 동작 (서버 PDF 단일 소스로 통일, 2026-06-29 최종)
**핵심: 인쇄·저장·발급 모두 같은 '서버 puppeteer PDF'(contractPrintHtml) 하나만 쓴다** → 결과물(레이아웃·페이지 수) 100% 동일.
- **window.print(화면 직접 인쇄)는 폐기**. 이유: 브라우저가 배율·페이지나눔을 제어해 서버 PDF 의 한장맞춤(shrink-to-fit)을 못 따라가 페이지 수·레이아웃이 달라짐(실제 비교 결과 계약서 1장 vs 2장, 비상연락망 칸·계약번호 유무 차이). CSS 2벌 드리프트의 근본 원인이라 화면인쇄 경로 자체를 제거.
- **전달 방식만 기기별 분기**(결과 PDF 는 동일):
  - **모바일(터치 기기)**: `navigator.share({files:[pdf]})` 네이티브 공유 시트 — 프린트·파일에 저장·메일이 한 곳에. 버튼 1개('인쇄 / PDF'). 감지: `maxTouchPoints>0 || /Android|iPhone|iPad|iPod/` && `navigator.canShare`.
  - **데스크톱**: 버튼 2개 — **인쇄**(서버 PDF 를 새 탭에 열어 Cmd+P) / **PDF 저장**(blob 다운로드).
- **계약서 저장(발급)** = 서버 PDF 를 Drive 저장 + ContractFile 기록(공식 보관). preview 모드(`body.preview`)는 Drive/DB·서명영구저장 미접촉.
- 서명 없이도 생성 허용(서명란 '(서명)' 자리표시). 빈 서명은 저장된 서명 안 지움.
- ⚠️ 이모지 금지(운영자 지시) — 버튼 라벨에 아이콘 문자 쓰지 말 것.
- ⚠️ 화면 미리보기(ContractView @media screen)와 출력(contractPrintHtml)은 여전히 CSS 2벌이지만, **출력은 항상 contractPrintHtml 단일**이라 인쇄=저장=발급이 같음(미리보기만 근사).

### 표시값 오버라이드 = 발급물 전용, 수납 무접점 (2026-08-05, 운영자 승인)
관 제출용처럼 **실계약과 표기가 다른 계약서**가 필요할 때(홍은주 비거주 건), 실계약(LeaseTerm 원천 컬럼)은 그대로 두고 `LeaseTerm.contractFieldOverrides`(sparse Json)에 표시값만 저장한다. '조건부 할인은 계약서=정가, 수납만 할인' 규칙의 연장.
- 정본은 `lib/contractFieldOverrides.ts`(파싱·검증·병합 한 벌). 소비처는 `buildContractData` 와 generate route 두 곳뿐 — **청구·수납 엔진은 이 컬럼을 모른다.**
- 편집 대상 8필드: 입실료·보증금·청소비·입실일·퇴실예정일·매월 납부일·호실·전입신고 표기. **신원 4종(성명·연락처·생년월일·성별)은 고객정보가 정본이라 안 연다.**
- UI 는 계약서 보기 정보 표 인라인 입력(§30 규칙 3). no-print 입력 + only-print 텍스트 쌍이라 종이엔 안 나간다. 서명 확정 후엔 bodyLocked 파생으로 함께 잠긴다.
- 저장·본문편집·복귀 시 **미서명 활성 링크를 자동으로 닫는다**(낡은 스냅샷으로 서명받는 사고 봉합). 제출된 링크는 닫지 않는다 — 발급 리마인더가 closedAt:null 조건(2026-07-23 결정).
- generate API body 로 금액을 받지 않는다 — 값은 DB 단일 출처(API 직접 호출로 임의 금액 발급 방지).
- 감지망: check-contract-override-lock G5 축(서명 후 표시값 편집 대조).

### 서명 지우기 = 서버 저장 서명도 X 버튼으로 (2026-08-05, 운영자 요청)
원격 링크 서명은 **서명 순간 서버에 저장**된다(제출 전이라도). 잘못 서명하면 지울 길이 없었다(홍은주 동의서 사건). `clearContractSignature(leaseTermId, 'contract'|'disposal')` 가 해당 서명 두 칸을 지우고, **서명 네 칸이 전부 비면 signedContractSnapshot 도 함께 지운다**(생사 동일 원칙). 열린 링크(미제출)는 함께 닫는다 — 지운 서명의 출처가 열려 있으면 되살아난 것처럼 보인다.
- ⚠️ Prisma 7 에서 Json 칸 비우기는 `Prisma.DbNull`. `{ set: null }` 은 컬럼에 문자 그대로 `{"set": null}` 값이 저장된다(실측). resetContractOverride 가 이 방식이어서 '공통 템플릿으로'가 본문을 그 객체로 만들 뻔했다 — 세 곳 모두 DbNull 로 통일(2026-08-05 봉합).
- X 버튼은 서버 서명이 있으면 danger 확인창 후 삭제, 화면 임시 서명만 있으면 즉시 로컬 삭제. 삭제 시 capturedAt 로컬 상태도 함께 비운다(안 비우면 파생 잠금이 잠긴 채 남는다).

### 버전 폐기 = 증거를 남기고 잠금만 푸는 유일한 문 (2026-08-19, 신고 63cd1049)
발급본 삭제(`ContractFile.deletedAt`)는 **잠금 사슬의 어느 고리도 아니다.** 서명 네 칸이 그대로라 계약서는 여전히 잠겨 있고, 오히려 마지막 부를 지우면 `/contracts` 발급 대기가 되살아나 옛 스냅샷으로 재발급을 권한다(501호 실측 — 한글 이름 계약서를 지우고 다시 발급했더니 같은 한글 이름이 또 나왔다).
- **폐기 = 서명 네 칸·격리본·오버라이드 사본을 `LeaseTerm.contractVersionArchive`(append-only Json)로 옮기고, lease 의 그 칸들만 비운다.** 발급본과 `issuedSnapshot` 은 손대지 않고 `ContractFile.voidedAt` 도장만 찍는다. 살아 있는 서명 링크는 전부 닫는다(발급 대기·종 알림 동시 해소).
- 정본은 `lib/contractVersion.ts` + `voidContractVersion`. **결과가 '서명 0' 이 되는 갈래는 전부 이 문을 지난다** — 전량 삭제('all')도 마지막 한 장 삭제도. 그러지 않으면 증거 파괴 경로가 하나 남는다.
- 적용취소(`restoreContractVersion`)는 폐기 직전 상태를 그대로 복원하되, 그 사이 새 서명이 들어왔으면 거부한다.
- **폐기 후에는 재서명이 필요하다.** 이름 표기가 잘못된 계약서는 정정본에 다시 서명받는 것이 계약 실무의 정석이고, '서명은 A 에 했는데 B 를 발급하지 않는다'(2026-08-03)와 같은 자리다.
- 잠금 안내 세 곳(표시값·본문·계약일)이 이 버튼을 가리킨다. 종전 문구 "서명란의 X 버튼으로 지우면"은 잠금이 네 칸 OR 인데 단수로 말해 거짓이었다(서명 둘이면 X 하나로 안 풀린다).
- 감지망: G7(폐기 이력 증거 결손) 신설, 계약일 정합 축 1 에서 폐기본 제외, G1·G5 대조 대상을 `isCurrentSignatureLink`(지금 서명을 만든 링크)로 한정. 드리프트 비교도 같은 정본을 쓴다 — 안 그러면 폐기 후 재작성이 허위 경고를 만들고 그 경고의 '재서명 받기'가 방금 받은 서명을 다시 폐기한다.

### 다중 버전 = 실계약이 먼저이고 대표는 실계약 고정 (2026-08-20, 운영자 결정 5건)
한 계약에 판본이 여럿 설 수 있다. 기능 자체는 **영업장 토글**(`Property.multiContractVersions`, 기본 꺼짐)로 잠겨 있고, 꺼진 영업장은 1인당 계약서 1개이며 목적 입력이 화면에 아예 없다.
- **목적**(`ContractFile.issuePurpose`)은 고정 선택지 셋뿐이다 — 실계약·제출용·번역본(`lib/contractPurpose` 정본). **저장값 null 이 곧 실계약**이라 이 칸이 생기기 전 발급본은 백필이 필요 없다. 쓰기는 발급 트랜잭션(번호 예약) 한 번뿐 — 고쳐야 하면 폐기하고 다시 발급한다. 사후 수정을 열면 '실계약'을 나중에 '제출용'으로 바꿔 책임을 옮기는 길이 생긴다.
- **대표본은 실계약 고정**이다(`lib/contractCurrentIssue`). 시각은 실계약이 여럿일 때 동률만 가른다. 종전 '폐기 아닌 것 중 최신'은 어제 뽑은 번역본을 대표로 만들었다. **대표본 없음은 정당한 상태다** — 실계약을 폐기했다고 파생 판본이 승격되면 근거 없는 표시본이 대표 자리에 앉는다. 화면 둘과 서류 보내기가 이 정본 하나를 쓴다(종전에 서류 보내기는 `voidedAt` 을 읽지도 않아 폐기본을 발송 후보로 올렸다).
- **실계약이 무조건 먼저다.** 살아 있는 실계약본이 없으면 파생 발급도 새 버전 작성도 서버가 거부한다.
- **모든 판본은 각각 서명을 받는다.** 새 버전 작성(`supersedeContractVersion`)이 지금 서명을 이력으로 옮기므로, 다음 판본은 서명 없이는 발급할 수 없다 — '재서명 필수'가 규칙이 아니라 구조로 강제된다.
- **폐기와 새 버전은 같은 이동, 다른 도장**이다. 폐기 = `voidedAt`('계약서로서 효력이 없다'), 새 버전 = `supersededAt`('그때는 맞았고 지금 서명의 주인은 다음 판본이다'). 이력 항목에 `kind` 로 남고 **kind 없는 구항목은 폐기로 읽는다**(`versionKind`). 배열의 `v` 는 절대 올리지 않는다 — 올리면 파서가 새 항목을 통째로 버려 G7 과 되돌리기가 조용히 눈을 감는다.
- **한 발급본은 이력 항목 하나에만 속한다.** 이동 쿼리가 `voidedAt: null, supersededAt: null` 을 함께 보고, 되돌리기는 그 항목이 실제로 찍은 도장만 지운다. 안 지키면 나중 항목을 되돌릴 때 앞 항목의 도장까지 지워져 폐기된 종이가 이력만 남긴 채 되살아난다(감지망 G8).
- **폐기본은 목록에서 접힌다**(숨김이지 삭제가 아니다). 접힘 칸에 폐기 적용취소가 상설로 있고, 폐기본 행에서는 보내기·인쇄를 걷었다 — 효력 없는 종이를 밖으로 내보내는 길은 없다. 세는 일(`groupCount`·대표 판정·삭제 안내)은 접힌 행까지 포함한 전량으로 한다.
- **토글을 끄면 파생 판본이 숨는다.** 서버가 행에 `hidden` 플래그만 실어 보내고 화면이 접는다. **감지망·발급 대기·종 알림 쿼리에는 이 필터를 절대 넣지 않는다** — 그쪽은 '파일이 존재하면 알림을 끈다'는 억제 로직이라 여기서 새면 이미 종이가 나간 계약이 발급 대기로 되살아나고 같은 내용이 또 발급된다.
- 계약일 정합 축 1 은 `supersededAt: null` 을 더해 봉합했다. **축을 '라이브 또는 이력 중 하나와 일치'로 넓히는 안은 채택하지 않았다** — 집합 소속 판정이 되면 이 축이 잡아야 할 결함(발급이 옛 링크 날짜를 인쇄하던 것)이 그물 밖으로 나간다.
- 잠금 안내 문안은 `lib/contractLockMessage` 한 벌이고 화면 셋·서버 둘이 같은 문장을 쓴다. 토글이 켜진 영업장에서만 '새 버전 작성'을 함께 말한다.

## 서명 진행 판정 (2026-09-04 확정)

정본은 `lib/disposalSignGate.ts` 하나다. `signStage()` 가 none·partial·complete 를 답하고,
`disposalSignatureMissing()` 은 그중 발급 축(계약서는 있는데 동의서가 없다)만 본다.
관계는 `disposalSignatureMissing(s) === (signStage(s)==='partial' && s.hasContractSignature)` 다.

- **완료의 정의는 영업장마다 다르다.** 동의서를 쓰면 둘, 안 쓰면 계약서 하나.
- **반쪽은 양방향이다.** 계약서만(413호)과 동의서만(506호)이 둘 다 반쪽인데, 종전에는 뒤쪽이
  화면 어디에도 안 나왔다. 링크 쿼리의 `signedAt: { not: null }` 이 그것을 통째로 걸렀다.
- **종과 푸시는 한 소스다.** computeAlerts·summarizeAlerts 하나를 쓰므로 판정을 거기서 고치면
  둘이 자동으로 같이 움직인다. cron 이 카테고리를 손으로 세면 그 계약이 깨진다.
- **완료와 반쪽은 다른 카테고리다.** 같은 것으로 두면 푸시 요약이 반쪽을 '서명 받음'으로 세고,
  그것이 운영자를 잘못된 발급으로 이끈 원래 경로다.
- 반쪽의 할 일은 발급이 아니라 남은 서명 받기라 목적지도 다르다.

## 서명란 성명 (2026-09-04 확정)

**종이 위 성명 네 자리는 서버가 정한 한 변수에서 나온다.** 1p 정보표 · 2p 서명란 ·
3p 동의서 정보표 · 3p 동의서 서명란. 종전에는 서명란 둘만 클라이언트가 보낸 값이었고, 그래서
한 종이 안에서 상단은 한글 하단은 영문으로 갈렸다(413호 실측).

- 조정 수단은 **표기 선택과 고객 정보 세 칸**이다. 서명란 자유 입력이 아니다.
- 자유 입력이 위험한 이유는 고칠 수 있다는 것보다 **무엇으로 고쳤는지 안 남는다**는 것이다.
  printedFacts 에 서명란 축이 없어 발급본 박제는 정보표 이름만 기록한다.
- `PrintContractData` 에 그 필드를 두지 않는 것이 봉인이다. 필드가 없으면 값이 흐를 통로가 없다.

## 남은 서명 안내 (2026-09-04)

서명자 다수가 한국어를 못 읽는다(베트남·방글라데시·러시아·우즈베키스탄·미얀마).
**텍스트에만 기대는 안내는 이 화면에서 작동하지 않는다.**

- 토스트는 이 페이지에서 제일 약한 수단이다. 핀치줌을 허용해서 fixed 요소가 확대 중에는 시야
  밖으로 나간다(knowledge/mobile-scroll-viewport, 신고 d9f93bdd). 계약서를 확대해 읽은
  사람에게는 안내가 아예 없었던 셈이다.
- 그래서 상시 표시(흐름 안 CTA)가 정본이고 확인창이 보조다. 확인창은 세션당 한 번뿐이다.
- **아라비아 숫자가 가장 강한 무텍스트 신호다.** 서명자 국적 전부가 실생활에서 읽는다.
- 제출 버튼을 disabled 로 두지 않는다. 눌러도 반응이 없으면 화면이 고장난 증거로 읽힌다.
  회색에서 코랄로 켜지는 전환 자체가 "이제 된다"를 말한다.
- 자동 스크롤은 사용자가 눌렀을 때만. 저절로 움직이면 서명이 취소된 줄 안다.

## 본국어 성명 — 수집만 남고 종이 병기는 회수 (2026-09-07 확정)

계약서에 본국어 이름이 꼭 필요하지는 않으니까(필요로 했던 건 단지 내가 알고 싶어서)."

  옛 라벨 '신고'는 normalizeRegistrationLabel 이 흡수해 드리프트 비교가 오탐하지 않는다.


## 납부일 게이트 — 계약서 문에서는 원천 납부일이 필수 (2026-09-07 배포, 설계 D)

정금순님(422호) 계약서의 매월 납부일이 빈 채 서명된 건에서 나왔다. 예약 단계는 납부일이
비는 게 정상인데, 계약서를 쓰는 순간부터는 계약의 사실이어야 한다. **상태가 아니라 문을
보고 막는다.**

- 막는 문 넷 — 서명 요청(`issueContractShareLink`, `DUE_DAY_REQUIRED` 코드)·이어받기
  (`renewContractShareLink`, 빈 스냅샷 승계 거절)·발급 API(409, `SNAPSHOT` 재발급만 예외)·
  계약서 화면(진입 시 모달 + 발급·미리보기 문 앞 선채움). 한 자리만 막으면 나머지 문으로
  빈 값이 나간다(같은 클래스 반복 금지).
- 거절은 막다른 길이 아니다 — 화면이 코드를 받아 채움 창(`DueDayFillDialog`, 입주일 날
  프리필)을 열고, 저장하면 하던 일을 이어서 재시도한다(SIGN_IN_PROGRESS 와 같은 문법).
- 값은 표시값 오버라이드가 아니라 **원천(lease.dueDay)** 저장(`setDueDayForContract`) —
  표시값만 얹으면 종이에는 날이 찍히는데 청구는 납부일 없는 계약을 굴린다. 게이트 판정도
  같은 이유로 병합값이 아니라 원천(`ContractData.lease.dueDaySource`)을 본다. 저장 시 미서명
  활성 링크는 닫는다(closeStaleUnsignedLinks 와 같은 다섯 조건).
- ContractView 인라인 납부일 셀은 원천이 빈 동안 원천 저장으로 갈아탄다. 원천이 차면 종전
  표시값 오버라이드(이 계약서에만 다르게 찍는 길)로 돌아간다.
- 보존 두 곳 — 거주 전 상태 저장과 호실 일정 적용취소가 납부일을 강제로 비우던 것을
  **보존**으로 바꿨다. 문이 예약 단계에 채운 원천을 걷으면 서명받은 종이의 납부일이
  사라진다. 감사 규칙 1-b(거주 전 납부일=오염)는 계약서 흔적(링크·파일) 없는 건만 잡는다.
- 그물 `scripts/check-due-day-gate.mjs`(verify:fast) — 문 넷·채움 액션·화면 배선·보존·감사
  예외 앵커. 역주입 4건(병합값 게이트·보존 회귀 2·문 제거) 전부 적발 확인.
