# 회귀 감지망 (2026-08-01 자동화)

"기존에 잘 되던 게 새 기능 때문에 먹통되는" 것을 막는 장치. 관련: [[mobile-scroll-viewport]], [[money-display-feedback]].

## 왜 자동화했나
감지망 9종이 있었지만 **커밋·배포 어디에서도 자동 실행되지 않았다**(F페이즈에서 확인).
그동안 회귀가 잡힌 건 사람이 매번 손으로 돌렸기 때문이지 체계가 막아준 게 아니었다.

## 배치

수동: `npm run verify:fast` · `npm run verify:db` · `npm run verify`

**우회**: `git commit --no-verify` / `git push --no-verify` / `STAYEUM_SKIP_HOOKS=1`.
우회는 기대값이 바뀐 게 확실할 때만. 규칙 변경은 loop.md 4번(운영자 승인) 대상이다.

tsc 가 중복 식별자 오류로 실패한다. pre-push 가 먼저 지운다(`find .next -name "* [0-9].*" -delete`).

## 만들 때의 교훈 — 마운트만 보면 알맹이가 빠져도 통과한다

`check-standalone-scroll` 은 원래 `<DocumentScroll />` 이 **마운트됐는지**만 봤다.
그래서 DocumentScroll **안의 클래스 토글을 지워도 통과**했다(자동화 검증 중 실측).
Modal 검사도 처음엔 `/lockBackgroundScroll/` 이라 **import 만 남아도 통과**했다 — 호출(`()`)을 봐야 한다.

**감지망을 새로 만들면 반드시 회귀를 일부러 주입해 잡히는지 확인한다.** 통과만 보면 무력한 감지망을 신뢰하게 된다.

D 페이즈에서 새로 짠 그물 넷이 역주입에서 안 잡혀 고쳤다. 실패 양상이 반복된다.

1. **부분 문자열** — `includes('activeMs')` 는 `activeMsX` 로 이름만 바꿔도 통과한다.
   `lastFocus` 도 같았다. 검사 문자열은 **호출 형태까지** 잡아야 한다(`r.activeMs ?? r.durationMs`).
2. **같은 문자열이 주석에도 있다** — `open.kakao.com` 이 셀렉터에서 빠져도 주석 때문에 통과했다.
   파일 전체가 아니라 **그 선언 줄만** 본다.
3. **정규식으로 중첩 구조를 가른다** — `@media` 블록을 정규식으로 벗기려다 규칙 절반을 놓쳤다.
   중괄호 깊이를 직접 세야 한다.
4. **거리로 위치를 근사한다** (2026-08-03) — "가드 밖에 있는가"를 `앵커[\s\S]{0,300}?대상` 으로 봤다.
   가드를 씌워도 앵커에서 몇 글자 떨어져 있지 않아 그대로 통과했다. 거리는 위치가 아니다.
   블록을 열고 **중괄호 깊이를 세서 깊이 1인지** 보고, 한 줄 `if` 로 감싼 경우까지 그 줄에서 확인한다.

## 데이터 조건으로 걸면 영구 실패 게이트가 된다

"지금 공개인 파일이 있나" 같은 데이터 조건은 이관이 끝나기 전까지 계속 실패한다.
그런 자리에서는 **코드가 규칙을 다시 어기는지**를 본다(명단·소스 가드).
데이터 그물은 이관이 끝나 상시 참이 된 뒤에 겹친다.

## 목록은 package.json 이 정본이다 (2026-08-03)

훅은 `npm run verify:fast` / `verify:db` 를 부르기만 한다. **훅에 스크립트 이름을 나열하지 않는다.**
전에는 훅과 package.json 이 각자 목록을 들었고 실제로 5종이 어긋났다 —
공개 사이트 감지망이 커밋 때 안 돌았고, 재고 규격·경계 두 종이 푸시 때 안 돌았다.
`npm run verify` 는 계속 실패하는 상태였는데 훅이 그걸 안 불러서 아무도 몰랐다.

| 묶음 | 무엇 | 어디서 도나 |
|---|---|---|
| `verify:fast` | 순수 로직 9종 (DB 불필요) | pre-commit · 2.1초 |
| `verify:db` | DB 대조 9종 | pre-push · 3.6초 |
| `verify:data` | **운영자 판단 대기** (규격 누락 · 미반환분 분류) | pre-push 에서 경고만, 막지 않는다 |
| build 게이트 | check-public-tracking · check-public-site | Vercel 배포 |

## 게이트와 입력 대기를 가른다

`check-spec-missing` 은 "낱개 용량이 안 들어간 지출"을 잡는다. 진짜 문제지만
**개발자가 푸시 시점에 채울 수 있는 값이 아니다.** 게이트로 두면 값이 채워질 때까지 모든 배포가 막힌다.
그래서 `verify:data` 로 분리해 pre-push 가 **보여주되 막지 않는다**. 조용히 넘어가지도 않는다.

판정 기준 — **개발자가 지금 고칠 수 있으면 게이트, 운영자가 값을 넣어야 하면 입력 대기다.**

`check-withhold-classification` 이 두 번째 사례다(2026-08-11). 퇴실 미반환분 중 보증금 청소비 몫이
'보증금 몰취'로 잡힌 건을 찾는데, 과거분 재분류는 "그 미반환에 파손 차감이 섞이지 않았다"는 운영자
확인이 있어야 확정된다. 실측 3건 중 2건(507·509)은 운영자가 지목해 백필했고 502호 남태우는 대기라,
게이트에 넣으면 승인 전까지 모든 배포가 막힌다. 대신 **생성 경로가 성격대로 가르는지**는 게이트에
남겼다(`verify-money-consistency` 6-2 소스 가드 + 미반환분 부가수익 합 대조).

즉 같은 규칙을 두 겹으로 건다 — **앞으로 생길 건은 게이트가, 이미 있는 건은 입력 대기가** 본다.

## 만들었는데 안 도는 감지망이 또 있었다

F 페이즈에서 "감지망은 만들어만 두면 안 돌아간다"를 고쳤는데, 그때 목록에서 셋이 빠졌다.
전부 실제 신고를 보고 만든 것들인데 **한 번도 자동으로 돈 적이 없었다.**
게다가 셋 다 출력만 하고 `exit 0` 이라 물려도 통과만 했을 것이다.

- `check-deposit-settlement` 퇴실 보증금 정산 누락 (신고 249b5652)
- `check-tracked-categories` 비추적 카테고리 활성 카드 (서빙집게 사건)
- `check-spec-dims` 규격 차원 불일치 (신고 0d6242f0)

세 번째는 판정도 틀렸다. **차원 불일치 자체는 정상이다** — '라면 120g x 100개'는 올바른 입력이다.
결함은 그 상태에서 곱셈이 실제로 걸리는 것이다. 불일치 존재로 걸면 늘 실패한다.

**새 감지망을 만들면 그 자리에서 훅에 연결하고, 실패 조건을 넣고, 역주입으로 종료코드 1 을 확인한다.**
셋 중 하나라도 빠지면 없는 것과 같다.

## 감지망이 없는 축은 없다 (2026-08-03)

사람 상태 전이(B)·대외 다국어 4벌(D)·서류 발급 문구를 전부 붙였다.
서류 쪽은 두 겹이다 — 화면(ContractView)과 인쇄(contractPrintHtml)의 **변수 표가 같아야 하고**,
저장된 템플릿의 `{{키}}` 를 코드가 전부 채울 수 있어야 한다. 못 채우면 renderContractText 가
원문을 그대로 남겨 **자리표시자가 실제 계약서에 찍혀 나간다**(실제로 29건이 비문이었다).

## 못 읽으면 통과가 아니라 위반이다

계약서 변수 그물을 정규식으로 짰다가 `useMemo<Record<string,string>>` 제네릭에서 빗나가
null 을 돌려줬고, **대조 자체가 조용히 건너뛰어졌다.** 통과처럼 보였다.
깊이 추적으로 바꾸면서 "파싱 실패 = 위반" 을 명시했다.

소스를 파싱하는 그물은 파싱이 깨지는 순간 무력해진다. 그러니 **파싱 실패를 통과로 두지 않는다.**

## 모델이 실제 규칙을 모르면 그물은 자기가 지키려던 것을 못 본다 (2026-08-11)

`verify-money-consistency` 18번은 홈과 수납 관리의 청구 합을 대조하는 그물인데, 수납 쪽 모델을
'방이 붙은 청구 대상 계약 전부'로 가정하고 있었다. 실제 코드는 방마다 대표 하나만 행으로
만들었고, 그래서 402호 황인정 329,000 이 화면에서 통째로 빠진 날에도 **위반 0으로 통과**했다.
모델과 코드가 다른 그물은 통과가 아니라 침묵이다.

고친 방식은 **행 생성 규칙을 소스에서 읽는 것**이다(`roomsActions.includes('roomLeaseRowOrder(')`).
정본 헬퍼를 쓰면 계약마다 한 행으로 모델링하고, 아니면 종전 대표 1건 규칙으로 모델링한다.
그래서 규칙이 퇴행하면 그물이 그 퇴행한 규칙으로 데이터를 재보고 실제 사라지는 계약을 이름으로
찍는다. 실증: 행 붕괴 코드로 되돌리면 위반 17건에 402호 황인정·503호 송호준·404호 조성훈이
이름으로 뜬다.

**합만 보면 상쇄된다.** 그래서 합 대조 옆에 '청구 대상인데 행이 없는 계약'과 '청구가 0이어도
목록에서 빠지는 계약'을 따로 센다. 두 누락이 서로를 지우는 날에도 잡히게 하기 위함이다.

**캡은 감지망의 대체물이 아니다.** 초과 수취를 캡으로 조용히 잘라내면 화면은 맞아 보이고 문제는
사라진 것처럼 된다. 잘라내는 대신 위반으로 띄우면 사람이 그 돈의 성격(선수금·잡수입)을 정한다.

## 락인은 정본을 이긴다 — 그래서 '값이 다른 것'이 아니라 '없는 청구'를 본다 (2026-08-12)

`billForLeaseMonth` 는 그 달 record 의 `expectedAmount` 최댓값(락인)을 청구 정본보다 먼저 돌려준다.
가변 마스터(rentAmount)로 과거 결산을 재계산하지 않기 위한 설계지만, **한 번 잘못 굳은 락인은
스스로를 정당화한다** — 읽는 자리가 전부 그 값을 청구로 받아들이므로 오간 적 없는 미납이 영구히 선다.

미수율이 0.82% 로 부풀어 있었다).

그물의 축을 '락인 != 정본' 으로 잡으면 안 된다. 둘이 다른 것은 정상이고 그게 락의 존재 이유다.
잡아야 할 것은 **그 달에 청구 자체가 없는데 양수 락인이 있는 것**이다.
`check-billing-lock-drift.ts` 는 정본 함수에 락을 넘기지 않고(`billForLeaseMonth(lease, mon, null)`)
0 이 나오는 달만 본다. 규칙을 사본으로 적지 않으므로 정본이 바뀌면 그물도 같이 바뀐다.

**옵셔널 필드는 조용히 규칙을 끈다.** `isShortTerm`·`moveInDate` 는 `BillingLeaseFields` 에서
옵셔널이라(둘 다 있을 때만 단기 규칙 발동) 안 넘겨도 컴파일이 통과한다.

새로 찍는다** — 코드가 422 와 같은 오염을 만든다. 소스 가드로 그 두 칸을 본다.

## select 는 모르는 값을 만나면 첫 항목을 고른다 (2026-08-12)

부가수익 '입주자 연결' 선택지를 그 달 수납 행에서 파생하고 있었다. 수납 행에는 퇴실 계약이 없으므로
퇴실자에게 묶인 수익은 `defaultValue` 가 목록에 없었고, 브라우저가 첫 항목('연결 안 함')을 골랐다.
그래서 **카테고리만 고쳐 저장해도 연결이 조용히 끊겼다.** 서버는 폼이 준 대로 `tenantId`·`leaseTermId`
를 null 로 썼다 — 폼에 칸이 없는 것과 '연결 안 함' 을 구분하지 않았기 때문이다.

봉합은 세 겹이고 셋 다 소스 가드가 있다. ① 선택지 축을 '그 달 청구 대상'에서 '연결 가능한 계약
전부(퇴실 포함)'로 바꾼다. ② 목록에 없는 기존 연결은 항목으로 세운다. ③ 서버가 '칸 없음'과
'연결 안 함'을 구분한다. 끊긴 연결은 뱃지 하나가 아니라 원장의 대조 축이다 — 보증금 출처 부가수익은
`leaseTermId` 로 미반환분과 맞춰 보고 청소비 잔고도 계약별로 묶인다.

## 날짜 칸 껍데기 — 맨글자로 태어나는 것을 막는다 (2026-08-24, 오류신고 c2ab5b83)

`scripts/check-datepicker-shell.mjs`, `verify:fast` 등재. 호출부 71곳 검사.

정본 `DatePicker` 트리거의 기본 클래스는 `w-full text-left truncate` 뿐이라, 껍데기를 안 넘기면

**정본에 기본 껍데기를 주는 안은 기각했다** — 소비처 높이가 dense 26px ~ 모달 42px 로 갈려서,
한 벌을 강제하면 §12 '한 폼 안 입력 높이 혼용 금지' 를 이쪽에서 깬다. 각 자리가 자기 폼 형제와
같은 껍데기를 넘기는 것이 정본이고, 그물은 그 약속(배경 + 보더)만 본다.

**반쪽이 되기 쉬운 자리가 셋이었고 역주입으로 셋 다 겪은 뒤 조였다.**

1. `className=(\{[\s\S]*?\}|"[^"]*")` 로는 값을 못 읽는다. `` className={dense ? `${cls} …` : x} ``
   에서 첫 `}` 는 템플릿 보간의 닫는 괄호라 값의 절반만 읽고 통과한다. **중괄호 균형**을 센다.
2. 상수 선언을 줄 단위로 자르면 삼항(`const cls = dense ? '…' : '…'`)에서 첫 줄 `dense` 만 읽고
   껍데기를 못 봐 **거짓 위반**을 낸다. 들여쓰기와 이어짐 기호로 선언 전체를 집는다.
3. 삼항을 합쳐서 보면 **한 가지만 껍데기가 있어도 통과한다.** 실제로 `dateFieldCls` 를 빈
   문자열로 만들어도 같은 식의 `inputCls` 가 검사를 통과시켰다. 가지를 갈라 각각 본다.

예외 하나 — 인라인 텍스트 편집형(입주자 상세 '연락 알림일')은 밑줄과 강조색이 어포던스를
대신하므로 `underline` 을 배경·보더 대신 인정한다. 밑줄도 배경도 보더도 없으면 맨글자다.
