# 돈 표시·저장 피드백 정본 (크리티컬 신고 50a2a69b, 2026-07-30)

관련: [[domain-billing]], [[decisions]]. 신고: 예약금 입금·할인 입력이 화면에 반영되지 않아 재시도 → 중복 수납.
사고는 두 클래스의 결합이었다 — **계산 정본 이탈**(원가 직표시)과 **보이지 않는 저장**(성공 무피드백).

## 1. 표시 정본 수렴 원칙

- 청구·잔액·예정액을 화면에 내보내는 모든 경로는 정본 계산(lib/billing billForLeaseMonth, lib/rentDiscount discountedRent)을 탄다. **원가(lease.rentAmount) 직표시 금지.** 클라이언트 재계산 금지 — 서버 settlement 값을 소비한다.
- 예약(RESERVED) 단계도 예외가 아니다: 청구 예정액 = 입주월 기준 할인·예약 인상 반영, 실수납은 `RoomRow.reservationPaid`(조회월 무관 lease 전체 합)로 노출. 단 balance·totalPaid 0 + isPaid true 는 유지(예약은 미납·수금 집계에서 제외하는 정본 — rooms 스트립·배치 문자 회귀 방지).
- **받은 돈은 사실이고, 사실은 조회월과 무관하게 보여야 한다**(운영자 정의). 보증금·예약 선납 합계는 월 필터를 타지 않는다(getPaymentsByLease.depositPaidTotal).
- **보증금 표시 정본은 `DepositStatusPanel` 하나다**(2026-08-02). 수납 정보 모달과 고객정보가 각자 그려서 갈렸고,
  둘 다 `getPaymentsByLease`(payDate 월 창)를 걸러 만들었기 때문에 보증금을 받은 달을 지나면 화면에서 사라졌다.
  계약 단위 조회는 `getDepositPaymentsByLease`. 편집·삭제 접점도 이 패널 하나로 모았다(PaymentRecordList 의 보증금 행은 안내만).
- **인수 전 입주자 보증금은 승계분 명목으로 돌려주지 않는다**(운영자 확정 2026-08-02).
  이전 원장의 운영 원칙이었고 인수 시 그 보증금을 전달받았으므로, 그때 입실한 분들에게는 그대로 적용한다.
  케이스가 아니라 클래스다 — 퇴실 폼이 `carriedOver` 이면 '환불 안 함' + 사유 `CARRIED_OVER_WITHHOLD_REASON`
  을 기본 선택으로 제안하고 화면이 그 이유를 문장으로 말한다. 세그먼트라 한 번 눌러 되돌릴 수 있다.
  대기 중인 승계 계약 9건(각 50,000)이 이 규칙을 탄다.
- **사유 라벨은 '키값' 에서 '인수 승계 보증금' 으로 중립화했다**(운영자 확정 2026-08-17, 어휘만·설정 분리 없음).
  열쇠값은 이 영업장의 옛 관행을 부르던 말이라 다른 영업장이 읽으면 뜻이 통하지 않는다.
  **이미 저장된 '키값' 문자열은 불변**(DepositRefund 4건·ExtraIncome detail). 표시 화면 셋은 저장값을
  그대로 찍고 사유 셀렉트 셋은 전부 새 기록용이라 옛 값을 되읽지 않는다. 그래서 목록에서 빠져도 안 깨진다.
  `scripts/fix-carryover-forfeit-reason.ts` 의 `REASON` 도 그때의 백필 기록이라 옛 문자열 그대로 둔다.
- **승계 보증금에 수납 record 를 만들지 않는다.** 인수 전 계약 38건 중 35건에 record 가 없는 것이 정상 상태다.
  없는 입금을 만들면 증빙 없는 기록이 되고, 코드가 승계를 인식하는 근거(입주일 대 인수일)도 꺼진다.
  설명이 필요한 자리는 record 가 아니라 `DepositRefund.reason` 과 ExtraIncome detail 이다.
- **청소비는 받은 경로와 무관하게 '청소비' 다**(운영자 정본 2026-08-11 — 08-02 판단 갱신).

  > "보증금 5만원에 이미 청소비 2만원이 포함되어 있었고 난 3만원을 돌려준 거야. 즉 정상적인 청소비를
  >  받은 거야. 보증금 몰취는 시설물이 파손되거나 했을 때 (잔여) 3만원에서 차감할 때 몰취가 되는 거지."

  보증금 안의 청소비 몫을 쓴 것은 정상 청소비 수취라 카테고리가 '청소비' 이고, **그 몫을 넘는 차감만**
  '보증금 몰취' 다. 미반환분이 섞이면 부가수익 행도 둘로 나뉜다.
  2026-08-02 에 정한 "받은 경로대로 둔다" 는 **계정 등급**(청소비도 그냥 사업 수입) 판단이라 그대로 유효하고,
  이번에 바뀐 것은 **라벨**이다. 같은 거래가 받은 경로에 따라 몰취로도 불리면 세무 자료에서
  손해배상성 잡수입으로 읽힌다.
  - 판정은 **구조**로 한다 — `lib/depositComposition` 의 `splitWithheldDeposit`, 청소비 몫은
    `cleaningFeeDeductible(lease.cleaningFee, 입실 수령분)`(퇴실 폼이 여는 최대 환불액과 같은 식).
    사유 텍스트('청소비')는 운영자가 자유롭게 고르는 값이라 계정을 정하지 않는다.
  - 퇴실 정산이 만든 청소비는 `payMethod='보유 보증금'` 이라 **입실 수령분과 구분된다.**
    '입실 때 따로 받았는가' 를 묻는 자리는 전부 `CLEANING_FEE_RECEIVED_WHERE` 를 써야 한다 —
    안 그러면 either/or 판정이 퇴실 직후 뒤집혀 같은 2만원을 두 번 돌려주는 경로가 열리고,
    청소비 잔고가 두 배로 뜬다.
  - 존량 3건이 이 규칙 이전 상태였다(전부 계약 보증금 50,000 · 청소비 20,000 · 반환 30,000).
    507호 먀 야다나 모에·509호 탄 타르 누 아예는 2026-08-11 백필로 정정. **502호 남태우는 승인 대기.**
  - 인수 승계분 '키값' 몰취 3건은 `lease.cleaningFee=0` 이라 규칙상 전부 몰취로 남는다(변동 없음).
- **승계 보증금을 몰취하면 매출이 맞다**(운영자 확정 2026-08-02). 인수 시 그 보증금을 인계받거나
  인수대금에서 차감받았으므로 장부에 예수보증금이라는 부채가 서 있다. 퇴실 시 반환하지 않으면 부채가 소멸하며
  순자산이 늘고, 그것이 수익이다. 앱의 보유 보증금 KPI 가 이미 계약 보증금 합계 기준이라 구조도 정합한다.
  전제가 바뀌면(인계·차감을 못 받은 인수) 결론도 뒤집히므로, 다른 영업장에 적용할 때 반드시 다시 확인할 것.
- **인수 전 입주자는 '미수납'이 아니다**. 보증금을 양도인이 받았고 인수 시 승계됐다. 실측 10건 중 9건이 이 경우였다.
  서버가 입주일과 인수 컷오프를 비교해 `preAcquisition` 을 내려보낸다. 같은 이유로 투어 대기·취소 계약도 '미수납'이 아니다.
- RESERVED 행의 expected 는 **표시용**이다 — 화면 집계(수납 스트립 청구·수납 합산)에 섞으면 잔액 0 특성 때문에 청구·수납이 함께 부풀려진다(신고 78ea0c3d: 호실 배정 순간 +890,000 유령 수납). 스트립 정본: 청구·수납은 RESERVED 제외, 만실 시 참고치엔 예약 방 baseRent 포함. 예약 확정자의 그 달 전액은 홈 예상 매출에만 가산(2026-06-20 결정).
- 홈 예상 수입 = 수납 관리 청구 합 + 예약 확정 전액 + 퇴실 완료자 귀속 인식분 + 기타수익 — 두 화면 차이는 설계이며 양쪽 도움말이 교차 설명한다(7월 실측: 16,739,000 = 16,089,000 + 470,000 + 110,000 + 70,000).
- **등식 문장은 `components/ui/MoneyEquation` 하나가 만든다**(2026-08-12). 홈 KPI 카드 **세 장**(예상 수입·예상 운영이익·예상 지출)과 수납 관리 캡션이 같은 함수를 부른다. 값이 원 단위로 같아도 화면마다 문장을 조립하면 항 구성·항 이름이 갈리고, 그러면 같은 숫자에 다른 설명이 붙는다(실제로 RoomsClient 가 같은 값을 39줄 간격으로 '이 달 청구액'·'이 달 청구' 두 이름으로 불렀다). 항 이름은 전부 운영자가 확인하러 갈 화면의 라벨과 글자까지 같다 — 이 달 청구액(수납 스트립)·기타수익(홈 세부 재무 요약 타일)·기록된 지출(홈 세부 재무 요약 타일·결산 보고서 운영이익 정의)·고정 지출 (예정)(지출 관리 요약).
  - 지출 두 항의 이름은 `MoneyEquation` 안의 상수 하나에서 나온다(`L_RECORDED_EXPENSE`·`L_PENDING_RECURRING`). 운영이익 등식이 **빼는** 두 항을 예상 지출 등식이 **더한다** — 문자열을 두 곳에 두면 한쪽만 고쳐졌을 때 같은 모집단이 두 이름을 갖는다.
- **같은 숫자에는 화면과 무관하게 한 이름을 쓴다**(2026-08-12 운영자 지시로 '홈 예상 수입' → '예상 수입'). 이름에 화면 지시어를 붙이는 것은 그 숫자가 화면마다 다를 수 있다는 뜻이 되므로 금지한다.
- **축 이름 정본 — payDate 축은 '입금일', targetMonth 축은 '귀속월'** (오류신고 8b9b6c43, 2026-08-24).
  - **`납부일` 을 payDate 축에 쓰지 않는다.** 이 앱에서 `납부일` 은 `LeaseTerm.dueDay`, 곧 **매달 며칠**이라는 약정 지급일의 이름이다(설정 '납부일 (매월)' · 입주자·수납 목록의 컬럼·필터·정렬·미납 배지 · 계약서 '매월 납부일'). 그리고 그 약정 지급일이 **귀속월 축의 앵커**다([[cash-receipt-refund]], 소득세법 원칙 — 선납해도 약정 지급일이 속한 달이 귀속월). 즉 `납부일 기준` 은 payDate 축 숫자에 **반대 축의 이름**을 붙이는 말이다.
  - 실제로 그래서 신고가 났다. `/rooms` 상단 현금영수증 합계(payDate 축 7,170,000)와 아래 목록을 손으로 더한 값(귀속월 축 7,640,000)이 갈렸는데, 그 화면에는 값이 dueDay 인 `납부일` 열이 서 있었다. 차액 470,000원은 7/31 에 받은 8월분 한 건이 전부다.
  - `입금일` 이 정본인 근거는 저장소 안에 이미 있다 — `PaymentSummaryCards`(수납 카드 머리 상시 캡션 '… · 입금일 기준'), 발생주의 데이터 진단('실제 입금일'과 '귀속 월'), `PaymentBody`('입금일과 귀속월 모두'), 설정 데이터 점검('입금일(payDate)과 귀속 월(targetMonth)').
  - **축이 갈리는 자리에서는 축 이름을 상시 텍스트로 적는다.** 접힌 InfoHint 안에만 두면 화면은 침묵한 것이나 같다. 소스 가드는 `scripts/verify-money-consistency.mjs` 20번(`<InfoHint` 앞 상시 텍스트 조각만 잘라서 본다 — 파일 전체 검색은 되숨음 회귀에서 통과한다).
  - **미정리 잔재 둘**(범위 밖, 별건). `DashboardClient` '추이' 축 칩이 같은 payDate 축을 `납부일 기준` 이라 부른다. `RoomsClient` 일괄 수납 모달의 라벨 `납부일` 은 실제로 payDate 다(형제 수납 폼들도 같아서 하나만 고치면 케이스 수정이 된다).
- 홈 예상 운영이익 = 예상 수입 − 기록된 지출(`totalExpense`) − 고정 지출 (예정). 마지막 항은 **실제로 뺀 금액**(`expectedExpense − totalExpense`)이지 미기록 고정지출 추정치가 아니다 — 과거월엔 그 추정을 안 빼므로(dashboard/page.tsx `isPastMonth` 분기) 추정치를 적으면 등식이 그만큼 거짓이 된다. 8월 실측: 10,004,801 = 18,452,000 − 2,530,850 − 5,916,349.
- 홈 예상 지출 = 기록된 지출 + 고정 지출 (예정) — 운영이익 등식이 빼는 **같은 두 항**이다. 실측(2026-08-12): 6월 11,391,873 = 11,391,873 + 0 · 7월 12,901,774 = 12,901,774 + 0 · 8월 8,210,934 = 1,489,870 + 6,721,064. 과거월은 둘째 항이 0 이라 등식 줄 자체가 안 뜬다(운영이익 카드와 같은 술어).

### 지출 어휘 정본 — 같은 모집단 같은 이름, 다른 모집단 다른 이름 (2026-08-12 운영자 지시)

같은 화면에서 같은 돈을 다른 말로 부르지 않는다. 지출은 **두 축**으로 쪼갤 수 있고, 축이 다르면 이름도 갈라야 한다.

| 이름 | 모집단 | 쓰는 자리 |
| --- | --- | --- |
| 기록된 지출 | 그 달 Expense 전건(고정 연결분 포함) = `totalExpense` | 홈 세부 재무 요약 타일 · 홈 두 등식 · 결산 보고서 운영이익 정의 |
| 고정 지출 (예정) | 그 달에 아직 기록 안 된 활성 고정지출 추정분(홈은 실제로 더하거나 뺀 차분) | 홈 두 등식 · 지출 관리 요약 |
| 고정 지출 (기록됨) | 활성 고정 규칙 중 이 달 기록된 것의 실액(규칙당 1건) | 지출 관리 요약 |
| 일반 지출 | 비고정 기록분(`!recurringExpenseId`) | 지출 관리 요약·필터 |
| 고정 지출 전체 (정액/변동) | 활성 고정 규칙 **전체**의 추정액(기록 여부 무관) | 홈 예상 지출 카드 범례 |
| 수시 | 예상 지출 − 고정 전체 추정(잔여, 0 클램프) | 홈 예상 지출 카드 범례 |
| 예상 지출 | 기록된 지출 + 고정 지출 (예정) | 홈 카드 제목 · 지출 관리 요약 제목(글자까지 같게) |
| 운영이익 | 실수납+기타수익 − 기록된 지출 = `netProfit` | 홈 세부 재무 요약 타일 · 홈 예상 운영이익 카드 보조줄 · 결산 보고서 |

- **'고정' 앞머리가 같다고 같은 것이 아니다.** 카드 범례의 고정 두 칸은 **전체**, 등식의 '고정 지출 (예정)'은 그중 **미기록분**이다(8월: 7,440,464 대 6,721,064). 그래서 범례에 '전체'를 박았다.
- 폐기 어휘: **순이익·순수익·실지출**. 전부 '운영이익'·'기록된 지출'로 통일했다(2026-08-12 에 '장부 순이익'·AI 프롬프트 '순수익' 마지막 두 자리 제거).
- **동명이의 둘은 남아 있다** — 결산 보고서 '예상 (6개월)' 탭의 '예상 지출'·'예상 운영이익'은 전년 동월/최근 3개월 평균 기반이라 홈과 모집단이 다르다. 이름을 바꾸면 그 화면의 열 헤더·CSV 헤더(운영자 외부 시트)까지 갈리므로 각주에 차이를 적는 것으로 갈랐다.
- 미해결(산식 축, 표시로 못 고침): 홈 예상 지출 카드의 tier 3단은 `!isPending`·`!recordedExpenseId` 필터가 없어 합계가 예상 지출을 넘으면 '수시'가 0 으로 클램프된다(6~8월 실측에서는 미발동). [[open-issues]] 참조.
- `totalExpense`(홈) ≠ 일반 지출 + 고정 지출 (기록됨)(지출 관리)일 수 있다. 한 고정지출 규칙에 한 달 안에 지출이 두 건 기록되면 지출 관리는 규칙당 한 건만 세고 홈은 전부 센다(6월 전기요금 596,410 · 7월 가스요금 182,570 실재). 그래서 캡션에 화면 간 약속을 적지 않는다.
- 감지망: `scripts/verify-money-consistency.mjs` — 원가 직표시 소스 패턴·중복 수납·할인 미반영 락·스트립 RESERVED 혼입을 상시 탐지. test-money 에 락 vs 할인 우선순위·예약 표시 불변식 케이스 고정.

## 2. 돈 저장 피드백 정본

돈이 저장되는 모든 액션(수납·예약금·할인·일할·환불)은 다음을 지킨다.

- (a) 성공 토스트에 **금액과 수납일 명시** — "예약금 50,000원 수납 기록됨 · 수납일 8/17". "수납했습니다"만으로는 실패로 오인된다.
- (b) 결과가 현재 화면 스코프(조회월 등) 밖이면 **어디서 보이는지 사후 안내** — "지금 보는 7월 내역에는 표시되지 않습니다". 사전 확인창 금지, 전부 사후 안내.
- (c) 관련 합계는 저장 직후 **서버 재조회로 갱신**(클라 재계산 금지).
- (d) pending 잠금 + 성공 시 폼 닫기. 재진입 프리필은 **기수납을 차감한 잔여액**으로(전액 프리필은 이중 입력 공범 — 이번 사고의 직접 원인).
- (e) 가능하면 토스트에 적용취소 액션.
- **"저장됐는데 화면이 안 변하는" 상태는 미완성으로 간주한다.**

## 3. 입력 기본값 정본

- 수납일 기본값은 항상 **오늘(받은 날)**. 입주 예정일 파생 금지 — 미래 날짜로 저장되면 월 필터 화면에서 사라져 보인다.
- 중복 수납 서버 가드: 보증금 계열은 기수납 합 ≥ 계약 보증금이면 저장 거부 + 내역 확인 유도.
- **보증금 수납 진입로·기록 규칙은 [[deposit-entry-paths]] 가 정본이다**(2026-08-24 신설). 실입금
  대 소급 기록의 역할 경계, 진입로 셋, 귀속월 규칙(입주월 앵커), 분해 제안·확인형, 승계 계약 게이트가
  거기 모여 있다. 이 문서의 "받은 돈은 조회월과 무관하다"·"재진입 프리필은 잔여액"·"수납일 기본값은
  오늘"이 그 문서의 세 진입로에 그대로 적용된 상태다.
