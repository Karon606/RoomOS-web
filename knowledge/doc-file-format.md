# 저장 서류의 형식과 판본 — 스캔본이 섞이는 세계 (2026-08-26)

긴급 신고(419호 계약서가 깨진 pdf 로 도착)에서 나온 정본. 코드 정본은 `lib/docMime.ts`(형식
판정), `lib/docBundle.ts`(판본 후보), `lib/contractPurpose.ts`(용도·번복).

## 서류는 PDF 만이 아니다

앱이 발급한 계약서·확인서는 전부 PDF 지만, **스캔 업로드본은 JPEG·PNG 일 수 있다.** 저장
바이트를 소비하는 자리가 "서류는 PDF다"를 전제하면 스캔본이 그 자리마다 깨진다. 실제로
여섯 자리가 전부 그랬다 — 메일 첨부, 보기 화면(pdfjs 파싱 실패로 **열리지도 않았다**),
기기 공유 사진 변환, 단건 내보내기, 공유 시트 인쇄, /api/doc-file 응답 헤더.

**판정은 파일 이름이 아니라 바이트다**(`sniffDocMime`). 업로드 파일명은 사용자 입력이라
거짓일 수 있고 확장자가 없을 수도 있다. 이름 기반 추정(`guessDocMimeByName`)은 아직 바이트를
쥐지 않은 자리(메일 초안의 첨부 표기)에서만 쓰고, 실제로 내보내는 순간에는 언제나 스니핑이
최종 권위다. 이름 추정과 실제가 갈리면 실제를 따른다.

**화이트리스트 밖은 전부 `application/octet-stream`이다.** `text/html`·`image/svg+xml` 을 절대
만들지 않는다 — /api/doc-file 이 그 헤더로 바이트를 돌려주면 인라인 렌더에서 스크립트가
실행되는 면이 생긴다(저장 파일은 업로드된 것이라 내용이 신뢰 대상이 아니다). 모르는 형식의
확장자는 `bin` 이다. 가짜 `.pdf` 를 붙이는 것이 이번 사고의 실체였다.

**이 절의 규칙은 전부 '내보낼 때' 의 규칙이다.** 저장된 바이트를 메일·공유·인쇄·응답으로
내보내는 순간 형식을 지어내지 않는다는 뜻이고, 올릴 때의 정규화는 다른 이야기다(다음 절).

내보낼 때 이미지는 변환기(pdfToPng)에 넣지 않는다. 원본 한 장이 이미 최종 형태이고 최대
해상도다. 이미지를 PDF 로 싸지도 않는다 — 없는 종이를 지어내는 일이다.

## 올릴 때는 정규화한다 (2026-09-16 운영자 결정, 위 규칙의 예외)

위 규칙과 **방향이 반대다.** 내보낼 때 형식을 지어내지 않는 이유는 저장된 바이트가 사실이기
때문인데, 올릴 때는 **무엇을 사실로 굳힐지 우리가 고를 수 있다.**

아이폰 사진은 HEIC 다. 그 바이트를 그대로 저장하면 쓰는 자리마다 깨진다 — 사업자등록증은
상담 문자·메일 첨부로 열리지 않는 파일이 되어 나가고, 도장은 pdf-lib 의 embedPng/embedJpg 가
못 읽어 **실거주 확인서 발급이 통째로 실패하며**, 계약서 렌더는 `data:image/heic` 를 크로미움이
못 그려 **도장 없는 계약서가 조용히 나간다.** 서버에서는 못 고친다(sharp 의 libheif 가 AVIF 만
문다, 실측). 브라우저는 HEIC 를 이미 알고 있으므로 **올리기 전에 브라우저에서 바꾼다.**

정본은 `lib/uploadImage` 이고, 무엇이 되느냐로 형식이 갈린다.

- **종이가 되는 것**(사업자등록증·스캔 계약서) = PDF 한 장(`fileToUploadPdf`). 페이지는 언제나
  하나, 용지 비율은 사진 비율 그대로다.
- **그림으로 얹히는 것**(도장·계약서용 로고) = PNG(`fileToUploadImage`). 알파가 정보라 JPEG 로
  바꾸면 도장 배경이 흰 사각형이 되어 서명란을 덮는다. 이미 PNG·JPEG 면 손대지 않는다.

**디코드에 실패하면 던진다.** `lib/ocrImage` 는 실패해도 원본을 그대로 보내는 것이 옳지만
(Gemini 가 HEIC 를 읽는다) 여기는 반대다 — 그 바이트가 **저장**되면 위 세 자리가 다시 깨진다.
조용한 원본 통과는 금지이고 감지망 축 ⓘ 가 그것을 지킨다(`scripts/check-upload-hygiene.mjs`).

서버도 함께 좁혔다. 사업자등록증·스캔 계약서 모두 `application/pdf` + JPEG·PNG 만 받는다
(JPEG·PNG 는 낡은 화면이 남아 있을 때의 안전망이고, **HEIC/HEIF 는 거절된다**). 스캔 계약서는
종전에 **크기만 보고 mime 은 아예 안 봤다** — 그 자리가 이번에 처음 생긴 문이다.

이미 저장된 HEIC 는 코드로 못 고친다(서버에 디코드 수단이 없다). 재업로드 요청이 유일한
길이고, 건수는 `scripts/audit-heic-uploads.ts`(읽기 전용)로 센다.

## 계약서 판본과 대표본

한 계약에 계약서가 여럿 설 수 있다(실계약·스캔본·제출용·번역본). **대표본은 실계약이
고정 대표**이고 파생 판본은 승격하지 않는다([[domain-contracts]] 의 판정 정본). 그 규칙은
옳다 — 근거 없는 표시본이 실계약 자리에 앉으면 안 된다.

없던 것은 **파생 판본을 명시로 골라 보내는 길**이었다. 419호는 스캔본을 지우자 남은 것이
제출용뿐이라 "보낼 계약서가 없다"가 됐다. 서류 보내기 행은 그대로 1개이고, 행에 `versions`
가 얹혀 판본이 둘 이상이거나 대표가 공석일 때만 판본 줄이 선다. **기본 선택은 언제나
대표본** — 아무것도 안 고르면 종전과 같은 종이가 나간다.

선택 키는 `contract:<leaseId>#<contractFileId>` 다. 접미는 **서버가 재조회한 행의 versions
안에서만** 파일로 되바뀐다 — 후보 밖 id 는 거절되므로 임의 ID 를 끼울 자리가 없다는
멀티테넌트 방어가 그대로다. 폐기본은 후보에서 빠지고(효력 없는 종이를 내보내지 않는다),
구버전은 라벨로 말한다. 파생 판본은 파일명에 '계약서(제출용)'처럼 적어 받는 쪽이 실계약으로
오인하지 않게 한다.

## 용도 번복 — 증거와 지위를 가른다

발급 시점 목적(`issuePurpose`)은 **불변 증거**다. 번복은 `purposeOverride` 가 든다.
판정은 `override ?? issuePurpose`(`effectiveIssuePurpose`)이고, **소비처 전수가 이 값을
봐야 한다** — 한쪽만 issuePurpose 를 직접 읽으면 "패널은 실계약이라는데 목록은 아니라는"
상태가 돌아온다. 소비처는 입주자 파일 목록·계약서함·새 버전 게이트·서류 보내기 넷이다.

원 규약("한 번 쓰면 못 고친다")이 막으려던 것은 실계약을 나중에 제출용으로 바꿔 책임을
옮기는 길이다. 그것은 지금도 막힌다.
- 증거가 남고 `purposeLog` 에 이력(from·to·시각·바꾼 사람)이 append 된다.
- **마지막 실계약의 강등은 서버가 거부한다** — 실계약 없이 파생만 남는 상태는 발급 게이트가
  이미 금지하는 것이고, 화면이 그걸 만들게 두면 안 된다.
- 폐기본은 못 바꾼다. 여러 판본 만들기가 꺼진 영업장은 파생 개념 자체가 없어 막힌다.
- 적용취소는 직전 값 복원이라 강등 게이트를 타지 않는다(새 위험을 만들지 않는다).

재발 감지는 `scripts/check-contract-purpose-log.ts`(verify:db) — 현재 값과 이력의 종착지가
갈리면 쓰기 경로가 로그를 놓친 것이다.

## 삭제 복구

계약서 삭제는 소프트삭제(Drive 는 휴지통)이고 **Drive 휴지통은 30일 뒤 영구 삭제**된다.
복구 진입점이 삭제 직후 토스트뿐이면 토스트가 사라진 순간 길이 없어진다(§16 위반). 계약서
파일 칸의 '삭제한 계약서 N부 보기' 접힘 칸이 정식 경로이고, 행마다 남은 복구 기간을 적는다.
