# 공실 집계 정본 (2026-07-21, 신고 9d844226)

공실 수는 화면마다 따로 세지 않는다 — **`lib/vacancy.ts`가 유일한 정의**.

- **집계 제외 방** = 비거주 계약(NON_RESIDENT) 점유 + `Room.nonResidentVacant=false` (창고·사무실). 설정은 호실관리 편집의 "비거주 점유 시 공실 집계에서 제외" 체크박스, 해제하면 즉시 복귀(undo).
- 제외 방은 **공실에도 입실에도 넣지 않는다**. 입실 = 전체 − 공실 − 제외 (운영자 결정 2026-07-21). 입주율 분모도 전체 − 제외.
- 소비처: 대시보드 공실 KPI·입실 현황 카드("집계 제외 N실" 캡션, 0이면 숨김)·호실 현황 도넛·평면 배치도·희망 이동 후보, 리포트 점유율·수익 예측 점유/공실·30일 이상 공실, 호실관리 헤더(상태 필터 칩과 같은 `roomStatusKey` 분기).
- `Room.isVacant`는 여전히 raw 플래그(NON_RESIDENT 비관여, tenants/actions 주석 참조) — 집계 시점에 정본 정의로 걸러서 쓴다. 스키마 무변경.
- 미통일 잔여(운영자 판단 대기): 검색 결과·방 현황 그리드 '공실 (비거주자)' 표기·엑셀 내보내기 공실 열·방 선택 드롭다운의 개별 방 '공실' 표기.

# 희망 매칭 정본 (2026-08-11, 운영자 승인)

"어느 방이 언제 비고, 그 방을 기다리는 사람 중 누가 그 날짜에 맞는가" 는 **`lib/wishMatch.ts` 가 유일한 정의**.
소비처는 홈 매칭 알림(`dashboard/page.tsx`)·홈 연락 알림 뒷문장·고객 목록 제외 사유(`getWishDateNotices`)·
고객 상세 '입주 가능한 방'(`getWishRoomsForLease`)이고, 전부 같은 함수 한 번의 결과를 쓴다.

## 방 축
- 방 축 = **`lib/leaseStatus.roomAvailability`** — 호실 관리 '입주 가능' 칩과 **같은 함수**다(2026-08-11 lib 승격).
  `now`(점유 계약 없음) · `soon(availableFrom = max(퇴실 예정일)+1)` · `null`(하나라도 무기한 → 축에서 뺀다).
- 종전 매칭은 자기 축('isVacant 인 방 + 퇴실 예정 방')을 따로 들고 있었다. 그래서 퇴실일이 잡힌 예약이
  걸린 방(404·409호)을 몰랐고, 뒤에 무기한 예약이 이어 붙은 방(503호)을 빈 방처럼 불렀다. **사본 금지.**
- 비거주(창고·사무실)는 `Room.nonResidentVacant` 를 그대로 따른다(위 공실 집계 정본과 같은 선).

## 날짜 게이트
- **리드 3상태(WAITING_TOUR·TOUR_DONE·RESERVED 미확정)에만** 건다. 거주중 이동 희망은 방을 비우는 약속이
  아니라 메모라 날짜로 자르지 않고, 예약 확정자는 방이 정해져 매칭에서 빠진다.
- 입력은 **`LeaseTerm.moveInFlexible`(Boolean?)** 하나. `true`=조절 가능 · `false`=그 날짜여야 함 · `null`=미확인.
  **null 을 false 로 읽지 않는다** — 안 물어본 사람을 "못 기다린다"고 단정해 후보에서 지우게 된다.
- `wishConditions` JSON 에 넣지 않는다. 거기 값을 하나 더 두면 `hasRealCond`(빈 객체 = 조건 무관 판정)가
  참이 되어, 2026-07-01 에 막은 '아무 방이나' 오탐이 그대로 되돌아온다.
- 판정 넷. `ok`(방이 now 이거나 희망일 ≥ 입주 가능일) · `flexible` · `unconfirmed` · `excluded`.
- **GAP_CAP = 30일.** 희망일보다 방이 30일 넘게 늦게 비면 제외한다. 한 달 넘게 기다리라는 연락은
  매칭이 아니라 다른 방 안내이기 때문이다.

## 사람 축 (전치, 2026-08-11 운영자 승인)
같은 판정을 뒤집어 본 것이다 — "이 사람은 어느 방에 들어갈 수 있는가". `WishMatchResult.leases`.
- **전치일 뿐 두 번째 판정이 아니다.** `buildWishMatch` 가 방별 후보를 세는 그 루프 안에서 같은 후보를
  사람 쪽에 담는다. 새 순회도 새 게이트 호출도 없다. 항등식은 `scripts/test-wish-match.ts` 가 고정한다 —
  방 축을 펼친 `(계약·호실·게이트)` 집합 == 사람 축을 펼친 집합.
- `noDateFitLeaseIds` 는 이 구조에서 파생한다(통과 방 0실 + 제외 1실 이상). 종전 정의와 같은 집합이다.
- 사람 축 안의 방 순서: `ok` 먼저 · 대기 일수 오름차순 · 동률은 호실번호 numeric.
- **DELAY_HINT_DAYS = 7** — 미루기 권고 **문구 등급에만** 쓴다. 후보 집합을 자르는 것은 여전히 GAP_CAP 30일뿐이다.
  발화 조건은 '지금 희망일에 맞는 방 0실 + 최단 대기 7일 이하'. 문장은 `wishGateDetail` 원문에 방 번호만 앞에 붙인다.
- 앞당기기 권고(방이 희망일보다 먼저 비는 경우)는 **넣지 않는다**(운영자 확정).
- 표시는 **고객 상세 한 곳만**이다. 고객 목록 카드에는 캡션을 붙이지 않는다(운영자 확정).
  홈은 알림을 신설하지 않고 기존 '연락할 때'(contact) 알림의 설명문 **뒤에 답 문장을 잇는다** — 앞 문장은 보존한다.

## 제외해도 알린다
운영자 오더 원문: "제외는 하되 notice 는 줘야 돼. 그래야 기다리는 사람에게 방이 없다고 알려줄 수 있으니까."
- 통과 후보가 **0명이어도** 제외자가 있으면 알림이 뜬다("404호 12/21 입주 가능 · 조건 맞는 대기자 없음", 날짜 불가 N명).
- 알림 상세 하단에 제외 수 캡션.
- 희망한 방이 **전부** 날짜에서 빠진 사람은 고객 목록 카드·표에 "현재 희망일에 맞는 방 없음".

## 표시
- 뱃지 신설 없음. 캡션 토큰만 잇는다 — "희망 8/25 · 조건 매칭 · 일정 조절 가능".
- 알림 제목은 날짜로 말한다 — "402호 8/30 입주 가능"(공실이면 "402호 공실").
- 순번은 **통과자만 1..N**. 순서는 날짜 맞는 사람(ok) 먼저, 각 군 안에서 문의 순.

## 이중 부킹 가드 (같은 규칙 한 벌)
겹침은 **구간이 실제로 포개질 때만**이다(날짜 하나만 비교하면 이미 나간 앞 예약까지 걸린다 — 404호 사슬).
- 단기 연장(`extendShortStay`)·편집 폼(`updateTenant`) 둘 다 `nextReservationConflict` 하나를 쓴다.
- 화면이 확인창으로 묻고, 승인 표식(`allowOverlap`·`allowRoomOverlap`)이 있어야 서버가 통과시킨다.
- `updateTenant` 재검증은 방 변경·상태 상승에 더해 **같은 방 퇴실 예정일 연장**에도 발화한다.
- 겹침 문구는 실제로 앞을 막고 선 계약을 지목한다(방의 마지막 퇴실일이 아니다).

## 겹침 판정 3층 (운영자 확정 2026-08-19)
겹침을 한 덩어리로 다루던 것을 셋으로 나눈다. 정본은 전부 `lib/roomAssignment.ts`다.
- **층 0 — 겹침의 정의**: `occupancyOverlaps`. 같은 날도 겹침으로 센다. 이 `>=` 는 **고치지 않는다**
  (소비처가 가져오기·캘린더·감지망·화면 넷이라 정의를 옮기면 전부가 함께 흔들린다).
- **층 1 — 당일 회전은 정상**: `isSameDayTurnover`. 앞 계약 퇴실일 == 뒤 계약 입주일이고 겹침이 그
  하루뿐이면 정상 운영이다. 같은 날 **함께 시작하는** 둘은 회전이 아니다(앞의 입주일이 그 하루보다
  앞서야 한다). 가져오기 통과·캘린더 충돌 아님·감지망 축 ② 제외·입주자 폼은 확인창 대신 중립 캡션.
- **층 2 — 하루 이상 겹침은 확인을 데이터로**: `LeaseOverlapAck` 한 행이 '누가 어느 구간을 의도된
  겹침으로 확인했다'를 진다. 유효 판정은 `findOverlapAck` — **지금 겹침 구간이 확인 구간 안**일 때만
  유효하다. 하루라도 벗어나면 자동 실효돼 다시 발화한다. 무기한 겹침은 스냅샷이 없어 확인 대상이 아니다.
  해제는 소프트삭제, 재확인은 새 행([[soft-delete-pattern]]).
- 기록 경로 셋: 예약 확정 확인창 승인 · 퇴실일 연장 확인창 승인(둘 다 `allowRoomOverlap` 표식 →
  `lib/overlapAck` 이 저장 후의 사실을 다시 읽어 적는다) · 캘린더 충돌 요약의 [겹침 확인].
- 확인 대상이 아닌 충돌: `indefinite`(퇴실일을 넣으라는 다른 처방) · `reversed`(데이터 사고).
- 표시: 확인 전 빨강, 확인 후 중립. **줄은 지우지 않는다** — 해제 진입점이자 한 방에 두 사람이
  있다는 사실 표시다.
- 가드는 그대로다. 서버 저장은 막지 않고, 가져오기는 하루 이상 겹침을 계속 차단한다(시트에는 물을 자리가 없다).
