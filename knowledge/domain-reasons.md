# 사유 목록(입실 취소·퇴실·보증금 미반환)과 '기타' 저장 규약

2026-10-22 운영자 승인("입실취소 사유를 추가하는게 환경설정에 있어?" 이어서 "'기타'를 넣고 이 사유를 목록에 추가하는 기능을 다 넣고 … 삭제 수정 등은 설정에서"). 관련: [[domain-checkout-settlement]] · [[domain-cleaning]] · [[domain-auto-checkout]] · [[decisions]]

## 무엇이 참인가
- **목록은 영업장 설정이다.** `Property.cancelReasons`·`checkoutReasons`·`withholdReasons`(콤마 칸, null = 코드 기본값). 기본값은 `lib/optionLists` `OPTION_LIST_DEFAULTS` 한 벌이고 종전 코드 상수에서 '기타'만 뺀 것이다(백필 없음, 기존 영업장은 목록이 한 글자도 안 바뀐다). 환경설정 > 분류 관리의 할인 사유 카드 옆 세 장(OptionSection 정본, 삭제·초기화·이름 변경 적용취소)에서 고친다.
- **'기타'는 목록 항목이 아니다.** 고르는 칸(CategorySelect `addMode="ask"`) 맨 끝에 늘 붙는다. '기타'·'기타 · …'·시스템 라벨은 목록에 못 넣는다(`reservedOptionNameError`, 손 추가·이름 변경·자동 추가가 같은 문).
- **저장 규약(정본 `lib/reasonLists`).** 기타에 적은 글은 `'기타 · 글'`(글이 없으면 `'기타'`). '이 사유를 목록에 추가'(기본 꺼짐)를 체크하면 그 글이 목록 끝에 들어가고 기록은 맨 글자로 남는다. 서버(`lib/reasonListSave` `reasonForSave`)는 화면을 믿지 않는다. 목록(과 보호 이름)에 없는 맨 글자는 `'기타 · 글'` 로 바꿔 남기고, 고치는 기록의 지금 값과 같으면 그대로 둔다(목록에서 뺀 항목·옛 이름 '키값'). 목록 추가는 기록이 선 뒤(commit)이고 영업장 행을 잠그고(FOR UPDATE) 붙인다(검수 N4). 순서 저장·삭제 적용취소·초기화 적용취소·이름 변경 적용취소 입구도 '기타'·시스템 라벨을 막고(이름 변경 적용취소는 옛 이름과 새 이름 둘 다 본다. 새 이름에 시스템 라벨이나 청소 코드를 넣은 위조 표가 그 행을 글자로 바꾸던 길, 2차 검수 B1), 사유 목록 순서 저장은 지금 목록과 같은 이름 집합만 받는다(검수 N2).
- **수정 화면 해석**(`reasonPickOf`). 목록에 있으면 그 항목, `'기타 · '` 로 시작하면 기타 + 글, 둘 다 아니면 저장 글자 그대로 한 줄 세워 손대지 않으면 그대로 저장된다. 상태 이력 사유 적용취소는 서버가 서명한 토큰(`undoStatusLogReason`, 이전 값·바꾼 값 서명, 지금 값이 바꾼 값일 때만)으로 이전 글자 그대로 되돌린다(독립 검수 N1).
- **이미 쌓인 `'기타 · 공실 없음'` 류는 손대지 않는다**(결정 4). 운영 DB 2026-10-22: 취소 '기타' 7건 중 6건이 공실 없음 갈래, 퇴실 '기타 · 친구와 동반거주' 2건, DepositRefund '키값' 4건.
- **보호 이름**: 미반환 '청소비'(퇴실 정산이 몰취를 청소비와 나누고 청소비 잔고를 센다)·'인수 승계 보증금'(인수 전 입주자 퇴실에서 앱이 미리 고른다)은 이름을 못 바꾼다. 목록에서 빼도 서버가 그 글자를 그대로 받는다(보호 이름은 '알려진 이름').
- **이름 변경이 따라가는 기록**: 취소·퇴실 사유는 `TenantStatusLog.reason` 을 영업장(`propertyId` 칸이 있다)과 `toStatus`(취소 CANCELLED / 퇴실 CHECKOUT_PENDING·CHECKED_OUT)로 나눠 바꾼다. 같은 글자의 다른 사유·`'기타 · 글'`·남의 영업장은 안 바뀐다. 무효 처리 행도 그때의 표기라 함께 바뀐다. 퇴실 예정 '그날 바꾸기' 로 남는 거주중 그대로 행(ACTIVE → ACTIVE + 퇴실 사유)도 퇴실 사유 이름 변경이 따라간다(`REASON_FIELD_SELF_STATUSES`, 검수 N3). 미반환은 `DepositRefund.reason` 만 바꾸고 `ExtraIncome.detail` 문장은 그때의 기록이라 안 바꾼다. 적용취소는 바뀐 행 id.
- **퇴실 사유 이어받기**(`lib/checkoutReason`)는 '시스템 라벨이 아닌가'로 본다. 시스템 라벨 전수는 `lib/statusReasons` `SYSTEM_STATUS_REASONS`(단기 자동 전환·퇴실 한 달 전 자동 전환·자동 전환 되돌림·단기 연장·퇴실 적용취소·단기 연장/감액 적용취소)이고 상태 이력 쓰기는 이 상수만 쓴다(글자를 바로 적으면 `scripts/test-reason-lists` 가 붉게 선다). 운영 퇴실 예정 사유 전부에서 종전 판정과 답이 같다. 퇴실 예정에서 퇴실로 갈 때 이어받은 사유는 그 계약의 지금 값이라 목록에서 뺐어도 그대로 남는다(검수 R1, 상태 전환·입주자 수정이 `latestCheckoutReasonFor` 를 prev 로 넘긴다).
- **저절로 쌓던 목록(할인 사유·직업·지출 카테고리 두 폼·요청 카테고리)도 같은 체크박스**(`addMode="auto"`, 기본 켜짐, 결정 2). 끄면 목록에 안 넣고 값은 적은 글자 그대로다. 이 칸들은 원래 목록 밖 글자(뺀 카테고리)를 맨 글자로 두는 칸이라 `'기타 · '` 꼴로 바꾸지 않는다. 단위·쇼핑몰·수행자는 종전 그대로(체크박스 없음). 힌트는 한 문장 '목록은 환경설정 > 분류 관리에서 고칩니다.' 다. 요청 카테고리 기본값에서 '기타' 를 뺐다('기타(직접 입력)' 과 두 줄). 목록을 저장해 둔 영업장(운영 영업장은 '기타' 포함)은 그대로이고 '기타' 요청 기록은 운영 0건(2026-10-22).

## 사유 고르는 자리(전부 `addMode="ask"`)
입실 취소·퇴실: 상태 전환 미니폼(TenantStatusTransitions)·입주자 수정 폼 상태 칸(TenantClient, FormData `cancelReason`·`cancelReasonAddToList`)·상태 이력 사유 수정(TenantStatusHistory). 미반환: 미니폼·입주자 환불창(TenantClient)·홈 퇴실 정산(DashboardClient)·보증금 패널 기록 폼(DepositStatusPanel, 힌트 `hintTone="mid"`, --cream-soft 위 --warm-muted 는 다크 4.46:1). 새 자리는 `scripts/check-option-lists` ⓛ ASK_SITES 에 적는다.

## 2차 목록 여섯과 저절로 쌓는 목록의 남은 자리(2026-10-22, 2차 패널 '추천대로')
원칙은 하나다. **ask** = 뜻을 모아 세는 사유·출처·경로('기타 · 글' 저장, '목록에 추가' 체크 기본 꺼짐). **auto** = 이름 자체가 값인 카테고리·종류(맨 글자 저장, 체크 기본 켜짐).
- **칸 여섯**(`Property.dueDayReasons`·`cleaningReasons`·`stockDisposalReasons`·`stockSourceOptions`·`assetDisposalReasons`·`visitRouteOptions`, null = 기본값, 백필 없음, 운영 적용은 `prisma/migrate_reason_lists_2.sql` 먼저). 전부 `REASON_LIST_FIELDS`(ask). 기본값: 납부일 임시 조정 사유·청소 사유는 빈 목록, 소모품 폐기 '상함·부패, 유통기한 경과, 파손', 무상 입수 '무상, 기증, 이월', 비품 폐기 '시공 중 철거, 파손, 분실, 노후·고장으로 교체', 방문 경로 '인터넷 검색, 지도 앱, 지인 소개, 간판, 직접 방문'. 종전 소모품 폐기 저장 글자 '유통기한' 은 이제 '유통기한 경과' 로 선다(운영 폐기 0건).
- **저장 검증은 칸 이름으로 한 벌**: `reasonForSave(propertyId, field, raw, { addToList, prev })`(`REASON_LIST_SELECT`), 목록 추가는 `appendOptionName`(행 잠금). 시스템 라벨 금지는 사유 셋(1차)에서만 본다.
- **이름 변경이 따라가는 기록**: 납부일 임시 조정 `LeaseTerm.overrideDueDayReason`·방문 경로 `LeaseTerm.visitRoute`·청소 `RoomCleaning.reason`·비품 `Expense.disposalReason`, 재고 둘(`StockDisposal.reason`·`StockAddition.source`)은 propertyId 가 없어 `via: 'trackedItem'`(추적 품목으로 영업장). 메모 칸은 사유 규약 밖이다(메모 그대로).
- **청소 사유**: 코드 셋 `CLEANING_REASON_CODES`(CHECKOUT 퇴실 청소·AFTER_WORK 공사·도배 후·DURING_STAY 입실 중 요청)은 고르는 칸 맨 앞 고정(`FIXED_OPTION_VALUES`), 그 뒤 영업장 목록, 맨 끝 '기타(직접 입력)'. 저장은 코드 또는 글자, 옛 'OTHER' 는 이행 없이 '기타' 로 보인다(`LEGACY_FIXED_VALUES` 로 서버가 받기만 한다). 화면 글자는 `cleaningReasonLabel` 한 벌(목록 행·사유 변경 칸·캘린더 '…청소'·토스트 '사유를 바꿨습니다 · A → B'). 목록에 못 넣는 이름: 영문 대문자 코드 꼴, 공백을 걷고 대소문자를 무시해 코드(OTHER 포함)나 고정 라벨 셋과 같은 이름('퇴실청소'·'checkout', 2차 검수 R1). 직접 입력 글은 코드와 견주지 않는다('기타 · CHECKOUT' 은 퇴실 청소가 아니다). 받은 청소비 부담·자동 퇴실 청소의 'CHECKOUT' 판정 줄은 한 글자도 안 바뀌었다(통합 하네스: 부담은 CHECKOUT 에만). 사유 칩(코랄 채움, §03 위반)은 select 로 바꿨다. `createCleaning` 에 서버 검증이 생겼다(종전에는 화면 글자를 그대로 적었다).
- **납부일 임시 조정**: 고르는 자리 둘(수납 정보 위젯·입주자 상세). `setDueDayOverride`·`clearDueDayOverride` 는 계약을 영업장 범위로 먼저 읽는다(운영자 승인 별건 권한, `check-action-property-scope`). 저장 글자를 돌려준다. 위젯 힌트는 `hintTone="mid"`(바탕 --warning-bg 에서 --warm-muted 다크 3.84:1).
- **재고·비품**: 소모품 폐기·무상 입수(등록과 수정이 같은 칸, 수정은 prev 로 옛 자유 입력 '522호 이경호님' 을 그대로 둔다)·비품 폐기·교체(같은 목록, 교체 칸은 `CategorySelect groupLabel` 로 묶음). 비품 폐기 적용취소는 스냅샷의 `disposalReason` 까지 돌린다(전량 폐기 + 그사이 이름 변경 뒤 적용취소 바이트 동일, 통합 하네스). CAS 는 사유를 안 본다(폐기 전 사유로 돌리는 것이라 이름 변경과 다투지 않는다).
- **방문 경로**: 입주자 등록·계약 추가·수정 모두 `visitRouteForSave`(tenants/actions). 옛 자유 입력 경로는 그 글자 그대로 한 줄 선다.
- **auto 새 자리**: 작업 종류(`createRoomWork`, 맨 글자, 지출 품목 글자 맞춤 lib/roomWorkMatch 와 같은 글자)·부가수익 카테고리 등록·수정(체크 칸이 실린 저장 '1' 만 더한다. 수납 과납분처럼 칸 없는 저장은 종전대로 안 쌓는다. 수정 폼은 목록 밖 값('청소비' 가 목록에 없는 영업장)을 첫 항목으로 바꾸던 잠복 버그가 봉합됐다)·지출 카테고리 남은 넷(고정 지출 두 폼·일괄 수정·홈 승인. 홈 승인은 인식이 뽑은 카테고리 그대로면 체크 칸이 안 서고 서버도 안 더한다). 헬퍼는 `autoOptionForSave`(지금 값과 같으면 안 더함, 지금 값도 `normalizeCategoryInput` 을 거쳐 견준다, 2차 검수 D5). 홈 승인의 재고 보충(품목 있음)은 카테고리를 목록에 안 쌓는다(통합 하네스 장면). 부가수익 기본값에서 '기타' 를 뺐다(목록을 저장한 운영 영업장은 그대로).
- **분류 관리 묶음 머리 다섯**(호실 · 입주자 · 돈 · 청소·작업 · 재고·비품, 카드 스물셋, 가이드 §22). 기본값 없는 두 카드(납부일 임시 조정 사유·청소 사유)는 쇼핑몰처럼 초기화가 없다. 탭 맨 위에 묶음 바로가기 줄이 있다(2026-10-23 운영자 결정. 줄 앞 캡션 '바로가기' 가 이동이라는 단서다(필터로 읽히지 않게). 정본 `OptionGroupNav.tsx` 의 `OPTION_GROUPS` 한 벌이 머리 글자·id·버튼 라벨을 낸다. 누르면 머리로 스크롤하고 머리에 포커스, 이동뿐이라 적용취소 없음, 감지망 `check-option-group-jump`).
- **사유 칸 접근 이름·커서**(2차 독립 검수): CategorySelect `id`·`ariaLabel` 은 고르는 칸과 직접 입력 칸 중 지금 선 쪽이 받는다. 보이는 라벨이 있으면 `<label htmlFor>`(청소 예정 사유·작업 종류·방문 경로·비품 교체·폐기 질문·소모품 폐기 사유·무상 입수 등록 출처), 라벨 글자가 없는 조밀한 자리와 납부일 사유는 `ariaLabel`('청소 사유'·'작업 종류'·'납부일 조정 사유'·'출처'). 커서는 '기타(직접 입력)' 을 방금 골랐을 때만 간다(ask·auto 같은 규칙, 목록 밖 값으로 연 수정 폼은 키보드를 안 띄운다). 목록 첫 항목을 기본으로 세우는 등록 폼(소모품 폐기·무상 입수)은 목록을 읽는 동안 칸과 저장을 잠근다(`useReasonOptionList`). 청소 사유 변경은 보이는 사유가 그대로면 저장 대신 닫는다.
- 체크박스 문구: 사유 '이 사유를 목록에 추가'·출처 '이 출처를 목록에 추가'·경로 '이 경로를 목록에 추가'·종류 '이 종류를 목록에 추가'·카테고리 '이 카테고리를 목록에 추가'.
- 운영 DB 읽기(2026-10-22): 임시 조정 사유 18건 열 갈래('급여'·'급여지연' 따위)는 목록이 비어 전부 옛 글자 한 줄로 서고 그대로 저장된다. 청소 CHECKOUT 24·AFTER_WORK 5·DURING_STAY 1·OTHER 1('기타' 로 보임). 무상 입수 '무상' 11·'기증' 1·'522호 이경호님' 1. 방문 경로 17건 중 '직접 방문' 1건만 목록 이름이고 나머지는 옛 글자 그대로.

## 투어일 비움 기록(2026-10-23, 운영자 승인 '추천대로' (가)안)
'문의'로 바꿔 저장하면 투어일·투어 시각이 지워지는데 기록이 어디에도 안 남았다(운영 DB 입실 취소 49건 중 18건이 투어일 보유). 정본은 `lib/tourClearLog`.
- **비우는 저장만** 남긴다. 폼 투어일 값이 `''`(칸이 있고 비웠다)이고 지금 값이 있을 때. 칸이 없는 저장(null)·새 날짜·같은 날짜는 남기지 않는다. 시각만 비우는 저장도 대상이 아니다.
- **범위**: '문의' 저장뿐 아니라 예약·투어 완료·입실 취소 상태에서 투어 날짜 칸을 손으로 비운 저장도 같은 기록을 남긴다(그 상태 그대로면 같은 상태 행).
- **글자**: `TenantStatusLog.memo` 에 `투어일 2026-09-28 비움`, 시각이 있으면 `투어일 2026-09-28 14:00 비움`(저장은 날짜 꼴, 내보내기에서 날짜로 읽힌다). `reason` 은 비운다. 사유가 아니라 기록이라 이어받기(`lib/checkoutReason`)·이름 변경·사유 수정(같은 상태 행은 거부)·종료 사유 표시가 이 행을 사유로 읽지 않는다. 시스템 라벨 집합에도 안 넣는다.
- **행 수**: 상태가 함께 바뀌면 그 전이 행 하나에 memo 를 싣는다(행 둘 금지). 상태가 그대로면 `fromStatus = toStatus` 행을 하나 만든다(`createTourClearedLog`, changedById 는 저장한 사람). 두 행 모두 계약 저장과 같은 트랜잭션에서 쓴다(독립 검수 2). 사유 재기는 그 앞, 사유 목록 추가는 그 뒤다. 운영 DB 의 같은 상태 행(투어 예정 52·예약 24 등)은 전부 등록 행(changedById 없음)이고 memo 는 0건이었다(2026-10-23).
- **쓰기 자리**: 투어일을 쓰는 곳은 새 계약 폼 읽기(`readLeaseFields`, addTenant·addLeaseToTenant, 만들 뿐 비우지 않는다)와 입주자 수정(`updateTenant`)뿐이다. 상태 전환 미니폼·일괄 수정·가져오기는 투어일을 안 쓴다. 영업장 범위·`requireEdit` 는 updateTenant 의 것을 그대로 쓴다.
- **화면**(TenantStatusHistory): 메모 줄은 어느 행이든 사유 줄 아래 같은 문법(10.5px `--warm-muted`)으로 `비운 투어일 2026.09.28 14:00`. 투어일을 비우고 투어 예정에 닿은 행은 도착 이름을 '문의'로 쓴다(`입실 취소에서 문의로`, 투어 예정 그대로면 `투어 예정에서 문의로`. '투어 예정으로' 아래 '비운 투어일' 은 모순, 독립 검수 1). 예약·투어 완료·입실 취소 그대로 비운 행의 제목은 `투어일 비움`(제목에 값을 넣으면 320px · 125% 에서 말줄임으로 잘렸다). 날짜는 목록 표기(점)로 바꿔 보인다. 무효 처리·적용취소는 다른 행과 같다.
- **오인 봉합**: 입실 취소 그대로 투어일만 비운 행(CANCELLED → CANCELLED)이 '최근 취소 행'으로 잡히면 취소 단계(투어 전 취소 따위)가 사라진다. 입주자 목록 조회(`getTenants` statusLogs)와 투어 캘린더 피드는 `fromStatus: { not: 'CANCELLED' }` 로 전이 행만 본다(종전 등록 행 4건도 같이 걸러진다, 피드 판정은 null 과 'CANCELLED' 가 같은 답이라 표시 변화 없음).
- 그물: `scripts/check-tour-clear-log.mjs`(쓰기 배선·입주자 수정·화면·오인 방지) · `scripts/test-tour-clear-log.ts`(진리표) · `scripts/test-reason-lists-flow.ts` 장면 14(PGlite, 문의 저장 → 같은 상태 행 memo, 상태 동반은 행 하나, 새 날짜·칸 없는 저장은 행 없음, 남의 영업장 거부, 이름 변경·무효 처리 뒤 memo 그대로).

## 알려진 공백
- 상태 전환·입주자 수정 경로의 통합 하네스는 사유 전용 관문 대역(uuid 사용자)으로 돈다(2차에서 입주자 수정의 방문 경로까지 돈다).
- 입주자 폼 '입실 문의 시각' 시각 칸(w-28)이 320·360px x 글자 125% 에서 줄 밖으로 넘친다(2차 하네스가 찾은 종전 문제, 이번 범위 밖).
- `updateExtraIncome`·`updateRecurringExpense` 는 쓰기를 id 만으로 한다(권한-영업장범위 감사 클래스). 2차는 지금 값을 영업장 범위로 읽기만 더했다. 막는 것은 운영자 결정 대기다.
- (해소 2026-10-23) 분류 관리 탭 길찾기. 운영자가 묶음 바로가기 줄을 골랐다(가이드 §22). 머리 고정·접기는 두지 않는다.
- 청소·작업 담당 칩은 아직 코랄 채움이다(§03, 사유 칩만 select 로 바꿨다).
