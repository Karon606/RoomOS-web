# 방 점검 · 퇴실 점검, 청소 검수, 입실 전 점검 (2026-10-27, 신고 2911c217)

신고 원문 요지: 퇴실 날짜·퇴실 후·입실 전에 확인할 것(파손, 비품 유무, 청소 상태, 외부 신발장)을 때맞춰 띄워 달라.
519호 입실 고객이 청소가 덜 됐고 신발장에 남의 신발이 있다고 항의했다. 목록은 환경설정에서 고칠 수 있어야 한다.

## 왜 생겼나 (구조적 원인)
1. 청소 완료(RoomCleaning)가 완료일·수행자·비용만 받는 사건으로 끝났다. 결과를 확인할 자리가 없었다.
2. 입실 처리가 방 준비 상태를 안 봤다.
3. 기존 체크리스트(Checklist)는 영업장 단위·주기 반복이라 방·단계에 못 묶는다. 다른 축이라 손대지 않았다
   (getDueChecklists 호출처 0 은 별건).

## 무엇이 참인가
- **표 둘.** `RoomInspection`(방·단계·상태·예정일·완료일) + `RoomInspectionItem`(항목 한 줄: 이름·출처·결과·확인 시각·메모).
  항목은 Json 이 아니라 표다. 항목마다 즉시 저장이 한 줄 단위이기 때문이다. 마이그레이션 `prisma/migrate_room_inspection.sql`.
- **단계 셋**(라벨 정본 `app/(app)/room-manage/inspectionConstants.ts`): `CHECKOUT` 퇴실 점검 · `AFTER_CLEANING` 청소 검수 · `BEFORE_MOVEIN` 입실 전 점검.
- **상태 셋**: 예정 · 완료 · 안 함. **검수 미통과는 넷째 상태가 아니다.** 문제(NG) 항목 수에서 파생한다('미통과 N항목'). 뒤 행동은 기존 청소 재등록.
- **항목 판정 셋 + 미확인**: 확인 · 문제(메모) · 해당 없음. 진행 표기는 정본 `inspectionProgressText` 하나 '점검 N/M' 이고 N 은 판정을 마친 항목 수다.
  상자가 판정 셋을 모두 보이므로(확인 코랄 체크, 문제 warning 틴트 가로줄, 해당 없음 중립 틴트 가로줄) N 이 채워진 상자 수와 같다.
- 확인 시각(checkedAt)은 누른 시각이라 로그다. 점검이 일어난 날은 완료일(doneDate)이 따로 묻는다
  (lib/completionDate, 화면 maxDate + 서버 assertNotFuture 두 겹. check-completion-date-axis 에 ALLOW·SERVER·GUARD·SCREENS 등재).
- **끝낸 점검의 항목은 못 고친다.** 완료·안 함을 먼저 적용취소해야 한다(INSPECTION_LOCKED).
- 같은 방·같은 단계에 **예정 점검은 하나뿐**이다. 손수 등록·안 함/완료 적용취소·삭제 복원이 모두 같은 판정으로 막는다(정본 문형 안내).

## 언제 생기고 언제 걷히나 (정본 `lib/roomInspectionEnsure.ts`, 화면이 못 부른다)
- 퇴실 처리: 퇴실 점검(예정일 = 퇴실일) + 입실 전 점검(예정일 없음). 자리는 퇴실 부수 처리 정본 `applyCheckoutSideEffects` 한 곳이라 퇴실 경로 셋이 다 지난다.
  퇴실 예정 전환 때는 안 만든다.
- 청소 완료: 청소 검수(그 청소에 묶임, 예정일 = 청소 완료일).
- 만들 때 차례: ① 그 방에 같은 단계의 열린(예정) 점검이 있으면 건너뜀 ② 같은 퇴실·같은 청소로 만든 점검이 살아 있으면(완료 포함) 건너뜀
  ③ 무른 처리로 걷힌(소프트삭제된 예정) 점검이 있으면 되살림(체크 그대로) ④ 없으면 새로 만듦.
- 퇴실을 무르는 **모든** 경로(상태 위젯 퇴실 적용취소, 수정 폼에서 퇴실을 다른 상태로 바꾸는 저장): 그 퇴실의 **예정** 점검만 소프트삭제하고 자동 퇴실 청소도 함께 걷는다.
  끝낸 점검은 사실이라 남긴다(2026-10-27 독립 검수 R3, 종전에는 수정 폼이 청소 예정도 안 걷었다).
- 청소 완료 적용취소, 청소 삭제: 그 청소의 예정 검수만 소프트삭제. 다시 완료하거나 삭제를 적용취소하면 되살린다(삭제 적용취소는 되살리기만, 옛 청소의 검수를 새로 안 만든다).
- **입실을 만드는 모든 경로**는 그 방(일정이 있으면 오늘 들어가는 방)의 열린 입실 전 점검을 **'안 함'으로 닫는다**(운영자 결정 ③).
  입실 판정 정본은 `isMoveInTransition(이전, 다음)` 하나다. 다음 상태가 거주중이고 이전 상태가 거주(거주중·퇴실 예정)가 아니면 입실이고, 계약 생성은 이전이 없다(null).
  그래서 예약뿐 아니라 투어·입실 취소·비거주·퇴실 완료에서 거주중으로 가는 전이, 거주중으로 바로 등록(addTenant·addLeaseToTenant), 일괄 편집 상태 변경, 엑셀 가져오기가 모두 입실이다.
  퇴실 예정에서 거주중으로 돌아오는 것(퇴실 예정 취소·자동 전환 되돌리기)은 계속 사는 것이라 입실이 아니다. tenants/actions 의 도움 함수 `moveInInspectionOnTransition` 이 모든 상태 쓰기에서 이 판정을 부른다.
  **방 이동**(일정 이사 advanceRoomSchedule, 수정 폼에서 거주 중 호실을 바꾼 저장)도 옮겨 들어가는 방의 입실이라 같은 방식으로 닫는다.
  판정은 그대로 남고, 둘째 줄(토스트 detail)이 '입실 전 점검 N항목이 남은 채 닫혔습니다' 를 말한다.
  누가 닫았는지는 doneBy 로그 칸에 표식으로 남긴다(moveInClosedMarker, 스키마 주석에 적었다). 입실이 닫으면 `auto-movein:<계약 id>`, 방 이동이 닫으면 `auto-move:<계약 id>` 다.
  그래서 입실을 무를 때 그 뒤 일정 이사로 닫은 다른 방 점검은 안 열린다(2026-10-27 재확인 차단 2). 닫기·되열기는 조건부 쓰기다(닫기는 예정일 때만, 되열기는 그 표식이 있는 안 함일 때만).
  **닫는 경로마다 짝인 적용취소가 되연다**: 상태 위젯·수정 폼(입실 되돌리기 판정 isMoveInUndoTransition, 거주중에서 예약·투어·입실 취소로), 홈 알림 입실·moveInTenant(상태 위젯 입실 적용취소),
  호실 일정 입실(undoRoomSchedule, 입주자 화면 '입실 처리를 적용취소'), 일정 이사(undoRoomMove, 이사 표식 중 옮겨 들어갔던 방 하나만), 일괄 편집(undoBatchUpdateTenants).
  되돌리기 판정은 입실 판정의 정확한 역(`undoesMoveIn(지금, 복원)` = `isMoveInTransition(복원, 지금)`)에서 나온다. 되돌림이 확실한 일괄 수정 적용취소는 이 역을 그대로 써서
  비거주·퇴실 완료에서 들어온 입실도 되연다. 상태 위젯·수정 폼·일괄 편집 저장은 되돌림인지 진짜 전이인지 몰라 그 역 가운데 입주 전 단계로 가는 것만 본다(진짜 퇴실·비거주 전환은 안 연다).
  계약 생성·엑셀 가져오기는 적용취소가 없다(계약 삭제로 정리). 수정 폼에서 거주 중 호실을 바꾼 저장도 짝이 없다(운영자 확인 2026-10-27). 다시 저장해도 자동으로 안 열리니 방 모달 작업 이력에서 '안 함' 을 적용취소한다.
  손으로 '안 하기로' 한 점검·다른 계약이 닫은 점검은 안 열리고, 같은 방에 다른 예정 점검이 있으면 안 연다.
- 실패해도 던지지 않는다. 퇴실·청소·입실은 이미 끝났다. 안내 끝에 "…을 만들지 못했습니다" 한 줄.

## 항목은 스냅샷이다
- 영업장 목록 넷(`Property.checkoutInspectionItems`·`cleaningInspectionItems`·`moveinInspectionItems`·`inspectionExcludedItems`, 분류 관리 '청소·작업' 묶음 카드)
  을 만들 때 베낀다. **목록 이름을 바꿔도 이미 만든 항목은 안 바뀐다**(RENAME_CASCADE 빈 표). 기본값은 `lib/optionLists OPTION_LIST_DEFAULTS`(멀티테넌트 중립어).
- **퇴실 점검에만** 그 방 비품 품명을 더한다(순수 함수 `lib/roomInspectionSeed`). 규칙: 그 영업장·그 방 지출 행 중 받았고(receivedAt) 폐기 안 했고
  배송비 줄 아니고 재고 제외 아니고 품명 있고 추적 카테고리(소모품) 아니고 **방 작업(도배·장판)에 묶인 시공 자재(roomWorkId)가 아님**(운영자 결정 ②).
  '점검 제외 품목' 목록은 뺀다. 같은 품명은 한 줄. 만든 뒤 폐기해도 항목 이름은 남는다.
- 손수 더하기(공유기·셋탑)와 행 빼기는 그 점검에만. '항목 편집'을 켜야 선다.

## 조작의 무게 (운영자 결정 ④, 독립 검수 R1)
- 판정 토글(확인·문제·해당 없음)은 토스트가 없다. 바로 저장하고, 같은 자리를 다시 누르면 미확인으로 돌아가는 것이 적용취소다.
  잠금은 저장 중인 그 항목 하나라 연달아 누를 수 있고, 화면 전체를 다시 그리지 않는다(항목 쓰기 서버 액션은 revalidatePath 를 안 부른다).
  항목을 바꿨으면 행을 접을 때·화면이 사라질 때(방 모달 닫기·탭 전환) 한 번 맞춘다(방 모달은 router.refresh 로 호실 카드까지).
- '문제' 는 메모 칸을 먼저 열고 저장 한 번에 문제 + 메모를 남긴다. 취소는 무변경이다. 메모는 문제일 때만 보이고, 문제를 끄면 저장된 채 숨고 다시 켜면 돌아온다.
  이미 적힌 메모를 고치면 옛 글이 사라지므로 토스트 [적용취소] 가 옛 글을 되살린다.
- 문제·해당 없음 칸은 형제 '긴급만' 필터 칩 문법의 토글 칩이다(켜짐 = 의미색 트라이어드, 문제 = warning · 해당 없음 = neutral). 같은 판정을 배지로 또 말하지 않는다.
  '문제' 의 색 뜻은 warning 하나다(상자·칩·미통과 캡션). 행 여닫기 이름은 '항목 펼치기 / 항목 접기'.
- 점검 완료·안 함·삭제·복원·항목 삭제·손수 더하기는 토스트 [적용취소] 가 있다. 점검 상태 쓰기만 화면을 다시 읽는다.

## 화면
- 행 정본 `components/inspection/InspectionRowBody.tsx`(형제 청소 행 문법), 등록 `InspectionPlanForm.tsx`(빈 방용 손수 등록, 단계 기본값 입실 전 점검).
- 호실 관리 '작업' 탭: 같은 목록·같은 세그먼트, 탭 접미 N 에 예정 점검 포함. 손수 등록은 **방 모달(호실 상세) 작업 이력에만**(운영자 결정 ①, 목록 헤더 CTA 는 종전 둘).
- 방 모달 작업 이력: 셋째 종류, '점검 등록', 삭제분 보기에 포함.
- 호실 카드: 배지는 늘리지 않는다. 두 배지의 보조줄 문법이 같다('10.28(화) 예정 · 점검 2/7'). 청소가 남았으면 '청소 필요', 청소 없이 점검만 남았으면 같은 자리에 '점검 남음'.
- 입주자 상태 위젯 '입실 처리' 앞 WhyCaption: 입실 전 점검 진행과 '입실 처리하면 안 함으로 닫힙니다' + '점검 열기'.
- 홈 퇴실 처리 토스트 '퇴실 점검 N항목이 준비됐습니다 · 열기', 청소 완료 뒤 '청소 검수 N항목이 준비됐습니다 · 열기'.
- 체크 상자: 22px r7 정본을 '항목 완료 체크'로 확장(가이드 §22 등재).
- 홈 알림·푸시는 2차. 끄기 키 규약만 `inspectionMuteKey(id)` = `inspection:{id}`.
- 알려진 별건: 다크 모드의 info 배지('안 함' 상태 배지)가 카드 위에서 검게 보인다. 공용 토큰(--badge-info-*) 문제라 손대지 않았다(독립 검수 R8).
  항목의 문제·해당 없음 배지는 걷었다(상자·칩·메모로 말한다).
- 알려진 별건: 기존 undoRoomMove·undoRoomSchedule 이 트랜잭션 안에서 전역 클라이언트(roomStillOccupied)를 부른다. 운영에서는 다른 연결로 새고, 하네스(연결 하나)에서는 시간 초과로 드러난다.
  통합 회귀는 그 호출이 안 도는 조건(방에 다른 열린 구간)으로 짰다.
