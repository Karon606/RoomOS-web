# Vercel 사용량 — 무엇이 CPU 를 먹는가 (2026-09-09 조사)

Hobby 플랜에서 함수별 CPU 는 **API·CLI 로 못 본다.** `vercel usage` 는 404, `vercel metrics` 는
1시간 창조차 Observability Plus 를 요구한다. 런타임 로그는 1시간만 남고 소요시간 필드가 없다.
그래서 아래는 **우리 쪽에서 잴 수 있는 것으로 세운 모형**이다. 대시보드 Observability 로 확인할 것.

## 실측한 것
- 배포 484건(9-9 정리 전) · 30일 커밋 923건 중 **문서만 바뀐 것 314건(34%)** · 최다 95건/일.
- 로컬 `next start` 부팅+첫 응답 CPU **1.10초**(M 시리즈), 웜 상태 `/login` 렌더 **12ms**.
  Vercel vCPU 는 이보다 느려 콜드 스타트 2~3초로 본다. **콜드 1회 = 웜 요청 수백 회.**
- 9월 PDF 발급 저장 24건(계약서 10 · 실거주 확인서 14). 미리보기·보내기는 저장이 안 남는다.
- 공개 공실 페이지 방문 9월 95건(하루 10 안팎). 방문 1건이 pageview·gallery·closeup 등 3~6회
  함수 호출을 일으키고, **밤낮없이 흩어져 들어와 매번 콜드 스타트**를 부른다.
- 미들웨어 없음. 크론 하루 2회(가벼움). 폴링은 `/api/build` 10분 주기(빈 응답)뿐.
- 대시보드 page.tsx 2333줄, prisma 호출 49개, **루프 안 await 9개(N+1)**. 응답 후 `after()` 로
  `applyScheduledRents` 를 돌리지만 그 함수는 인덱스 조회 1회에 대상 없으면 즉시 반환이라 가볍다.
- Prisma 는 모듈 스코프 1회 생성(요청마다 새로 안 뜬다). pdfToPng 는 클라이언트 전용.

## 모형 (4시간 = 14,400초를 어디에 썼나)
1. **콜드 스타트** — 배포마다 함수가 새로 만들어져 다음 요청이 콜드다. 배포 484 × 건드린 함수
   2~3개 × 3초 ≈ 1시간 남짓. 여기에 공개 페이지 방문·운영자 첫 접속의 콜드가 얹힌다. **가장 크다.**
2. **운영자 화면** — 대시보드·입주자 페이지 SSR 과 서버 액션. 하루 100회 × 0.3초 × 30일 ≈ 15분~30분.
3. **PDF** — chromium 콜드(압축 해제)가 특히 비싸다. 발급+미리보기 60회 × 8초 ≈ 8분.
합이 대략 2~3시간이라 4시간과 자릿수가 맞는다. **정확한 비율은 대시보드가 말해 준다.**

## 줄이는 길 (효과 순)
1. **문서만 바뀐 커밋은 배포하지 않는다.** vercel.json `ignoreCommand` 가 그 자리다(exit 0 = 건너뜀).
   34% 가 즉시 빠진다.
2. **푸시를 묶는다.** 작업마다 즉시 푸시하는 지금 규칙(2026-06-19)은 배포 = 콜드 스타트를 곱한다.
   운영자 결정 사항.
3. 대시보드 N+1 을 걷는다(루프 안 await 9개).
4. 그래도 차면 Pro. 초과분 종량제라 멈추지 않는다.

## 배포 정리
`node scripts/prune-vercel-deployments.mjs --apply` (안전 확인 `check-live-share-links` 가 세트).
보존 정책 30일은 우리 속도에서 무의미하고 기간 단축은 API 가 거부한다(대시보드 확인).

## 결정과 적용 (2026-09-09 운영자 확정)
- **문서 커밋 배포 제외 — 적용됨.** vercel.json `ignoreCommand`:
  `git diff --quiet ${VERCEL_GIT_PREVIOUS_SHA:-HEAD^} HEAD -- . ':(exclude)*.md' ':(exclude)knowledge/' ':(exclude)docs/' ':(exclude).claude/'`
  exit 0 이면 건너뛰고 그 외(1, 128)면 빌드한다. 기준을 마지막 성공 배포 SHA 로 둔 이유는 묶음
  푸시다 — HEAD^ 만 보면 마지막 커밋만 문서일 때 앞선 코드 커밋까지 건너뛴다. 실패 방향은 늘 "빌드".
  실제 커밋 쌍 검증: 문서 0 · 코드 1 · 묶음(코드+문서) 1 · 없는 SHA 128.
- **푸시는 묶는다.** 커밋은 작업마다 바로, 푸시는 하루 몇 번·긴급 건·실기 확인 직전에만.
  6-19 "바로 커밋·푸시"의 푸시 절반이 개정됐다.
- 대시보드 Observability 확인은 운영자 몫으로 남아 있다. Cold/Warm 비율과 경로별 CPU 두 화면이
  위 모형의 검증이다. Pro 전환은 그 뒤 판단.
