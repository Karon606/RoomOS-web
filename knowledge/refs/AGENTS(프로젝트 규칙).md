## 세션 시작 규칙
세션 시작 시 항상 프로젝트 루트의 Work_log.md(최근 진행, 시간순)와
knowledge/INDEX.md(지식 베이스 지도, 주제별)를 먼저 읽고 작업 상태·도메인 사실을 파악한 후 이어간다.
- Work_log = "무엇을 했나", knowledge/ = "무엇이 참인가". 추론하지 말고 knowledge/ 노트를 사실로 쓴다.
- 중요한 도메인 규칙·의사결정이 생기면 knowledge/ 에 노트로 적립한다(특히 §4 결제·계약·재고 규칙, 결정 근거).
- knowledge/ 는 Obsidian Vault(마크다운 + [[위키링크]]). 코드가 진실이며 노트의 file:line 은 시점 기록이라 단정 전 확인.

## 오류신고 처리 규칙 (5단계, 2026-07-18 운영자 오더 — 이전 트랙 규칙 대체)
세션 시작 시 `node --env-file=.env.local scripts/check-error-reports.mjs` 를 실행해 미처리(open) 오류신고를 확인하고, 있으면 아래 5단계를 그대로 수행한다.
1. 신고 내용을 카테고리로 분류한 다음, 신고 내용을 **원문 그대로** 운영자에게 보여준다.
2. 신고 내용에 가장 알맞은 전문가를 섭외하되, 다양한 측면으로 볼 수 있도록 각 분야의 전문가를 다수 섭외한다(서브에이전트 패널). **UX/UI 전문가와 디자인가이드를 꼼꼼히 따지는 웹디자이너는 항상 섭외한다.**
3. 바로 작업하지 않고 전문가들과 논의한 후 계획을 세운다. 신고가 다수이면 가장 효율적인 작업이 되도록 순서도 함께 정해 보고한다. 이 오류·문제점이 정확히 무엇인지, 왜 발생했는지도 함께 보고한다. **이 단계에서 코딩 작업은 하지 않는다**(원인 분석을 위한 조사·코드 읽기만 허용, 수정 금지).
4. 계획과 보고서를 운영자에게 보여주고, **운영자 승인 전에는 절대 먼저 작업하지 않는다.**
5. 작업은 철저히 계획대로 진행한다. 돌발상황이 발생하면 해당 오류에 대해 1번으로 돌아가 다시 진행한다.
- 처리 완료 후 `... done <id>`, 보류 시 `... dismiss <id>` 로 상태를 갱신한다.

## 작업 검증 규칙 (필수)
모든 개발 작업(기능 추가·버그 수정 등)은 프로젝트 루트의 loop.md를 **항상 참고**한다.
"구현 완료"라고 말하기 전에 loop.md의 1~4번 기준(필수 통과·측정·평가·인간 호출)을 스스로 점검하고,
통과하지 못하면 스스로 원인을 분석해 수정한 뒤, loop.md 5번에 따라 최종 증거 보고서를 제출한다.
특히 loop.md 4번(DB 스키마·인증/권한·결제 로직·기획 충돌)에 해당하면 임의 수정하지 말고 운영자에게 먼저 확인한다.
UI를 만들거나 고칠 때는 loop.md 1번의 'UI/UX 정합' 게이트(정본 컴포넌트 재사용·형제 페이지 문법 대조·가이드 § 확인)를 반드시 먼저 통과한다 — 기능이 돌아가도 이질감이 있으면 미완성이다.
