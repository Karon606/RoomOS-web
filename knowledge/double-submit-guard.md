# 중복 제출 방어 — 대기 표시와 서버 가드

운영자 실피해에서 나온 규칙. 2026-07-17 앱 전체 전수 감사(4영역 분할) 결과를 적립한다.

## 사건 (2026-07-17)
공지 문자 '이 내용을 템플릿으로 저장'을 눌렀는데 **누른 표시가 없었다**. 서버 왕복이 1~2초 걸리는 동안 버튼은 계속 눌리는 상태였고, 토스트는 왕복이 끝나야 화면 **맨 아래**에 떴다. 운영자 눈은 버튼에 있으니 반응이 없다고 느껴 5번 눌렀고 요청이 5개 나가 **템플릿이 5개 생겼다**.

운영자 증언: "저장을 눌렀는데 충분한 피드백이 없어서 반응이 없는줄알고 여러번 눌렀어."

**교훈: 토스트는 결과 통보이지 접수 확인이 아니다.** 접수 확인은 누른 그 자리에서 즉시 나야 한다.

## 정본 문법 — 대기 표시
**텍스트 교체 + disabled. 스피너 없음.** 앱 전체가 이 방식으로 통일돼 있다(계약서 저장·설정 저장·업로드 등 다수).
```
{busy ? '저장 중…' : '저장'}   // + disabled={busy}
```
- `components/ui/Btn.tsx` 에 loading/pending prop 이 **없다**. 각 호출부가 state 로 처리한다.
- 가이드 §"제출 중"은 스피너를 말하지만 **실사용 정본은 텍스트 교체**다. 새 코드는 형제를 따를 것.
- `useTransition` 의 `pending` 을 `disabled` 에 물리는 것도 정본이다.

## `isPending` 만으로는 부족한 자리가 있다
`useTransition` 의 `isPending` 은 **리렌더 후에야** 버튼에 반영된다. 같은 프레임 연타는 뚫린다. 그래서 이 프로젝트는 위험한 자리에 **동기 ref 가드**를 따로 붙인 선례가 있다.
- `InventoryClient.tsx` 의 `savingRef`/`submittingRef` — 위치별 점검 재적용 시 **허브가 2배 차감**되던 사고 이후 도입([[domain-inventory]] '위치별 점검 더블클릭 방지').
- 판단 기준: **서버가 비멱등이고 가드가 없으면** 동기 가드까지 붙인다. 멱등하면 `disabled` 로 충분.

## 감사 기준 (다음에 또 훑을 때)
셋을 **모두** 만족해야 버그다. 대기 표시가 없다고 다 버그가 아니다.
1. 클릭 핸들러가 서버 액션을 await 한다.
2. 왕복 동안 disabled 도 라벨 변경도 없다.
3. **중복 실행 시 실피해가 있다** — 행 중복 생성, 금액 이중 계상, 상태 꼬임.

3번이 핵심이다. 다음은 안전하므로 제외한다.
- 서버 멱등(예: `confirmReceipt` 는 `receivedAt` 있으면 그대로 성공 반환 / 같은 값 재대입 / id 지정 삭제).
- 서버 중복 가드 있음.
- `confirmDialog` 가 앞을 막음 — `fixed inset-0` 전면 오버레이라 왕복 전 클릭이 **물리적으로** 불가.
- 클릭 즉시 버튼이 **언마운트**됨(`{!isPending && ...}` 조건 렌더).
- stale 클로저로 같은 값을 재전송(토글 계열).

## 방어선이 화면 하나뿐인 자리 (주의)
서버가 **비멱등이고 서버 가드가 없는데** 클라 잠금만으로 막고 있는 곳. 그 잠금을 건드리면 즉시 사고가 난다.
- **`api/contract/generate`** — 파일명에 `Date.now()`, 계약 순번은 `count()+1`. 부를 때마다 Drive 파일과 `ContractFile` 행이 새로 생긴다. 방어 = `ContractView.tsx` 의 `contractSaving` **하나뿐**. **멱등화하지 않기로 결정(2026-07-17)** — 내용을 고쳐 다시 저장하면 새 파일이 생기는 게 정상이라, 서버가 실수 중복과 의도적 재저장을 구분할 수 없다. 이 경로를 손댈 때 `contractSaving` 잠금을 **절대 우회·제거하지 말 것**.
- `assets/actions.ts` 의 `addFreeAsset`·`setAssetReceived`(부분수령) — 서버 가드 없음. 방어 = `AssetsClient` 의 `disabled={pending}`. 동기 ref 가드는 없다(미판단).

## 서버 가드 정본 (2026-07-17, 0c26afc)
**조건부 `updateMany` + `count === 0` 검사**로 상태를 선점한 뒤 파생 행을 만든다. 행 잠금이 직렬화하므로 뒤늦은 요청이 걸러진다.
```ts
const r = await tx.pendingReceipt.updateMany({ where: { id, propertyId, status: 'pending' }, data: { status: 'approved' } })
if (r.count === 0) return null   // 다른 요청이 이미 선점
```
- 선점과 파생 행 생성을 **한 트랜잭션**으로. 안 그러면 '승인됐는데 지출 없음'이 생긴다.
- 선례: `finalizePendingReceipt`(주석에 '중복 등록 방어'), `approvePendingReceipt`(2026-07-17 통일).
- DB 재현 검증: 동시 3건 중 선점 1 / 차단 2.

**멱등 반환 문법** — 생성이 1회뿐이어야 하는 자원은 '이미 있으면 그대로 반환'.
- `getOrCreateCalendarToken`, `getOrCreateJoinCode`(2026-07-17 신설).
- **주의**: 재발급(기존 무효화)은 의도적 행위라 **별도 액션으로 분리**한다. 하나로 합치면 재발급이 깨진다. 호출부가 상태로 둘을 가른다.
