# 테스트 서버 도입 계획 (운영자 오더 2026-08-03)

운영자 원문 — "기존 기능은 그대로 진행되지만 똑같은 내용에 신기능이나 버그를 fix한 것들을
실제 사이트에 바로 푸시하는게 아니라 테스트 사이트를 거치고 거기서 ㅇㅋ를 받으면 실제 사이트에 푸시되는거지."

**우선순위 — 진행 중이던 전수검사(E페이즈 잔여)와 신고 처리가 먼저다**(운영자 지시).
이 문서는 결정사항을 잃지 않으려고 먼저 적어둔다.

## 왜 필요한가

환경이 하나다. 코드도 DB도 Drive도 전부 운영이다. 2026-08-02~03 하루에만 실서버 배포가 열두 번 넘었고
데이터 정정 스크립트를 여섯 번 돌렸다. 전부 실제 장부에 바로 적용됐고 `--revert` 가 유일한 안전장치였다.
스키마 변경(`receiptNo`·`contractNo`)도 운영 DB 에 바로 들어갔다.

## 운영자 확정 사항

| # | 항목 | 결정 |
|---|---|---|
| 1 | 테스트 DB 데이터 | **운영 데이터 복사** |
| 2 | 도메인 | **Vercel 기본 주소** (별도 DNS 없음) |
| 3 | 검색 노출 | **비밀번호로 잠근다** (noindex 만으로 부족) |
| 4 | 문자·푸시 | **실제 발송 없이 화면에만 찍는다** |

## 구조

```
develop  ->  <project>-git-develop-*.vercel.app   ← 테스트 DB · 테스트 Drive 폴더 · 발송 차단
main     ->  www.stayeum.com                       ← 운영
```

작업은 `develop` 에서 하고, 운영자가 테스트 사이트에서 확인한 뒤 승인하면 `main` 으로 올린다.
지금 흐름에서 바뀌는 것은 **마지막에 운영자 승인이 한 번 끼는 것**뿐이다.

## 반드시 분리해야 하는 것 셋

1. **DB** — 안 나누면 테스트로 만든 가짜 입주자·수납이 실제 매출에 섞인다.
2. **Drive 폴더** — 안 나누면 테스트로 만든 계약서 PDF 가 실제 폴더에 쌓인다.
3. **발송(문자·웹푸시)** — 안 막으면 테스트 중에 실제 입주자에게 문자가 간다. (4번 결정으로 확정)

## 운영 데이터 복사에 딸린 위험 (1번 결정의 대가)

실명·연락처·생년월일·서명 이미지가 테스트 DB 에 그대로 들어간다.
그래서 **3번(비밀번호 잠금)이 선택이 아니라 필수 조건**이다. 둘은 한 세트다.
복사 주기와 방법(수동 스냅샷 복원 vs 정기 동기화)은 착수 시 정한다.

## 착수 시 순서

운영자 계정 작업이 섞여 있어 같이 해야 한다.

1. Supabase 테스트 프로젝트 생성 → 운영 스냅샷 복원 (운영자)
2. Google Drive 테스트 폴더 생성 + 서비스 계정 권한 (운영자)
3. Vercel `develop` 브랜치 환경변수 세팅 — DB URL · Drive 폴더 ID · `STAGING=1` (운영자)
4. Vercel Deployment Protection 으로 비밀번호 잠금 (운영자)
5. 코드 쪽 — `STAGING` 플래그로 문자·웹푸시를 화면 출력으로 대체, 배너 표시 (나)
6. 배포 흐름 문서화 + AGENTS.md 반영 (나)

## 미결

- 테스트 DB 를 얼마나 자주 최신화할 것인가
- 스키마 변경을 테스트에 먼저 적용하는 절차(현재는 `scripts/migrate-*.ts` 를 직접 실행)
- 운영자 승인 기록을 어디에 남길 것인가
