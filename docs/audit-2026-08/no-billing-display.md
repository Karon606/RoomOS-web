## 사실

**두 경로가 서로 다른 이유로 같은 0원을 만든다.**

| 호실 | 상태 | 사정 | 실제로 낸 돈 |
|---|---|---|---|
| 503 송호준 | ACTIVE · 단기 | 입주 7/29, 퇴실 예정 8/29. 단기는 rentAmount 가 체류 전체 사용료라 **입주월에만 청구** | 7/29 에 420,000 완납 |
| 507·509 | CHECKOUT_PENDING | 납부일 7일, 퇴실 예정 8/2. 퇴실일이 8월 납부일(8/7)보다 앞이라 **무청구 퇴실월** | 7/7 에 470,000 완납 |

**정정.** 507·509 는 뱃지가 이미 '퇴실 예정'으로 뜬다(`showCheckout` 분기가 먼저 걸린다).
완납 뱃지를 먹는 건 503호 하나다. 운영자가 "507·509도 마찬가지"라고 한 것은 **뱃지가 아니라 0원 두 개**를 가리킨 것으로 읽어야 맞다.

## 이미 처리한 것 (커밋 4779e50)

`getTargetMonthOptions` 가 무청구 달을 귀속월 선택지에서 제외하도록 고쳤다. 표시 문제를 넘어
**청구 0인 달에 수납을 넣도록 유도**하던 실질 위험이라 먼저 처리했다. A-findings P2 동시 봉합.

## 남은 작업 — 패널 설계 (UX 라이터 겸 웹디자이너)

### 1. 서버가 이유와 금액을 내려보낸다

`app/(app)/rooms/actions.ts` 의 `RoomRow` 에 두 필드 추가.
```
noBillReason: 'shortTermPrepaid' | 'checkoutNoBilling' | null
noBillCoveredAmount: number | null   // 그 달을 덮은 실수납 합
```
`checkoutNoBilling` 은 이미 지역변수로 계산돼 있고(`isCheckoutNoBillingMonthFor`), 단기 쪽은
`billForLeaseMonth` 내부의 `isShortTerm && mon !== inMonth` 판정과 같은 규칙이다.
**새 계산이 아니라 이미 있는 두 판정을 표면으로 올리는 것.** 클라 재계산 금지 원칙을 지킨다.

### 2. 수납관리 뱃지·금액

| 항목 | 값 |
|---|---|
| 라벨 | **청구 없음** (4자) |
| 톤 | **paid**(기존 Olive). 새 톤 만들지 않는다 — 돈 문제가 없는 정상 상태다 |
| sub (단기) | `입주월에 전액 납부` |
| sub (퇴실월) | `8/6까지 납부됨 · 오늘 8/2 퇴실` |
| secondary (퇴실월) | `{ tone: 'exit', label: '퇴실 예정' }` |

- 분기 삽입 위치는 `!room.isPaid`(미납) **다음**, `showCheckout` **앞**. 이월 미수가 있으면 미납이 먼저여야 한다.
- 청구액 자리는 `0원` 대신 **`청구 없음`** 텍스트. 숫자 0은 데이터에 그대로 두고 표시만 바꾼다
  (스트립 합계·정렬 키 무영향). 선례 있음 — `PaymentSummaryCards.tsx:54`, `PaymentBody.tsx:131`.
- 총납부 자리는 숫자 0 유지 + 캡션 `총납부 0원 · 7/7 수납 470,000원`.
  **숫자 자체를 바꾸지 않는 이유**: `totalPaid` 는 월 격리 값이고 엑셀·AI 등 소비처가 그 의미에 의존한다.
  바꾸면 8월에 안 들어온 47만이 8월 실적으로 샌다.
- `knowledge/money-display-feedback` 과 충돌하지 않는다. 그 노트가 채택한 해법이 정확히
  "사실은 보조 텍스트로, 집계는 월 격리 유지"이고 `TenantClient.tsx:2087` 의 `예약금 {금액} 포함` 캡션이 그 구현이다.
- **카드와 표 두 곳을 같이 고칠 것.** 이 파일은 쌍둥이 구조다(405호 건에서도 표 쪽이 따로 있었다).

### 3. 정렬·필터는 건드리지 않는다

정렬 그룹 신설 안 함(503 은 4=완납, 507·509 는 1=퇴실예정 그대로). 정렬은 '할 일 순서',
뱃지는 '무슨 상태'라 축이 다르다. 필터 칩도 신설 안 함 — 칩이 이미 7개고,
'완납 N실'에서 빼면 "미납+퇴실예정+납부예정+완납+공실 = 전체" 등식이 깨진다.

## 운영자 판단 대기

**홈의 '완납 N건'에 청구 없는 방을 넣을 것인가.** 그대로 두면 완납 건수에 청구 없는 방이 섞이고,
빼면 분모(`billableLeases`)와 분자가 어긋나 수납률이 흔들린다. 수납률 정의에 달린 문제라
임의로 정하지 않는다(loop.md 4번).

## 그 외 남은 것 (별건, 우선순위 낮음)

**유예 판정 규칙이 화면마다 다르다.** 클라 `getEffectiveDueInfo`(`RoomsClient.tsx:177-185`)는
`overrideDueDayMonth === dueMonth` 일 때만 유예를 인정하는데, 서버 `effDueDateForMonth` 와
대시보드 `daysOverdueForMonth` 는 **다음 달 조정이 이전 달 미납 기한을 미루는 파급**까지 인정한다.
현재 해당 데이터가 0건이라 증상은 없다. 봉합하려면 `lib/dueDate` 쪽 규칙으로 통일해야 한다.
