## 1. 정본이 잘 서 있던 것

- 소프트삭제·복구가 서류 3종 대칭이고 적용취소 진입점이 네 화면에 다 있다(§16 충족).
- `deletedAt: null` 필터가 목록·검색·알림·파일 스트리밍 전 지점에 누락 없이 붙어 있다.
- 서명 토큰 설계(256비트·24시간·Serializable getOrCreate·5회 잠금·httpOnly 쿠키)가 견고하다.
- 쓰기 액션에 `requireEdit` 누락이 없고, 대상 레코드는 전부 `{id, propertyId}` 복합 조건으로 조회한다.
- 확인서 금액 정본이 실입금이다. 기록 없는 과거 달에 계약액을 자동 기입하지 않는다.

**패턴** — 규칙이 파일 하나에 모인 축은 지켜졌고, 문자열 치환·금액 조립처럼 여러 파일에 흩어진 축이 갈렸다.

## 3. 운영자 확정 사항

- 청소비 0원은 **"청소비 없음"으로 명시**(조항째 교체).
- 서명받은 계약은 **스냅샷으로 발급**하고, 바뀐 내용은 새 서명을 받아 **각각 남긴다**.
- 실거주확인서는 **정가**로 찍는다(계약서와 같은 기준).
- 청소비는 입실 수납이 있으면 퇴실 공제를 **끈다**.
- 환불 조항은 계약서에 **넣지 않는다**(설정 안내 문구만 정정).
- 발행번호는 **원장으로 만든다**(스키마 추가 승인).

## 4. 남은 것

- **E16** 영수증·확인서 generate 가 클라이언트 `body.fields` 를 무검증으로 받아 공식 도장과 함께 PDF 로 만든다.
  계약서는 DB 에서 채워 상대적으로 견고하다. 세 서류의 무결성 수준이 다르다.
- **E21** 조항 내부 상호참조(§4 가 "제2조 제1항 준용")가 섹션 이동 시 깨질 수 있다. 참조 무결성 검사 없음.
- **E22** 계약번호가 스캔 업로드본까지 세던 문제는 `contractNo` 도입으로 해소됐으나,
  기존 36건은 번호 null 이라 과거분 대조는 불가.
- **E13 잔여** 영수증·확인서 generate 에 보상 삭제 없음(계약서만 처리). Drive 고아 탐지 배치도 없음.
- `lib/integrityAudit.ts` 에 Drive 검사 0건 — 한 번 생긴 고아가 영원히 누적되고 아무도 모른다.
