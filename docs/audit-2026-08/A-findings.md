## 2. A-2 트랙 — 월 귀속·경계 규칙 (전문가 조사)

**한 줄 요약**: 정본 4종(billing·dueDate·prorate·rentDiscount)은 테스트로 방어돼 있고 규칙도 맞다.
깨지는 곳은 전부 **정본을 안 타고 손으로 다시 짠 호출부**이고, 그 손계산이 빠뜨리는 건 거의 항상
**락인 단계**와 **override 해석**이다. 게다가 월 마감 개념이 없어 오차가 지난 달로 소급 전파된다.

### 이번 달 액션이 다른 달에 영향을 주는데 화면에 그 사실이 없는 자리 (운영자 최우선 관심)

1. **할인 추가·삭제** → 과거 전월 청구·미수가 즉시 재계산. 안내 없음(DiscountWidget 124)
2. **인상 예약 등록** → 다음 달부터 오르지만 **이미 선납된 달은 안 오름**(락인). 예외 표시 없음
3. **납부일 임시조정** → 기존 다른 달 조정이 조용히 삭제됨(슬롯 1개). 경고 없음
4. **납부일을 다음 달로 미룸** → 무청구 판정·경과일·인수 cutoff 가 함께 바뀌는데 위젯은 날짜만 표시
5. **귀속월 이동** → 확인 문구가 "입금일·금액은 그대로"라며 **안심시키는 톤**. 지난 달 매출이 바뀐다는 말이 없음
6. **일괄 귀속월 이동** → 몇 건이 어느 달로 가는지 미표시
7. **과거 날짜 지출·부가수익 입력** → 지난 달 손익 변경. DatePicker minDate 없음, 서버 검증 없음
8. **퇴실 예정일 저장** → 다음 달 일할 즉시 확정 저장(먼 미래는 게이트 있음 — 이건 일관)
9. **수납 기록 삭제** → 어느 달 매출이 줄어드는지 미표시

### 정본 복제 현황
override 해석 로컬 복제 6개(overrideAbsDate ×2, effectiveDueDayForMonth ×3, resolveDueRaw ×1).
게다가 `lib/billing.ts:68 resolveDueDateForMonth` 가 `lib/dueDate.ts` 와 **두 번째 정본**으로 병존.

## 3. A-3 트랙 — 소프트삭제·현금영수증·카드 정산 (전문가 조사)

### 소프트삭제 — [정상] 오차 0
익스텐션 우회 경로 없음(원시 SQL·findUnique·원시 클라이언트 전부 확인). seqNo 채번 9곳 opt-out 정상.
실측 대조: 7월 이용료 수납 16,249,000(삭제 포함) vs 15,779,000(활성), 보증금 890,000 vs 840,000,
현금영수증 5,832,000 vs 5,362,000 — **네 집계 모두 삭제를 정상 반영.**
잔여 경미 2건: 복구 진입점이 undo 토스트뿐(토스트 사라지면 삭제분을 볼 곳이 없음), updateMany 는 익스텐션 미적용.

### 현금영수증 — **실 금전 오차 2건**

1. **[오차] 김민정 172,000원 (2026-07-26, payMethod '결제선생')**
   결제선생은 카드 계열(`lib/paymentMethods.ts:8` CARD_LIKE_METHODS)인데 현금영수증 스탬프가 찍혀 있다.
   `rooms/actions.ts:1413-1416` 의 두 if 가 배타가 아니라 **현금영수증 합계와 카드 수납 합계에 동시 계상**.
   카드 매출전표가 현금영수증을 대체하므로 세무상 이중 인식. 입력 폼에 payMethod 연동 가드가 없다.

2. **[구조적 누락] FIFO 이월 record 는 스탬프가 불가능** (`rooms/actions.ts:819`)
   조건이 `isOriginalMonth && portion > 0` 인데, 지정월이 이미 완납이면 원본월 record 자체가 안 생긴다.
   실측: 과납 이월 record 13건 **전원** 스탬프 없음. 그중 9건은 형제 record 조차 없다.
   7월 해당분 — 오병용 470,000(payDate 7/31, targetMonth 8월), 민경진 350,000(7/27, 8월).
   **발행 체크를 했다면 7월 합계에서 최대 820,000원 누락.** 알려진 부채(2026-07-14)가 현재도 유효.

3. [잠복] `getMonthPaymentAggregates` 가 isDeposit 무필터 — 보증금에도 스탬프 가능. 현재 해당 0건.

### 카드 정산 — [위험] 3건

1. **[가정 붕괴] payDay < cutOffDay 계좌** (`CardSettlementClient.tsx:107`)
   등록된 하나카드 'MG+ S' 가 마감 19일·결제 1일이다. 코드는 7/20~8/19 거래를 8월로 묶고
   명목 결제일을 8/1 로 계산하는데, 이는 마감(8/19)보다 앞선 **불가능한 날짜**이고 실제 이체는 9/1.
   미정산 건이 생기면 "8월 결제 확정"으로 떠서 한 달 앞당긴 이체를 유도한다. 현재 미정산 0건이라 무증상.
   파생: cutOffDay null·31 이면 청구기간 문자열이 2개월치로 표기(롯데 Hilton 62건 해당),
   말일 결제가 주말이면 헤더 월과 실제 이체월이 어긋남, 할부·부분취소 개념 없음.

2. **[비대칭] 대상 판정** — 생성은 '신용카드'만 UNSETTLED 인데 조회는 '체크카드'도 포함.
   체크카드는 항상 SETTLED 로 생성되므로 정산한 적 없는 지출이 '정산완료'로 표시된다(현재 0건, 잠복).
   `Expense.settleStatus` 기본값이 SETTLED 라 신규 경로가 명시를 빠뜨리면 미정산에서 영구 누락.

3. **[무피드백] 확정·정산취소 실패가 안 보인다** (`finance/actions.ts:1638·1647`)
   두 액션 모두 반환값 void, 클라(`CardSettlementClient.tsx:158·387`)는 try/catch·토스트 없음.
   권한 거부·네트워크 실패면 refresh 조차 안 돌고 화면 그대로 — 운영자는 정산된 줄 안다.
   같은 파일의 다른 액션은 `{ ok, error }` 규약인데 여기만 이탈. 적용취소도 없다(rollback 원칙 위반).
   `settledAt` 컬럼이 없어 '언제 정산했는지' 자체를 모른다.

4. [정상] 중복 계상 없음 — settleStatus 는 어떤 금액 집계 필터에도 쓰이지 않는다(표시 전용).
