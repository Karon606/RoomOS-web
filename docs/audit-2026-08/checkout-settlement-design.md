## 퇴실해야 하는 날 (must-leave date)

정산 판정의 기준선. **다음 납부일 − 1일.** 납부일이 20일이면 퇴실해야 하는 날은 19일.
```
dayOf(y,m) = dueDay 가 '말'이면 그 달 말일, 아니면 min(dueDay, 그 달 말일)
그 달 d < dayOf(y,m) 이면 기간 시작은 전월
mustLeave = 다음 기간 시작일 − 1일
```
말일·30일 납부일이 짧은 달과 만나는 경우를 `min(dueDay, 말일)` 이 흡수한다.
UTC 고정 산술로 계산한다(로컬 `new Date(y,m,d)` 와 DB 의 UTC 자정을 섞으면 하루 밀린다 — 실제로 겪음).

## 핵심 개념 — 정산 기간(settlement period)

세 경우를 따로 코딩하지 않고 **퇴실일을 품는 서비스 기간 하나**를 확정한 뒤 선납 여부로 분기한다.
```
settlementStart = 그 달 dueDay (입주월이면 max(dueDay, 입주일))
settlementMonth = 퇴실일 >= settlementStart ? 퇴실월 : 전월
daysUsed        = 퇴실일 - settlementStart + 1
prepaid         = settlementMonth record 의 actualAmount 합
prepaid > 0  → 기간 만료 전(case 1) / prepaid == 0 → 기간 경과(case 2)
```
이 하나가 "일할·환불이 퇴실월 단일에만 걸려 전월 돈을 못 건드린다"는 P0 을 해소한다.
`finalizeRentRefund`·`previewCheckoutRefund` 는 이미 임의 월을 다루게 짜여 있어 기준월 산출 한 줄 교체로 끝난다.

## 계산

| 경우 | 처리 | 저장 |
|---|---|---|
| (a) 만료 전 · 환불 안 함(기본) | 일할을 **아예 걸지 않는다**. 그 달 청구는 락인/월세로 전액 | `checkoutProrationUndo.settlement` 에 결정 기록 + StatusLog.reason |
| (b) 만료 전 · 환불 | `calcCheckoutRefund` 그대로(prepaid − usedAmount − 위약금). **정산 기간 월**로 `finalizeRentRefund` 호출 | 기존 동작 재사용(원 record 소프트삭제 + companyKeeps 재기록) |
| (c) 경과 · 부과(**기본**) | `usedAmount = floor(월세 × daysUsed / 30)` 를 `checkoutProratedAmount` 에 넣는다. record 0건이라 미납으로 뜬다 | 새 메커니즘 없음 — 기존 필드 재사용 |
| (d) 경과 · 면제(선택) | 아무것도 하지 않음(현재 동작). 사유를 StatusLog 에 남긴다 | — |

기본값이 (a)·(c) 인 이유: 둘 다 **원칙**이고, 예외인 (b)·(d) 만 운영자가 의식적으로 고른다.

`isBillingAdjust` 마커 record 방식은 배제(락인 우선순위와 겹쳐 순서 의존 발생, 퇴실일==dueDay 에서 1일치 삼켜짐).

## 질문 시점 — 2회 (운영자 확정)

> "미리 퇴실예정일을 미리 입력할거고 그 날짜가 퇴실해야 하는 날짜보다 전이면 환불처리를 할지 일단 물어는 보고,
> 이후가 되면 일할 계산할지 물어보고 처리는 하되, **실제 퇴실날짜에 처리하면서 다시 한번 더** 환불할지 일할부과할지를 물어보게 하는게 좋을 것 같아"

| 시점 | 성격 | 하는 일 |
|---|---|---|
| 퇴실 **예정일 입력** | 의향 확인 | 예정일 ≠ 퇴실해야 하는 날이면 묻는다. 답은 `checkoutProrationUndo.intent` 에 **의향으로만** 저장 |
| 퇴실 **완료 처리** | 확정 | 실제 퇴실일 기준으로 다시 계산해 다시 묻는다. 이때 돈이 움직인다 |

핵심은 **예정 시점 답변이 돈을 건드리지 않는다**는 것. 예정일은 바뀐다(실측 서민준 예정 6/13·실제 6/16).
지금의 자동 일할 적용은 예정일이 바뀔 때마다 무통보로 청구를 덮어쓰는데, 그게 신고 0df59b92 의 뿌리다.
의향은 완료 화면에서 **기본 선택값으로 되살아난다** — 두 번 물어도 두 번 고민하지 않게.

`CheckoutProrationWidget` 은 존치(자동 적용만 제거).

**퇴실 미니폼과 편집폼 환불 모달을 같은 컴포넌트로 통일해야 한다** — 안 그러면 또 경로별로 갈린다(B-3 P0 의 형태).

## UI (UX·디자이너 설계)

- **주의**: 운영자가 말한 "환불"은 미니폼의 기존 '환불액'(**보증금**)과 **다른 돈**(이용료)이다. 합치면 안 된다.
  블록 라벨에 '이용료'·'보증금'을 반드시 명시.
- 컨트롤은 **SegmentedControl** (확인창 alt 는 금액 미리보기를 못 보여줘 부적합). `CheckoutProrationWidget` 이
  이미 정산 방식을 세그먼트 2지선다로 묻고 있어 같은 문법.
- 위치는 퇴실 미니폼 안, 퇴실일 아래·보증금 블록 위.
- **정상 퇴실(퇴실일 == 예정일)이면 블록 자체를 렌더하지 않는다.** 대다수 퇴실은 지금 화면과 동일.
- 기본값 상태에서는 금액 입력을 띄우지 않는다(+78px). 선택 시에만 펼침(+52px).
- **임계값 없음(운영자 2차 확정으로 이전 안 폐기).** 하루라도 어긋나면 묻는다.
  "봐주기"는 운영자가 선택지에서 고르는 것이지 프로그램이 미리 판단할 일이 아니다.
  단 **기본 선택값**은 정책 기본값(초과=부과, 조기=환불 안 함)에 맞춘다 — 원칙이 기본, 예외가 선택.
- 한 번의 퇴실에서 새 결정은 **최대 1개**(조기이거나 초과이거나, 동시 발생 없음).
- 선택 사실은 `StatusLog.reason` 에 남긴다 — "조기 퇴실 6일 · 환불 안 함" 등. 표시 선례 `TenantClient:186-197`.

## 회귀 위험

자동 일할 제거는 `prorationDataForChange` 호출부 2곳의 `autoApply` 를 false 로 고정하면 끝이다
(tenants/actions 424·1326). `!wasApplied && !autoApply → no-op` 이 항상 참이 되어
**미적용 계약은 손대지 않고, 이미 적용된 계약의 재계산·해제 분기는 전부 살아 있다.** 회귀 표면이 좁다.

바뀌는 것: 퇴실월 선납 추천액·캘린더 청구 이벤트가 일할액에서 전액으로(정책상 맞다).
가장 위험한 셋: ① 퇴실월 청구 상승으로 부분 수납 계약에 미납 발생(실측 대상 0건)
② (b) 정산월이 전월이면 **과거 달 결산 소급 변동** ③ (c) 부과분이 CHECKED_OUT 이라 미납 집계에 안 보일 수 있음.
